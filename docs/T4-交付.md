# T4 交付：可复现的测试、可引用的实测、5 分钟 Demo

M4 的四件事——测试不依赖本机 MySQL、压测数据回填、README 与 Demo、AI 会话归档——都不产生新功能，
但决定了"这套东西是不是别人的机器上也能跑、说的数字是不是自己测的"。下面是每件事的做法与代价。

---

## 1. T4.1 集成测试搬到 Testcontainers

### 1.1 原来的问题不是"跑不起来"，而是"绿得没有意义"

12 个集成测试类各自写着 `spring.datasource.url=jdbc:mysql://localhost:33061/notify`，再用
`@EnabledIfEnvironmentVariable(named="MYSQL_IT", matches="true")` 拦一道。干净机器上 `mvn verify` 的结果是
**全绿**——但那是 60 多个单测的绿，40 多个集成用例一个没跑。这种绿比红更危险：CI 上没人会去数用例数。

### 1.2 做法：进程内单例容器 + 一个基类

```java
public abstract class AbstractIntegrationTest {          // 12 个集成测试类都继承它
    @DynamicPropertySource
    protected static void dataSourceProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", SharedMySql::jdbcUrl);   // 首次取值时才启动容器
        ...
    }
}
```

三个决定，每个都有被否掉的替代方案：

| 决定 | 否掉的方案 | 为什么 |
| --- | --- | --- |
| 整个 JVM 共用一个容器（singleton container） | 每个测试类 `@Container` | Spring 的上下文缓存按 `@SpringBootTest(properties=...)` 分组，本项目十来套属性组合 → 十几次 10 秒级启动 + 十几个 795MB 实例 |
| 容器句柄显式写在 Java 里 | `jdbc:tc:mysql:8.0.46:///notify` 一行配置 | `jdbc:tc:` 是「每个 DataSource 一个容器」，恰好放大上面那个问题；且容器生命周期藏在 URL 里，读代码看不见 |
| 删掉 `MYSQL_IT` 门禁，测试无条件跑 | 保留门禁、CI 里设 true | 门禁的存在本身就是"本地可以假装通过"的入口；需要 Docker 是 Testcontainers 的前提，写在 README 里就够 |

镜像与 `docker-compose.yml` 同版本（`mysql:8.0.46`），避免"测试过、生产挂"只因小版本差异。
离线环境可用 `-Dtestcontainers.mysql.image=<本地镜像>` 覆盖。

**代价**：跑集成测试需要 Docker；容器启动约 16s（一次性，之后所有上下文复用）。

**结果**：`mvn verify` → **166/166，0 skipped**，不需要 `MYSQL_IT`、不需要本机装 MySQL。

### 1.3 顺手补上 §9.2 用例 3

七条用例里，"双投窗口"原先没有测试——它最难写，因为要模拟"HTTP 已发出、结果没落库"。
新增 `AtLeastOnceIntegrationTest`：真实投递成功一次后，把库回滚成 `PROCESSING + 租约过期 + 明细不存在`
（这是 kill -9 落在两条语句之间的磁盘形态），再让第二个实例接手，断言**下游收到两次完全相同的报文**、
系统只记一次尝试、且最终收敛到 SUCCEEDED 不再重投。

这条测试钉的不是 bug，是**契约**：at-least-once 意味着重复是设计的一部分，能承诺的只有"不丢 + 会收敛"。

### 1.4 §9.2 七条用例 → 测试映射

| §9.2 | 用例 | 落在哪 |
| --- | --- | --- |
| 1 | 幂等 | `IngestIntegrationTest`：同键重复提交同一单号；**十并发同键**只落一行；不同 caller 同键互不影响 |
| 2 | 崩溃恢复 | `LeaseRecoveryIntegrationTest`：租约未到期抢不走 / 过期被接手且 `attempt_count` 递增 / 旧实例结果不许覆盖新状态 / 崩溃消耗预算但不会无限重投 |
| 3 | 双投窗口 | `AtLeastOnceIntegrationTest`（本轮新增）：下游收到两次、系统只记一次尝试、自动收敛 |
| 4 | 失败分级 | `DispatcherIntegrationTest` + `DeadLetterIntegrationTest` + `ErrorClassifierTest` + `BackoffPolicyTest`：4xx 一次进 DEAD、5xx 按指数退避带抖动、429 遵守 `Retry-After` |
| 5 | 熔断隔离 | `CircuitBreakerIntegrationTest`：坏端点被推迟且**不计尝试次数**、好端点全部成功、恢复后明细不出现序号空洞 |
| 6 | 背压 | `BackpressureIntegrationTest` + `BackpressureGuardTest`：超阈值 503 + `Retry-After` 且不落库；**退避中的老任务不触发背压**（用创建时间算年龄就会踩这条） |
| 7 | 测试隔离 | 所有 `@SpringBootTest` 都带 `notify.dispatcher.scheduler-enabled=false`，投递一律由 `pollOnce()` 手动驱动 |

## 2. T4.2 压测：150 QPS 下的三个数

### 2.1 压测器为什么是自己写的 80 行 Java

- `ab` 单连接串行，且**无法给每个请求不同的幂等键**——9000 次请求会全落到幂等分支上，
  真正要测的"每单一串写"一次都不会发生；
- `k6`/`wrk` 本机没有。为了一个"按 150 QPS 打 60 秒、记分位数"的需求，让复现者先卡在装工具上，不划算；
- JDK 自带 `HttpClient` + 虚拟线程足够：实测速率误差 <0.5%（150.0 vs 150）。

`scripts/loadtest.sh` 负责编排（12 个 mock 下游、起实例、采指标、数库里的行），`scripts/loadgen/LoadGen.java`
只负责按节奏发请求 + 记延迟。

### 2.2 实测结果（macOS + Docker Desktop，MySQL 8.0.46 容器）

| 场景 | p50 | p90 | p99 | p999 | 达成速率 | 结果 |
| --- | --- | --- | --- | --- | --- | --- |
| A 纯受理（关调度器），150 QPS | 3.2 | 7.0 | **16.9** | 33.9 | 150.0 | 全部 202 |
| B 全链路，下游 ~1ms（3 次） | 3.2 / 3.3 / 3.5 | 16 / 25 / 21 | **41.3 / 59.8 / 198.6** | 60 / 94 / 1134 | 150.0 | 8250 单全部 SUCCEEDED，积压排空 |
| C 全链路，下游 200ms | 3.2 | 13.1 | **35.3** | 62.1 | 150.0 | 8250 单全部 SUCCEEDED |
| D 单端点，150 QPS | — | — | 83.4 | 130.7 | 150.0（受理） | **投递只消化 ~57/s**，60s 后积压 6930 |

DB 写入：**600 行/秒**（`InnoDB_rows_inserted + InnoDB_rows_updated` 差值）。
worker：C 场景均值 **26.4 / 200**（13.2%），峰值 81。

### 2.3 发现一：§7 说"每单 2 写"，实际是 4 写

600 行/秒 = 150 QPS × **4**。四次写是：

1. `notification` INSERT（受理）
2. `notification` UPDATE（认领：`attempt_count+1`、`PROCESSING`、写租约）
3. `delivery_attempt` INSERT（明细）
4. `notification` UPDATE（终态：SUCCEEDED / RETRY_WAIT / DEAD）

§7 的 350 行/秒 = 172 QPS × 2 写，只数了"插入通知 + 写结果"。修正后应为 172 × 4 ≈ **690 行/秒**，
按单机 MySQL 约 3000 行/秒的余量，"9 倍余量"应改为 **~4.3 倍**。

**偏差 1.7 倍，不到"重估"的 3 倍阈值，选型结论不变**（30 万 / 100 万 / 300 万日量仍落在同一档），
但设计文档 §7 的那两行数字必须改，否则后面每次讨论容量都要重新推一遍。

### 2.4 发现二：全链路 p99 的抬升来自 redo log 争用，不是代码路径

证据链（四条互相独立）：

1. **p50 全程不动**（3.2 → 3.2ms）。如果是受理代码变慢，中位数一定跟着抬；
2. **关掉投递 → p99 从 41~60 掉到 16.9ms**，只改了"有没有并发的投递写"这一个变量；
3. **GC 不是原因**：带 `-Xlog:gc` 跑一轮，最大暂停 **9.5ms**，与 p99 差一个数量级；
4. **600 次提交/秒 × 单次提交 ~3ms**（本机 Docker 卷的 fsync）→ 单块盘已经在排队。

所以 50ms 这条线只在"投递写与受理写不抢同一份 redo log"时成立。B 组三次里的 198ms 那次，
同一次运行的 max 是 1251ms，而 GC 最长 9.5ms——那是宿主机层面的停顿（Docker Desktop 的卷），
不是服务端代码，也不是 GC。

**这条要说清的是边界，不是找借口**：换成真实 NVMe（fsync ~0.3ms），同样的并发下 p99 会掉一个量级；
而在单机 Docker 卷上，150 QPS 受理 + 150 QPS 投递已经把这台机器的提交能力用到临界。

### 2.5 发现三：单端点就是吞吐天花板

D 组把 150 QPS 全压到一个端点：投递只消化 ~57/s，60s 后还剩 6930 条待投。

机制是 T2.5 的两个设定叠加：`max-concurrent-per-endpoint=16`（许可）+ "拿不到许可就退还、延迟 2s 再来"
（不排队）。于是每轮认领的 100 条里，只有 16 条能真正发出，其余 84 条立刻被退还，要等下一轮。
**吞吐上限 ≈ 许可数 × 轮询频率**，与下游多快无关——下游再快也超不过这条线。

这是"设计如此"还是"设计缺陷"，取决于假设：§7 的前提是 150 QPS 摊在 ~12 个活跃端点上
（每端点 ~12.5 QPS，16 个许可绰绰有余），此时 D 组不会发生；B/C 两组（12 端点）也确实跑满了 150/s。

但它必须被写下来，因为有两种情况会踩到：

- 某一家供应商的回调占了绝大部分流量（现实里很常见）；
- 单机部署、接入方少。

**旋钮**：`notify.circuit.max-concurrent-per-endpoint ≥ 目标 QPS × 下游平均延迟`。
150 QPS × 0.2s = 30，即该值要 ≥ 30 而不是 16。另一条路是把"满额退还"改成"短暂等许可"，
但那会占住 worker，正是 T2.5 花整轮避免的事——两者不能同时要。

### 2.6 worker 利用率与 Little's Law

C 组（下游 200ms）：实测均值 26.4，理论 150 × 0.2 = 30，偏差来自"每 2s 采一次样"漏掉了峰谷。
利用率 13.2%，峰值 81——峰值不是持续排队，而是"每轮一次认领 100 条"的批量特征。

按这个比例，"下游整体慢到 1s"时在途 ≈ 150，池子 200 留 25% 余量给抖动——与 §7 的取值一致，
**200 这个数在本机实测下是站得住的**。

### 2.7 若要稳定 <50ms（含投递满负荷），V1 的三件事

按性价比排序，都不是本版该做的：

1. **受理写入批量提交**：把 N 条 INSERT 合成一次 commit，提交次数降一个量级；
   代价是崩溃窗口从"单条"变成"一批"（当前 3ms → 5~10ms），与 at-least-once 语义兼容；
2. **采样器合并查询 + 降频**：现在 10s 一次 4 条 SQL（积压 / 在途 / 死信 / 最老逾期），
   合并成一条 `UNION ALL` 结果集，代价是多写 20 行 SQL；
3. **受理与投递拆连接池**：投递的提交变慢时不该挤占受理的连接。当前共用一个 30 连接的池。

## 3. T4.3 README 与 5 分钟 Demo

### 3.1 README 首屏回答三个问题

| 问题 | 答案（原文摘录） |
| --- | --- |
| 边界在哪 | 单机 MySQL 即队列，设计点 150 QPS（校验 200）；日量 1000 万必须上 MQ |
| 语义是什么 | **at-least-once**：不丢，但会重复；重复窗口 = 租约 TTL，重复是可解释的 |
| 哪些没做 | MQ / 分布式锁 / 幂等去重表 / 模板引擎 / 全链路追踪 / 批量重放 / 顺序保证，每条都写了翻案条件 |

### 3.2 `scripts/demo.sh`（约 90 秒）

一条通知从提交到"成功 / 失败 / 死信 / 重放"的完整一生，八幕：

1. 幂等：同键两次 → 同一单号，表里一行；
2. 正常投递 → SUCCEEDED，查单看到逐次明细；
3. 查询侧保护：`Authorization → ****`、`has_body=true` 但内容不回显、越权与不存在同一个 404；
4. 失败分级：500 按退避重试到预算耗尽进 DEAD；400 一次即 DEAD；
5. 死信列表（拉取式，不需要谁主动推）；
6. 人工重放：把 500 的下游换成 200 模拟"供应商恢复"→ 重放 → SUCCEEDED，明细序号连续；重复点击 409；
7. Prometheus 指标；
8. 死信日志（单一宣布者）。

只压三个与"等得起"有关的参数（退避基数 1s、预算 2 次、采样 2s），语义不动。
全程不需要手工改配置：清库、起 mock、起实例都在脚本里。

## 4. T4.4 AI 会话归档

`docs/ai-session.zip`：

- `AI-会话记录.md`：7 条"AI 建议 → 我的判断 → 最终决定"的完整链条，含被否决的建议与否决理由；
- `raw/`：本次开发的完整会话原文（JSONL），供核对上下文，不做删改。

挑选标准只有一条：**决策点上有分歧**。AI 一次就说对的（比如"用 AES-GCM"）没有归档价值；
有价值的是"AI 给了方案 A，我判断后改成 B，并写下为什么"。

## 5. 已知边界（交付时明确写出来，不留想象空间）

| 边界 | 现状 | 触发条件 / 下一步 |
| --- | --- | --- |
| 单端点吞吐 ≈ 许可数 × 轮询频率 | 实测 ~57/s（许可 16） | 单供应商占多数流量时调大 `max-concurrent-per-endpoint` |
| 全链路 p99 受 fsync 支配 | 41~60ms（本机 Docker 卷） | 真机 NVMe 或 §2.7 的三件事 |
| 跑集成测试需要 Docker | Testcontainers | 无 Docker 环境只能跑单测（`-Dtest='!*IntegrationTest'`） |
| 压测只覆盖"受理 + 单端点投递" | 未压 200 QPS、未压多实例 | 200 QPS 校验点、双实例争抢认领属于 V1 验收 |
| AI 会话原文含本机路径与口令占位 | 只上传仓库内 `docs/`，不推送原始 JSONL | 若要公开，先过一遍脱敏 |
