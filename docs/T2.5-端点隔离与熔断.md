# T2.5 端点隔离与熔断 —— 设计与实现说明

> 对应：任务拆解 T2.5 ｜ 设计文档 V2 §4.5（端点隔离 + 熔断）｜ 依赖：T1.2 认领、T2.1 失败分级、T2.3 死信

## 1. 本阶段边界

| 做 | 不做（明确不采纳或归后续） |
| --- | --- |
| per-endpoint 并发上限（信号量，默认 16） | ~~全局熔断（跨实例共享状态）~~ —— 需要 Redis，本阶段用"每个实例各自保护自己"，见 §2.9 |
| 熔断器：60s 滑动窗口、样本 ≥20 且失败率 >50% → OPEN 60s | 按 caller 维度隔离（一个 caller 的坏目标不该影响别人，但那是配额问题，不是故障隔离） |
| HALF_OPEN 半开探测（1 个探针，成功才恢复全量） | 熔断状态的运维查询端点（M3 的指标一起做） |
| **跳过不消耗尝试预算**：`attempt_count - 1` 退还 | 按端点自定义超时（超时预算是全局的，端点级超时属"接口不规范"那类需求） |
| 跟踪表上限（1 万端点），超出退化不隔离 | 熔断恢复的指数退避（每次固定 60s，够用且好解释） |

**一句话取舍**：这一阶段的价值几乎全在一条语义上——**"没发出去的请求不算尝试"**。其余的都是围绕它的实现细节。

## 2. 设计思路：八个决策点

### 2.1 跳过只能发生在认领之后，不能靠 SQL 过滤

最直觉的做法是在认领 SQL 里加一句 `AND target_url NOT IN (...)`，把熔断中的端点排除掉。做不到，两个原因：

1. **熔断状态在进程内存**，数据库不知道（每个实例独立判断，见 §2.9），SQL 里没有可用的谓词；
2. 即使把状态写进库，`target_url` 是完整 URL，同端点不同路径（`/a`、`/b/c`）要归并成同一个键，字符串匹配做不到——那是"用 LIKE 猜 URL 结构"，遇到大小写、端口、userinfo 立刻错。

所以流程是：**照常认领 → 提交线程池前先看一眼熔断状态 → 命中的整批退还**。多了一次写，换来的是判定准确。

`pollOnce` 里用 `gate.isOpen()` 做前置过滤还有一层考虑：**纯读、不消耗配额**。真正的准入（半开探针、并发上限）在 worker 里由 `tryEnter()` 完成，两者职责分开，前置过滤才不会"顺手把一个探针名额吃掉"。

### 2.2 跳过 = 退还预算，这是全系统唯一动 `attempt_count` 的地方

`attempt_count` 在**认领时**自增（T1.2 的既定选择，理由是"worker 崩溃后没人执行完成后自增"）。于是"不消耗尝试预算"只能有一个实现：

```sql
UPDATE notification
SET attempt_count = attempt_count - 1,   -- 认领时加过，这里退回来
    status = 'RETRY_WAIT',
    next_attempt_at = DATE_ADD(NOW(3), INTERVAL ? SECOND),
    lease_owner = NULL, lease_until = NULL
WHERE lease_owner = ? AND status = 'PROCESSING' AND attempt_count > 0
  AND id IN (...)
```

反面方案是"认领不自增、落库时自增"，这样跳过天然不消耗预算。**但不能改**：一旦落库才自增，进程在投递中崩溃就没人自增，那些"必崩"的任务永远到不了 `max_attempts`，会无限重投（T2.2 §2.4 已论证过）。所以宁可接受"自增再退还"这个绕一点的实现。

`attempt_count > 0` 是防御性条件：正常路径下认领刚加过，一定 ≥1，但不允许出现负数——`attempt_count` 是预算的唯一真相，负数会让 `attemptNo < maxAttempts` 的判断永久为真。

### 2.3 跳过绝不能写 `delivery_attempt`

这条比上一条更容易踩，后果也更隐蔽。

假设跳过也写明细：认领把 `attempt_count` 加到 N，跳过时写一条 `attempt_no = N` 的明细，然后退还让 `attempt_count` 回到 N-1。下一轮它正常认领又拿到 N，再写一条 `attempt_no = N` → 撞 `uk_n_attempt (notification_id, attempt_no)` → `insertAttempt` 抛异常 → 后面的 `markFailed` 不执行 → 行停在 `PROCESSING`，直到 60s 后租约过期。**症状是"这条任务莫名卡住一分钟，日志里只有一条落库失败"**，很难联想到这里。

所以跳过路径**一行明细都不写**，理由也站得住：这次 HTTP 一个字节都没发出去，写进去就不是事实。集成测试 `被跳过的任务恢复后仍能成功_明细不出现号码空洞` 直接钉住这点：被跳过之后恢复正常，明细必须是连续的 1..N。

### 2.4 端点的粒度是 `scheme://host:port`，不是裸 hostname

设计文档写"按 host 维度"。实现时把粒度定成 authority：

| 粒度 | 问题 |
| --- | --- |
| 裸 hostname | 同一台机器上 8080 和 9090 是两个完全不同的下游，健康度被混在一起算；本地/容器环境里尤其常见 |
| 全 URL | 同一端点的 `/a` 和 `/b` 各自熔断，20 个路径就要各攒 20 个样本，等于没有熔断 |
| **`scheme://host:port`** | 与实际"连接目标"一致，harness 里两个端口天然是两个端点，可测 |

小写归一化（`CRM.Example.com` 与 `crm.example.com` 是同一个端点），缺省端口补齐（`https://x` → `https://x:443`），否则 `https://x/` 与 `https://x:443/` 会被当成两个。

### 2.5 熔断状态机必须有 HALF_OPEN

设计文档只写了"OPEN 60s"，没说之后怎么办。如果 OPEN 到期就全部放行，60s 那一瞬间几十上百个任务会一起打过去——供应商往往还没恢复，于是又攒一批失败、再熔断 60s。熔断退化成"每 60s 打一轮"的定时炸弹，反而比不熔断更糟（不熔断至少退避是有抖动的、越等越久）。

所以补了半开：

```
CLOSED ──(窗口内样本≥20 且失败率>50%)──> OPEN
  ^                                      │ 等 60s
  └────────(探测成功，清窗口)──── HALF_OPEN <┘
                                 │ 探测失败
                                 └──> OPEN（重新计 60s）
```

- **半开只放 1 个探针**（`half-open-probes`），其余继续拒绝。探针成功才恢复全量，失败就重新计时；
- 探针名额用独立的信号量，且**每次进入 HALF_OPEN 重建**：这样"上一次半开遗留的在途请求"释放的是旧对象，不会把新窗口的名额放大。

`isOpen()` 故意只回答"确定 OPEN"，半开返回 `false`——这个方法是给 `pollOnce` 做前置过滤的，如果它在半开时也返回 true，那么半开期间所有任务都会被跳过，探针永远发不出去，熔断就再也恢复不了了。

### 2.6 什么算"失败"：只算 RETRYABLE

失败率的分母和分子都只统计**与端点健康度相关**的结果：

| 结果 | 计入 | 理由 |
| --- | --- | --- |
| 2xx 成功 | 成功 | — |
| 网络层失败、408/429/5xx | 失败 | 对方的问题，可能自愈 |
| 4xx / 3xx（PERMANENT） | **不计** | 是我们请求的问题（凭证过期、路径写错）。计入的话，一个配错凭证的 caller 就能把共用该端点的所有 caller 一起熔断——**把别人的配置错误变成所有人的故障** |
| SSRF 拒绝 | **不计** | 我们自己的策略拒绝，请求根本没发出去 |

这个判断写在 `Dispatcher` 里（`decision.type() != PERMANENT` 才 `record`），而不是在闸门内部——因为"这次失败意味着什么"是分类器的知识，闸门只该回答"这个端点现在还健康吗"。

顺带一个副作用是好的：凭证过期这类故障会走 PERMANENT → 一次即 DEAD，本来就不该占预算，也不该把端点标成"不健康"。

### 2.7 并发上限和熔断是两个东西，都要有

| | 并发上限（信号量） | 熔断器 |
| --- | --- | --- |
| 生效时机 | **故障早期**，不需要先判断"是否故障" | 故障被确认后（20 个样本） |
| 解决的问题 | 一个慢端点占满 worker，别人排队（故障扩散） | 明知会失败还一遍遍重试（浪费预算、放大告警） |
| 失效方式 | 拿不到许可 → 退还，2s 后再来 | OPEN → 退还，30s 后再来 |

只有熔断的话，前 20 个样本仍然会占满 worker（样本要攒，攒的过程就是打满的过程）；只有并发上限的话，一个挂掉的端点会一直以 16 并发持续被打，每个任务照常烧预算。

拿不到许可时**不阻塞等待**，而是退还：worker 在信号量上排队等于"认领了却不干活"，而 batch 是按空闲 worker 算的，堵住一个就少投一条，没有任何收益。

### 2.8 跳过延迟 30s 不是随手取的

三个候选值，只有一个是安全的：

| 延迟 | 后果 |
| --- | --- |
| 0 | 下一轮 poll（500ms 后）立刻重新认领同一批 → "认领-退还"热循环，纯写放大；更糟的是这些行会一直占据认领名额 |
| **30s**（本版） | 与 OPEN 窗口（60s）同量级：熔断期间每条任务最多被碰两次，恢复后自然继续 |
| 5min | 恢复后要等很久才补投，违背"补偿窗口内送达"的承诺 |

**热循环不只是写放大的问题，还会饿死其他端点**——这一点是在集成测试里撞出来的：测试里把所有 `RETRY_WAIT` 的行都快进到"已到期"，熔断中的行每轮都抢走全部认领名额，健康端点的任务一条都认领不到。生产里靠 30s 延迟把它们自然排到队尾，这也反过来证明了延迟不能为 0。

延迟带 ±20% 抖动（`skipDelaySeconds()`），否则端点恢复瞬间所有被跳过的任务同秒涌回。

### 2.9 内存有界，多实例各自判断

端点键来自用户提交的 URL，不做限制就是一条内存耗尽路径（10 万个不同域名 = 10 万个状态对象）。所以有 `max-tracked-endpoints`（默认 1 万）：**达到上限后，新端点放行但不建记录**——退化为"不隔离"，而不是拒绝服务。

多实例：状态只在进程内存，各实例独立判断。代价是"要 N 个实例各攒 20 个样本才全体熔断"，即总共 20N 次失败请求；换来的收益是不引入 Redis、不引入全局一致性。局部熔断已能保护自身（不被打满、不烧预算），全局熔断留到"多实例下确实观察到不一致"再说。

## 3. 处理流程

```
pollOnce()
  ├─ claim(roundToken, batch)                     ← 短事务，attempt_count +1
  ├─ for each claimed:
  │    if gate.isOpen(endpoint)  → 收集进 deferred
  │    else                      → 提交线程池
  └─ releaseSkipped(deferred, 30s)                ← 一条 UPDATE 退还整批（attempt_count -1）

worker: deliverOne()
  ├─ permit = gate.tryEnter(endpoint)             ← 熔断判定 + 并发配额
  │    null → skip(2s)                            ← 退还，不写明细，不烧预算
  ├─ try (permit):
  │    ├─ SsrfGuard.checkForDelivery()            ← T2.4，被拒则请求不发
  │    ├─ decode → deliver → classify
  │    ├─ gate.record(endpoint, 是否可重试失败)     ← SUCCESS/RETRYABLE 才计数
  │    └─ insertAttempt → markSucceeded/markFailed/markDead（带 lease_owner 守卫）
  └─ finally permit.close()                       ← 归还并发配额
```

### 5.2 现场演示（`scripts/circuit_breaker_demo.sh`，实测输出）

配置：worker 池 8、单端点并发 4、熔断阈值 20 样本 / 50%。40 条任务打恒 500 的端点，20 条打恒 200 的端点。

```
== 2. 观察故障端点收到的请求数（应在 20 来个样本后停止增长）
  t=1s  故障端点累计收到 13 次请求
  t=2s  故障端点累计收到 21 次请求
  t=3s  故障端点累计收到 21 次请求
  → 请求停止增长（熔断已打开）

== 3. 故障端点：任务状态分布（关键：没有 DEAD）
status      cnt  min_attempt  max_attempt
RETRY_WAIT   40            0            1

== 4. 故障端点：真正的请求只发生了这么多次
requests_sent  attempts_kept  budget_if_no_breaker
           21             21                   400

== 5. 健康端点：全部成功，一次都没被拖累
status      cnt  max_attempt
SUCCEEDED    20            1

== 6. 日志里的熔断信号
WARN EndpointGate : 端点熔断打开 60000ms：20 个样本中失败 20 个（阈值 50%）；
                    期间该端点的任务只推迟、不消耗尝试预算
```

三个数字合起来才是完整的证据：

- **21 次请求 / attempt_sum 21**：第 20 个样本让熔断打开，第 21 次是当时已在途的那个。此后再没有请求发出；
- **40 条全是 `RETRY_WAIT`，`max_attempt 1`**：没有一条被烧到 DEAD。若没有熔断，这 40 条会一路重试到 `max_attempts=10`，即最多 400 次请求 + 大批 DEAD；
- **健康端点 20 条全 SUCCEEDED**：同一个 worker 池，没被拖累。

> 写脚本时踩过一次采样坑：熔断打开瞬间仍有在途投递，"mock 已收到 20 次、库里只有 8 条明细"这种中间态会让人误判成 bug。脚本里加了 2s 静默等待再取快照。**读在途状态得出的结论不可信，这条对排查生产问题同样成立。**

## 6. 已知限制（三条要紧的，先说）

### 6.1 熔断是"全端点"的，不区分 caller

端点键里没有 caller。A 公司把回调地址填成 `https://vendor.example.com/a`，B 公司填 `/b`，两者共享同一个熔断器：A 的凭证过期导致大量 401（PERMANENT，不计入失败）不会影响 B——这条恰好被 §2.6 挡住了；但若 A 的请求体让对端 500，B 会被一起熔断。

按 caller 隔离需要把键变成 `(caller, endpoint)`，状态数 × 调用方数量。当前规模（十几个 caller）不值得，接入外部不可信 caller 时再改。

### 6.2 多实例下熔断不同步

见 §2.9。实际后果：实例数 N 时，供应商故障期间总共有约 20N 次失败请求才全体熔断。这个量级可以接受（20 次失败 ≈ 几百毫秒的正常流量），但要说清楚"不是一致性的熔断"。

### 6.3 熔断恢复靠半开，不靠"探测旁路"

半开只放 1 个探针，这个探针是从**真实任务**里来的（第一条被放行的投递）。如果那一刻恰好没有任务（低峰期），熔断会一直停在 OPEN，直到有任务来触发半开。这不算 bug——没有任务就不需要恢复——但意味着"熔断状态可能在无事可做时停留很久"，M3 做指标时不要用 `state == OPEN` 的持续时间当告警。

## 7. 其余限制

| 限制 | 后果 | 触发条件 / 何时补 |
| --- | --- | --- |
| 跟踪表满后新端点不隔离 | 超 1 万端点的极端场景下退化 | 真实出现 >1 万独立回调域名时，换成带 TTL 的 LRU |
| 熔断窗口用固定分桶（6×10s），不是精确滑动 | 边界处可能多算或少算不到一个桶 | 无实际影响，误差 ≤ 1 个桶的样本 |
| 并发峰值受 `batch ≤ 空闲 worker` 影响 | 空闲 worker 少于并发上限时，端点用不满配额 | 属于"池子太小"，不是隔离问题 |
| HALF_OPEN 期间只有一个探针，恢复较慢 | 供应商恢复后，第一条成功才放量，最坏多等一个轮询周期 | 可调 `half-open-probes`，但调大就削弱了防惊群 |
| 熔断状态没有持久化 | 实例重启后熔断状态清零，故障中的端点会重新攒 20 个样本 | 重启频率远低于故障周期，可接受；要持久化就得引入共享存储 |
