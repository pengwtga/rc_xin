# T2.2 租约与崩溃恢复 —— 设计与实现说明

> 对应：任务拆解 T2.2 ｜ 设计文档 V2 §4.3（认领与租约）/ §4.2（状态机）｜ 依赖：T1.2、T2.1 已完成

## 1. 本阶段边界

| 做 | 不做（归后续阶段或明确不采纳） |
| --- | --- |
| 验证"租约到期即回收"的四个边界：未到期不可抢 / 到期可接手 / 过期结果不许覆盖 / 预算不被无限重投 | ~~清理定时任务把 PROCESSING 改回 PENDING~~ —— **不采纳**，见 §2.1 |
| 把"崩溃发生过"变成可观测信号（`staleResults` 计数 + 日志） | ~~租约续约 / watchdog 心跳~~ —— **不采纳**，见 §2.2 |
| 优雅停机：停机时等在途投递结束，再退出 | 指标上报（M3，届时直接读 `staleResults`） |
| 进程级 `kill -9` 演示脚本（`scripts/crash_recovery_demo.sh`） | 死信告警（T2.3）、重放（T3.2）、多机部署编排 |

**本阶段认领 SQL 与守卫 SQL 一行未改。** 崩溃恢复的机制在 T1.2 就已经写完了——T1.2 的已知限制第 4 条写着"多实例并发正确性由 SKIP LOCKED + 轮次 token 保证，属于 T2.2 演练验证范围"。T2.2 的工作就是把这个"验证范围"变成可重复执行的证据，并补两个真实缺口（可观测、停机）。

## 2. 设计思路：六个决策点

### 2.1 崩溃恢复不是一个功能，是认领条件的一个分支

整个机制的代码量是 `WHERE` 里的一个 `OR`：

```sql
WHERE (status IN ('PENDING','RETRY_WAIT') AND next_attempt_at <= NOW(3))
   OR (status = 'PROCESSING' AND lease_until < NOW(3))   -- 崩溃回收
```

**为什么不做"清理任务"**（定时扫描过期行、改回 `PENDING`、写一条"已回收"记录）：

1. **多一个写者就多一套协调问题。** 清理任务自己也会崩，多实例下还要选主或抢锁，否则三个实例同时清扫同一批行——为消灭一个恢复问题，造出三个新的。
2. **判定者 ≠ 持有者，会引入新的双投窗口。** 清理者只能凭 `lease_until` 判断 worker 已死，而 worker 可能只是慢。一旦清理者把行改回 `PENDING` 而 worker 还活着，别人立刻认领 → 双投。**租约本来就是给认领者用的判定依据，把判定搬到第三方手里，判定与写入就不再是同一个原子动作。**
3. **恢复延迟变成两段。** 清理周期（比如 30s）+ 认领周期（0.5s）；读时判定只有一段，且上界可算：租约剩余时长。

代价要认：**在到期被认领之前，这行在查询接口里一直显示 `PROCESSING`**。所以 T3.1 的查询语义必须写清"status 是最近一次认领后的状态，不等于任务正在被处理"。这个代价是可解释的，而清理任务带来的不一致窗口不可解释。

### 2.2 没有心跳续约：用"执行时间有上界"换掉一整套机制

标准做法是 worker 定期 `UPDATE lease_until = NOW() + 60s` 续约（watchdog）。**我们不做**，理由是全链路里只有一个动作在耗时，而它有硬上界：

| 环节 | 耗时上界 | 依据 |
| --- | --- | --- |
| 认领（UPDATE + 回读） | 毫秒级 | 短事务，无 HTTP |
| 投递（一次 HTTP） | **15s** | `http.total-timeout-ms`，JDK HttpClient 强制 |
| 落库（2 条 UPDATE/INSERT） | 毫秒级 | — |
| 租约 | **60s** | 4× 投递上界 |

只要 `lease > timeout + 余量`，就永远不会出现"我还活着但租约已过期"。这条约束由 `StartupGuard` 在启动期断言（配成 10s 直接拒绝启动），不是口头约定。

**续约自身的问题**（不是为了省代码才这么说）：

- 续约线程/定时器自己会死，死了以后任务静默卡到租约过期——**检测"续约没来"又需要租约**，机制递归；
- 续约与落库之间存在竞态：续约成功、落库前崩溃，等于让一个死进程"又多活 60s"；
- 200 worker × 每 20s 续约 ≈ 10 QPS 的纯写放大，且这些写会与认领抢同一批行锁。

**这个取舍的代价写清楚**：如果某次 GC 停顿超过 45s（60 − 15），别人会判定我死并接手，产生一次双投。这个量级的 STW 本身已是事故级事件（远超 G1/ZGC 的正常停顿），用它换掉一整套续约机制是划算的；反过来说，**如果投递不是"一次有超时的 HTTP"而是"可能跑几分钟的批处理"，这个设计立刻失效，必须上心跳**。

### 2.3 守卫键必须是"这一次认领"，而不是"这台机器"

`lease_owner` 存的是 `实例ID/轮次token`（如 `04e8fc85879b/99b571df`），不是纯 `instanceId`。为什么多这 9 个字符：

- **同一实例可以有多轮认领同时在途。** 调度每 500ms 一轮，一轮里最慢的任务要跑 15s，所以第 1 轮的结果返回时，第 2、3 轮早已开始。如果守卫用 `instanceId`：
  - 第 1 轮的行在极端情况下（GC 停顿导致过期、被本实例第 3 轮重新认领）会带着"同一个 instanceId"回来，**守卫通过，用一份 30 秒前的结果覆盖最新一次认领的状态**；
  - 更糟的是这种覆盖是静默的——日志上看起来"落库成功"。
- **一个键两用。** 认领后回读用它定位本轮的行（`WHERE lease_owner = ?`），落库用它做守卫（`WHERE id = ? AND lease_owner = ? AND status='PROCESSING'`）。同一个 token 保证"回读到的行"和"能改的行"是同一批。
- 长度：12（实例）+ 1（斜杠）+ 8（轮次）≤ `VARCHAR(64)`，留足余量。

守卫失败 = `UPDATE` 影响 0 行 = 这份结果已经过期。处理方式是**丢弃 + 计数**，绝不重试、绝不"顺手改回来"——因为此刻行可能已经被别人改成 `SUCCEEDED` 了，把一份失败结果盖上去就是把已送到的通知打回重投。

### 2.4 崩溃必须消耗一次尝试预算（否则会无限重投）

`attempt_count` 在**认领时**自增（T1.2 已定），崩溃自然也算一次。反面方案是"落库成功时再自增"：

| 方案 | 崩溃后的行为 | 后果 |
| --- | --- | --- |
| 落库时自增（不采纳） | 这次尝试不留痕，预算不变 | 一个必崩的任务（如启动即 OOM）会被无限重投，永远进不了 `DEAD` |
| **认领时自增（当前）** | 预算 −1 | 崩溃最多吃掉 9 档（`max_attempts=10`），之后进 `DEAD` 等人工重放 |

代价是明确的：**一次崩溃 = 少一次重试机会**。但"少一次机会"是可解释的，"永不停止重投"不是。

另一个被否掉的做法是"崩溃不计预算，单独记崩溃次数、单独给预算"：两套计数 = 两套状态机 + 两条告警规则，为一个低频事件把 `DEAD` 的判定条件复杂化。**一个计数器能说清的事，不要用两个。**

### 2.5 语义上限是 at-least-once：窗口在哪，为什么消不掉

"请求已发出、结果未落库"之间的每一个时刻崩溃，都会导致接手者重发一次：

```
解析 DNS 后 ─ TCP 建连后 ─ 请求字节发出后 ─ 对端处理中 ─ 响应返回途中 ─ 落库事务提交前
                                      ↑ 这 6 个位置里，前 4 个已经"对方收到了"
```

要消掉这个窗口只有两条路：与下游共享事务（跨组织不可能），或下游按幂等键去重（要求每个供应商都实现，需求里没有）。**所以系统只能保证"不丢"，"不重"必须下推给下游的幂等能力——这是 at-least-once 这个语义选择的真实含义，不是实现缺陷。**

系统能做的是**留下可追溯的证据**：崩溃的那次尝试没有 `delivery_attempt` 记录（明细写在投递返回之后），所以事后看到"`attempt_count=2` 但明细只有 `attempt_no=2` 一行"，就能判定中间发生过一次可能已送达的投递。§6.1 的第 2 个用例直接断言了这个缺口。

### 2.6 能优雅停机，就不要走崩溃路径（本阶段唯一的运行时改动）

原来的 `@PreDestroy` 直接 `shutdownNow()`：中断在途 HTTP → 结果不落库 → 行停在 `PROCESSING` → 60s 后被别的实例重投。**每次滚动发布都制造一批双投**，而发布是日常操作。

改成：

```java
workers.shutdown();                                    // 不再收新任务，在途继续跑
awaitTermination(totalTimeoutMs + 1000, MILLISECONDS); // 最多等 16s
if (还没结束) shutdownNow();                            // 卡在 DB/连接池的，等也不会好
```

等待上限不是拍的：单次投递有 15s 硬超时，超过 16s 仍未结束只可能卡在 DB；而 16s < 租约 60s，**等待期内租约仍属于本实例**，不会出现"我还在跑、别人已接手"。同时 16s < Spring 默认的 30s 优雅期，不会被容器强杀。

> 崩溃是意外，停机是日常。日常不该付意外的代价。

## 3. 崩溃恢复时序（实测数据，来自 §6.2）

```
t=0.0   A 认领 #58：status=PROCESSING, attempt_count 0→1, lease_owner=A/2bd125c0, lease_until=t+60
t=1.5   下游收到请求 #1（mock sleep 8s），A 阻塞等响应
t=2.0   kill -9 A。行留在 PROCESSING，租约剩余 58s，delivery_attempt 0 行
t=60.0  租约到期（没有任何进程做任何事）
t=60.3  B 的 poll 认领 #58：attempt_count 1→2，lease_owner 改为 B/xxxx
t=60.4  B 投递成功 200 → SUCCEEDED，lease_owner/lease_until 置 NULL
        delivery_attempt 只有一行：attempt_no=2, status_code=200, duration_ms=35
```

几步里只有两处真正关键：

1. **t=60 那一刻没有任何代码执行**——到期是"读的时候比较出来的"，不是"事件触发的"；
2. **t=60.3 的认领带了一个新 token**，所以 A 若在 t=61 复活并落库，`WHERE lease_owner='A/99b571df'` 影响 0 行（§2.3）。

## 4. 处理流程与"崩溃点"标注

```
pollOnce()
  ├─ idle = pool - active ; batch = min(batchMax, idle)
  ├─ claim(token)          ← 崩溃点①：认领已提交，任务从此归 A，无人知晓 A 已死
  ├─ workers.submit(...)   ← 崩溃点②：任务在队列里，行是 PROCESSING
  ├─ decode(headers, body) ← 崩溃点③：还没发出，下游无感知（重投是"补发"，不重复）
  ├─ deliver(target)       ← 崩溃点④：**请求可能已到达下游**，这是 at-least-once 的来源
  ├─ insertAttempt(...)    ← 崩溃点⑤：明细已写，状态没写（行仍 PROCESSING）
  └─ markXxx(token 守卫)   ← 崩溃点⑥：状态已写、租约未清 → 下一轮不会重领（status 已非 PROCESSING）
```

①~⑥ 全部由同一套机制兜住：**行仍是 `PROCESSING` 且租约终将到期**。区别只在"下游是否可能已经收到"——只有 ④⑤ 会产生重复投递。

## 5. 代码改动

| 文件 | 改动 | 为什么 |
| --- | --- | --- |
| `Dispatcher` | 新增 `staleResults` 累计计数，守卫失败时写进 WARN 日志；提供 `staleResults()` | 守卫失败是"租约曾被接管"的唯一直接信号；此前只有一行无上下文的 WARN，无法判断是噪声还是趋势 |
| `Dispatcher#shutdown` | `shutdownNow()` → `shutdown()` + `awaitTermination(total + 1s)` + 兜底 `shutdownNow()` | §2.6，把滚动发布从崩溃路径上摘出来 |
| `Dispatcher#pollOnce` | 开头加 `if (workers.isShutdown()) return 0;` | 停机与调度线程的时序不保证：若此时仍认领，行提交不进线程池，只能等租约过期才被回收——认领了却没人跑，是最不该出现的状态 |
| `LeaseRecoveryIntegrationTest`（新增） | 4 个场景 | §6.1 |
| `scripts/crash_recovery_demo.sh`（新增） | 起两个实例 + 真 `kill -9` + 真实下游 | 任务拆解的验收项要求"投递中途 kill -9"，单测无法覆盖进程级行为 |

## 6. 验证方案与结果

### 6.1 集成测试（真实 MySQL，4 个场景）

| # | 场景 | 断言 | 结果 |
| --- | --- | --- | --- |
| 1 | 租约未到期，第二个实例来认领 | 认领结果为空；`attempt_count` 仍为 1；`lease_owner` 仍是 A | PASS |
| 2 | 认领后崩溃（不落库）→ 租约到期 → 另一实例接手 | `attempt_count` 1→2；状态 `SUCCEEDED`；`lease_owner/lease_until` 清空；下游只收到 1 次；**明细只有 `attempt_no=2` 一行**（崩溃那次无明细） | PASS |
| 3 | 旧实例复活，带着过期结果回来 | B 已成功后，A 的 `markSucceeded` / `markFailed` 都返回 false；状态仍 `SUCCEEDED`；终态行不再被任何实例认领 | PASS |
| 4 | 崩溃消耗预算 | `max_attempts=2`：崩溃吃掉第 1 档，接手者第 2 次失败即 `DEAD`，之后多轮 poll 都不再动它 | PASS |

用例 3 和 T1.2 的"守卫失败不覆盖状态"不是重复：T1.2 验证的是"`lease_owner` 被改后，旧 token 改不动"（状态是 `PROCESSING`）；这里验证的是更坏的场景——**对方已经把任务做成功了，我的失败结果不许把它打回重投**。

不真等 60s：测试用 SQL 把 `lease_until` 拨到过去。租约是否到期只由"DB 时钟比较"决定，与进程经历了多少真实时间无关，所以快进时钟与真等 60s 等价。

### 6.2 进程级 kill -9 演示（`scripts/crash_recovery_demo.sh`，实测输出）

```
== 3. 提交通知并等待 A 认领
{"notification_no":58,"status":"PENDING"}
任务 id=58 状态=PROCESSING
下游已收到第 1 次请求（A 正在等响应，结果尚未落库）

== 4. kill -9 实例 A（模拟进程崩溃）
  row: status=PROCESSING attempt_count=1 lease_owner=5b30e1b17f8f/2bd125c0 租约剩余秒=58

== 6. 启动实例 B :18081（同一张表，不同 instanceId）
B 已就绪，等待租约到期（最多 60s，这是崩溃恢复的固有延迟）…

== 7. 恢复完成

== 8. 结果核对
— notification：
  status=SUCCEEDED attempt_count=2 max_attempts=10 last_status_code=200 lease_owner=NULL
— delivery_attempt（只应有接手者写的一行，attempt_no=2）：
  attempt_no=2 status_code=200 duration_ms=35
— 下游收到请求次数：2
  其中崩溃前 1 次由 A 发出（响应随进程一起消失），接手后由 B 重发——这就是 at-least-once 的语义代价
— 守卫信号（B 的日志里不应出现「被守卫丢弃」）：
  staleResults=0
```

## 7. 已知限制（显式记录，不留暗坑）

1. **恢复延迟上界 = 租约剩余时长（≤60s）+ 一个 poll 周期（0.5s）**。崩溃时这一条通知的送达时间远超 SLA p99<5s；只影响被崩溃波及的这批任务，不影响新任务（它们被正常认领）。要更快只能缩短租约，代价是 GC 停顿更容易被误判 → 双投；
2. **GC 停顿 > 45s 会被误判为死亡**（§2.2 的取舍）。生产上应把 `-XX:+UseG1GC -XX:MaxGCPauseMillis` 一类的停顿目标与租约长度一起看；
3. **认领 SQL 的 `OR` 分支在大表上可能退化为 index merge / 回表**：`status IN ('PENDING','RETRY_WAIT')` 走 `idx_due`，`status='PROCESSING'` 走 `idx_lease`，MySQL 8 多数情况下能合并，但数据量到千万级、且 `PENDING` 占绝大多数时应重测执行计划，必要时拆成两条 SQL（先回收、再取到期）；
4. **轮次 token 的 8 位十六进制（32 bit）** 在同一实例内存在理论碰撞概率；碰撞只会让"回读"多捞到同实例上一轮的残留行，而落库守卫仍是等值匹配——后果是多投一次而非错投，概率量级 1/2^32 每轮，当前接受；
5. **`staleResults` 只是进程内计数**，重启归零；跨实例的"回收次数"目前只能从 `delivery_attempt` 的 `attempt_no` 缺口反推，等 M3 接指标后按实例维度上报。
