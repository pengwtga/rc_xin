# T1.2 投递引擎 —— 设计与实现说明

> 对应任务拆解 T1.2（M1）：投递引擎 = 认领 + HTTP 调用 + 状态落库。
> 设计依据：设计文档 V2 §4.2（at-least-once）、§4.3（SKIP LOCKED + 租约）。

## 1. 本阶段边界

| 做 | 不做（后续阶段） |
| --- | --- |
| 完整认领 SQL（含租约过期回收分支，§4.3 原文） | 失败分级 ErrorClassifier（T2.1，本阶段失败只有"最小退避"） |
| HTTP 投递（JDK HttpClient，connect 3s / total 15s，禁重定向） | 429 Retry-After、全抖动（T2.1） |
| 结果落库带 `lease_owner` 守卫（§4.3 约束 5） | kill -9 崩溃恢复演练（T2.2，但认领 SQL 已天然支持） |
| `delivery_attempt` 逐次明细落库 | 熔断 / 端点隔离（T2.5） |
| batch 动态钳制到空闲 worker 数 | 指标（M3） |

## 2. 设计思路：七个决策点

### 2.1 认领和投递必须是两个事务，HTTP 绝不进认领事务

认领事务持有 `FOR UPDATE SKIP LOCKED` 的行锁直到提交。如果把 HTTP 调用放进去，一条 15s 超时的请求会让这批行锁挂 15s——其他实例 SKIP 跳过没问题，但**本实例的连接池**会被在途投递耗干（Hikari 30 个连接，200 个 worker 一人占一个就是事故）。所以顺序固定为：**短事务认领 → 提交 → 线程池投递 → 短事务落库**。

### 2.2 `lease_owner` = 实例 ID + 轮次 token（本阶段最关键的一个细节）

结果落库和认领后回读都以 `lease_owner` 定位自己这批行。如果 lease_owner 只是实例 ID，会有一个隐蔽的同实例双投：

```
轮次 1：认领 100 条 → 丢进线程池异步投递（行仍是 PROCESSING / owner=A）
轮次 2（500ms 后）：SELECT WHERE owner=A → 把轮次 1 还在途的行又取回来 → 再投一次
```

token 每轮随机生成（`<实例12位>/<轮次8位>`），SELECT `WHERE lease_owner = :token` 天然只命中本轮认领的行。这个 token 同时就是 §4.3 约束 5 的守卫键——一物两用，不需要额外的内存态。

### 2.3 `attempt_count` 在认领时自增，不在完成后

沿用设计文档 §4.2 的既定决策，落到实现上有个连带好处：`delivery_attempt.attempt_no` 取认领后的 `attempt_count`，与全局递增语义一致，`uk_n_attempt` 唯一键天然不会撞（旧版 replay_epoch 要解决的问题在这里不存在）。

### 2.4 batch = min(batchSizeMax, 空闲 worker 数)——约束 4 的运行时版

启动自检只保证 `batchSizeMax ≤ poolSize`（静态关系），运行时还要保证 `认领数 ≤ 空闲 worker`：`idle = poolSize - activeCount`，认领前查询。否则上一轮 15s 慢请求占满线程池、本轮又认领 100 条，多出来的只能等租约过期被重领——自己制造重复投递。

### 2.5 结果落库带守卫；attempt 明细无条件落库

两件事刻意分开：

- **notification 状态更新**带 `WHERE lease_owner = :token AND status = 'PROCESSING'` 守卫：投递耗时超过租约（GC 停顿、机器假死）时，旧 worker 的结果已过期，守卫失败（影响 0 行）就丢弃并告警日志，绝不覆盖新 worker 的状态；
- **delivery_attempt 插入不带守卫**：这次 HTTP 是**真实发生过的**，无论状态有没有被覆盖，明细必须留痕（追责与排查的依据）。守卫丢弃的 attempt 行反而是"下游可能收到两次"的直接证据。

### 2.6 失败处理只做"最小退避"，分类留给 T2.1

本阶段任何失败（HTTP 4xx/5xx、超时、连接拒绝）统一：`RETRY_WAIT` + `next_attempt_at = NOW + min(cap, base×2^(n-1))`；`attempt_count ≥ max_attempts` 时转 `DEAD`。没有 ErrorClassifier、没有全抖动、没有 Retry-After——**但 400 不重试这个最重要的判断在 T2.1 落地，本阶段的兜底保证是"失败的任务不会丢也不会卡死"**。把分级留到 T2.1 是刻意的：一次只引入一个机制，每个机制都有独立可验收的增量。

### 2.7 禁重定向从第一行代码就开

`HttpClient.newBuilder().followRedirects(NEVER)`。这不只是 T2.4 SSRF 的事：302 跟随会把带凭证的请求转发到 Location 指向的任意主机，HttpClient 默认（NORMAL）恰好就是跟随——安全默认值的偏差必须在投递器出生那天钉死，一行配置换一个故障类别消失。

## 3. 认领与守卫 SQL

### 3.1 认领（§4.3 原文，参数化）

```sql
UPDATE notification
SET status        = 'PROCESSING',
    lease_owner   = :token,
    lease_until   = DATE_ADD(NOW(3), INTERVAL :leaseTtl SECOND),
    attempt_count = attempt_count + 1
WHERE id IN (
  SELECT id FROM (
    SELECT id FROM notification
    WHERE (status IN ('PENDING','RETRY_WAIT') AND next_attempt_at <= NOW(3))
       OR (status = 'PROCESSING' AND lease_until < NOW(3))   -- 崩溃回收就在这一行
    ORDER BY next_attempt_at
    LIMIT :batch
    FOR UPDATE SKIP LOCKED
  ) t
);
-- 同一事务内回读本轮行
SELECT id, caller_id, target_url, http_method, headers_enc, body_enc, attempt_count
FROM notification WHERE lease_owner = :token AND status = 'PROCESSING';
```

第二个 `OR` 分支不是特殊恢复路径：租约过期的任务和到期任务一样可认领。T2.2 的"kill -9 恢复"验收不需要新代码，只需要演练。

### 3.2 结果落库（成功 / 失败两个入口，同一守卫）

```sql
-- 成功
UPDATE notification
SET status='SUCCEEDED', last_status_code=:code, last_error_class=NULL,
    lease_owner=NULL, lease_until=NULL
WHERE id=:id AND lease_owner=:token AND status='PROCESSING';

-- 失败（next_status = RETRY_WAIT 或 DEAD，delay 由最小退避算出）
UPDATE notification
SET status=:nextStatus, next_attempt_at=DATE_ADD(NOW(3), INTERVAL :delay SECOND),
    last_status_code=:code, last_error_class=:err,
    lease_owner=NULL, lease_until=NULL
WHERE id=:id AND lease_owner=:token AND status='PROCESSING';
```

返回 0 行 = 守卫失败 = 结果过期，丢弃并记 warn 日志。

## 4. 处理流程

```
@Scheduled(500ms) → DispatcherScheduler.tick() → Dispatcher.pollOnce()
  │
  ├─ idle = poolSize − activeCount；batch = min(batchSizeMax, idle)   ← §2.4
  ├─ token = 实例ID + 轮次随机段
  ├─ [事务] 认领 UPDATE + 回读（SKIP LOCKED，行锁随事务提交释放）      ← §2.1
  └─ 每条 → 线程池提交 deliverOne()
        ├─ decode headers/body（PayloadCodec，T2.4 换密文实现零改动）
        ├─ HTTP 投递（connect 3s / total 15s / 禁重定向）
        ├─ [无条件] INSERT delivery_attempt（attempt_no = 认领后的 attempt_count）← §2.5
        └─ [守卫] UPDATE 状态：成功 SUCCEEDED / 失败 RETRY_WAIT 或 DEAD    ← §2.5/2.6
```

异常边界：`deliverOne` 整体 try/catch，**任何未预期异常都按 IO 失败落 RETRY_WAIT**，绝不让异常杀掉 worker 线程、更不会让行卡在 PROCESSING 等租约（兜底保证"不丢不卡"）。

## 5. 代码结构

| 类 | 职责 | 关键点 |
| --- | --- | --- |
| `store/ClaimRepository` | 认领 / 回读 / 状态落库 / 明细插入 | `@Transactional claim()`；SQL 即 §3 |
| `dispatcher/HttpDeliverer` | 单次 HTTP 投递 | JDK HttpClient；超时分类为 `TIMEOUT/DNS/TLS/CONN_REFUSED/IO` |
| `dispatcher/Dispatcher` | pollOnce + 线程池 + deliverOne | batch 钳制、异常边界、守卫失败日志 |
| `store/PayloadCodec` | 新增 `decodeHeaders/decodeBody` | T1.1 只有 encode，投递需要反向；接口对称补全 |

**手工端到端**（mock 9001 → 202 → 2s 内核对）：

| 验收项 | 结果 |
| --- | --- |
| 提交 → 202 + notification_no | `{"notification_no":30,"status":"PENDING"}` |
| mock 收到请求 | 恰好 1 次：`POST /cb auth=Bearer tok123 body_len=26`（凭证与请求体完整到达） |

**过程中的一个修复**：首轮集成测试 2 项失败——原因是测试里注册的 `/5xx` mock handler 忘记记录命中数，实现代码无误。修正测试后全绿（记录在此：失败先查证根因，不轻易怀疑实现，也不轻易放过）。

## 7. 已知限制（显式记录，不留暗坑）

1. **失败不分类**：4xx 也走重试退避（T2.1 修正）。本阶段不产生"白烧预算"的永久后果，因为预算 10 次与退避曲线都会在 T2.1 重审；
2. **total timeout 只覆盖到响应头**：JDK HttpClient 的 `HttpRequest.timeout` 计时到响应头返回，2KB 响应片段读取理论上可被慢 body 拖住——片段读取有界且通常瞬时，真实故障面是超时分类精度而非资源泄漏（T2.1 一并处理）;
3. **started_at 用应用时钟**：delivery_attempt 是事实记录，单条记录的应用时钟偏差不参与任何调度决策（调度全部走 DB NOW(3)），可接受；
4. **单实例内 pollOnce 串行**：@Scheduled fixedDelay 保证不重叠；多实例并发正确性由 SKIP LOCKED + 轮次 token 保证，属于 T2.2 演练验证范围。
