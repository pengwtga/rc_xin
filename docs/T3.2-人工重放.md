# T3.2 人工重放 —— 设计与实现说明

> 对应：任务拆解 T3.2 ｜ 设计文档 V2 §4.6（死信与重放）｜ 依赖：T2.3 死信终态、T3.1 查询接口

## 1. 本阶段边界

| 做 | 不做（明确不采纳或归后续） |
| --- | --- |
| `POST /v1/notifications/{id}/replay`：DEAD → PENDING，预算追加一档 | 自动重放——系统无法区分"供应商拒收"与"已处理但响应超时"，只有人知道业务上能否承受重复（§4.6） |
| 状态守卫写在 UPDATE 的 WHERE 里（防重复点击 / 并发双击 / 误操作） | 分布式锁、`SELECT ... FOR UPDATE`——单行 UPDATE 的原子性已经覆盖全部三个场景 |
| `replay_log` 审计：操作人 / 原因 / 预算快照，与状态迁移同事务 | 复用 `delivery_attempt` 存重放事件——那会破坏"attempt_no 与 attempt_count 一致"的不变式 |
| `reason` 必填，`operator` 缺省为调用方标识 | 批量重放（按 caller + error_class + 时间窗）、重放前探测——运营工具，§4.6 明确列后续 |
| 查单详情的 `replays` 字段（补 T3.1 状态轨迹的时间线空洞） | 重放时重新校验 URL 合法性——投递期 SSRF 校验本来就会重做（T2.4），被拒则一次即 DEAD |

**一句话取舍**：重放接口本身只有一条 UPDATE，这一阶段的全部工作都在**约束"人"这个输入**——只放行 DEAD、留下谁与为什么、不重置历史、给多少预算说清楚。

## 2. 设计思路：六个决策点

### 2.1 守卫只有一条 SQL，却同时解决三个问题

```sql
UPDATE notification
SET status = 'PENDING', max_attempts = ?, next_attempt_at = NOW(3),
    lease_owner = NULL, lease_until = NULL
WHERE id = ? AND caller_id = ? AND status = 'DEAD'
```

| 场景 | 为什么这条 WHERE 能挡住 |
| --- | --- |
| 重复点击 | 第一次已把状态改成 PENDING，第二次匹配不到行（0 行受影响）→ 409 |
| 并发双击 | 两个 UPDATE 在同一行上被 InnoDB 行锁串行化，后到者读到的已是新状态 → 0 行 → 409 |
| 误操作非终态 | PENDING/RETRY_WAIT/PROCESSING/SUCCEEDED/CANCELED 全部匹配不到 → 409 |

先读快照（预算档位需要 `attempt_count`）再 UPDATE，读与写之间存在竞态窗口，但守卫在写时**重查状态**：任何基于过期快照的写入都会失败，而不是落下去。409 的语义对第二次点击完全正确——"不是你的单"是 404，"是你的但它已经不在 DEAD"才是 409，运维脚本靠这个码区分"刷新列表再选一条"和"别碰别人的单"。

### 2.2 预算追加一档：档位取当前配置，不翻倍

`new_max = attempt_count + tier`，其中 tier 与提交时同一来源（caller 覆盖值 `caller.maxAttempts()`，缺省全局 `retry.max-attempts`）。

反面方案是 `max_attempts *= 2`（"翻倍给预算"）：重放三次，预算 10 → 20 → 40 → 80，每次翻倍的档位越来越大，语义失控。取当前配置还有个顺手的好处：**运营给某个 caller 调大预算档位后，下一次重放自动按新档给**，不需要两处配置。

为什么不把 `attempt_count` 归零、按"新任务"给满 10 次：`attempt_count` 是预算的唯一真相（T1.2 起认领自增、T2.5 退还），也挂着 `delivery_attempt.attempt_no` 的一致性——归零后重放的第 1 次尝试会撞 `uk_n_attempt(notification_id, attempt_no)`，投递路径直接卡死。归零在数据上做不到，在语义上也不该做：重放不是"抹掉历史再试"，是"在历史之上再给一档机会"。

### 2.3 状态写 PENDING，与 T2.5 跳过退还的取舍相反

T2.5 的跳过退还特意写 `RETRY_WAIT`（"已经有过尝试的行标 PENDING 会误导排查"），这里却写 PENDING——两个决定表面矛盾，实际是同一个原则：**状态表达"这行此刻处在什么阶段"**。

| | 跳过退还（T2.5） | 重放（T3.2） |
| --- | --- | --- |
| 场景 | 系统自动让路，任务下一刻再次被认领 | 人把任务从终态捞回队列 |
| 语义 | "等待重试" → RETRY_WAIT | "回到队列起点" → PENDING |

调度上两者完全等价（认领条件同时包含两个状态），差别只在人读库时怎么理解。这个决定有一个真实的代价，必须写下来：**`PENDING + attempt_count > 0` 从此是合法组合**，任何"还有多少任务没投过"这类按状态统计的查询都必须把 `attempt_count` 一起看。

### 2.4 审计与状态迁移同事务，且 fail-closed

`replay_log` 与状态 UPDATE 在同一个事务里：审计写不进去，状态就不许迁移。

为什么这里 fail-closed，而投递侧的 attempt 明细是"无条件插入、不绑状态事务"？因为两组写入的关系不同：

- 投递侧：明细与状态是**同一个事实的两面**，明细丢一条只是记录不全，状态是对的；
- 重放侧：审计是**动作的全部凭证**。"重放过"却查不到"谁、为什么、给了多少预算"——这条信息在生产事故复盘时恰好是最需要的，且无法事后补记。

表结构刻意薄：`operator`（64）、`reason`（512）、`attempt_count_before`、`max_attempts_after`、时间。不存"重放后的结果"——那是 `notification.status` 与明细的事，复制过来必然漂移。

### 2.5 `reason` 必填，`operator` 缺省为调用方

- **reason 必填**（空白与缺失 → 422，超 512 字符 → 422）：重放是"人决定再花一次预算"的高风险动作，强制写原因让动作慢半拍——足够拦住"看到 DEAD 列表就全选重放"的条件反射。半年后没人记得"为什么把这批重放了"，这个字段就是唯一线索；
- **operator 可缺省**：脚本 / 系统触发时没有自然人，缺省用调用方标识（API Key 派生，不可伪造）；统一转小写存储，避免 `Alice` 与 `alice` 在审计里变成两个人。

鉴权粒度说明：本阶段信任 API Key（caller 级），`operator` 是**自报字段**，不做校验。谁拿着 k_shop 谁就能以任意 operator 名义重放 shop 的单——这与"凭证即身份"的现有模型一致；要做操作人级鉴权，得先有用户体系，不在这个系统的边界里（§2）。

### 2.6 `last_error_class` 不清空，让"死因"活到重放时刻之后

重放只动 `status / max_attempts / next_attempt_at / lease_*`，**不动** `attempt_count`、`last_status_code`、`last_error_class`。于是重放后的单查出来是：

```
status=PENDING, attempt_count=2/12, last_error_class=HTTP_5XX
```

"它之前是被 5xx 打死的"这个事实跟着单走，直到下一次真实投递落库覆盖。成功后 `markSucceeded` 把 `last_error_class` 置 NULL——那才是它该消失的时刻。

顺带一个正确性细节：重放后的下一次认领，`attemptNo = attempt_count + 1 = 3`，而 `delivery_attempt` 里已有 1、2 两行——不撞 `uk_n_attempt`。这条约束 T2.5 在"跳过不写明细"时保住过一次，重放路径天然满足（因为不归零）。

### 2.7 重放不做 URL 复检——防线在投递期

一条 DEAD 单在队列里躺了几小时甚至几天，期间域名完全可能被改指向内网。重放时不重新做 SSRF 校验是**安全的**，因为 T2.4 的设计本来就要求投递期重新解析并逐 IP 校验——被拦下则请求一个字节都不发，`SSRF_BLOCKED` 一次即 DEAD。在重放入口再查一遍是重复建设，还可能因 DNS 抖动误拒。

## 3. 处理流程

```
POST /v1/notifications/{id}/replay  {operator?, reason}
  ├─ ApiKeyAuthFilter → caller                     ← 无凭证 401
  ├─ @Valid：reason 必填 ≤512、operator ≤64         ← 失败 422
  ├─ readRepo.find(id, caller)                     ← 404（与不存在同一响应）
  ├─ status != DEAD → 409 CONFLICT                 ← SUCCEEDED/PENDING/... 一律拒绝
  ├─ tier = caller.maxAttempts ?? retry.max-attempts
  ├─ newMax = attempt_count + tier
  ├─ @Transactional:
  │    UPDATE ... WHERE status='DEAD'              ← 守卫：0 行 → 409（并发重放先到了）
  │    INSERT INTO replay_log(...)                 ← 同事务：审计失败则整体回滚
  └─ 200 {notification_no, status:PENDING, attempt_count, max_attempts}

调度器（无改动）→ 认领 PENDING → 投递 → attempt_no 继续递增
```

投递引擎零改动：重放只是把行放回认领 SQL 的可见范围（`PENDING` 且到期），后续全部复用 T1.2/T2.x 的既有路径。

## 5. 验证

### 5.1 测试（新增 10 例，全量 143/143 绿）

| 用例 | 覆盖 |
| --- | --- |
| DEAD 重放 → PENDING | attempt_count 不归零（1）、max_attempts=11（1+档位 10）、next_attempt_at 立即可认领、last_error_class 保留 |
| 重放后真实投递成功 | 调度器认领 → SUCCEEDED；明细 attempt_no 1=502、2=200 连续（不撞唯一键） |
| 档位取调用方当前配置 | k_inventory（max-attempts=6）→ 新预算 7；且单必须在 inventory 名下，借 shop 的单重放是 404 |
| SUCCEEDED 重放 409 无副作用 | 状态/计数/预算不变、replay_log 0 行 |
| PENDING 重放 409 | 状态守卫覆盖所有非终态 |
| 重复点击第二次 409 | 且 replay_log 仍只有 1 条 |
| 他人单号 404 | 与"不存在"响应逐字节相同，单未被改动 |
| 缺/空白/超长 reason → 422 | 且无任何副作用 |
| 审计落库 | operator 缺省=caller、reason trim、快照正确；查单详情 `replays` 读到同一条 |
| 无凭证 401 | — |

DEAD 不是 SQL 手写的，是**真实投递制造**的（max_attempts=1 打恒 502 的 mock）——走的是 T1.2/T2.3 的完整路径。

踩坑两条（都在测试侧，服务端无恙）：

1. **MockMvc 请求体中文乱码**：请求需显式 `.characterEncoding("UTF-8")`，否则中文按 ISO-8859-1 落库；
2. **响应断言中文乱码**：`getContentAsString()` 无参重载按 ISO-8859-1 解码，而 `application/json` 按规范默认 UTF-8 不带 charset——真实客户端不受影响，断言需显式给 UTF-8。

### 5.2 现场演示（`scripts/replay_demo.sh`，实测输出）

一条两次 502 进 DEAD 的单，指到"已恢复"的下游（mock 恒 200）：

```
== 2. 人工重放
{"notification_no":173060,"status":"PENDING","attempt_count":2,"max_attempts":12} [HTTP 200]

== 3. 等 3 秒，调度器自然投递
status=SUCCEEDED  attempt_count=3/12  last_status_code=200
attempt_no  status_code  error_class
1           502          HTTP_5XX      ← 重放前的历史
2           502          HTTP_5XX
3           200          NULL          ← 重放后的成功

== 4. 再点一次 replay → 409
{"code":"CONFLICT","message":"只有 DEAD 状态可以重放，当前 SUCCEEDED（attempt 3/12）"} [HTTP 409]

== 6. 查单详情
replays : zhang.san | 供应商已恢复，重新投递 | attempt_before: 2 | budget: 12 | 2026-11-02T10:15:40Z
attempts: [(1,502), (2,502), (3,200)]
```

三个观察合起来才是完整证据：**历史没有被抹掉**（attempt 1、2 还在，计数 3 = 2+1）；**重放给的是新档**（2/2 → 2/12）；**重复点击被状态守卫挡住且不留第二条审计**。

## 6. 已知限制

| 限制 | 后果 | 触发条件 / 何时补 |
| --- | --- | --- |
| 只能单条重放 | 凭证过期积压几千条 DEAD 时逐条点到手断 | 批量重放（按 caller + error_class + 时间窗）是运营工具，§4.6 明确列后续；做之前先把 T3.3 的死信指标补上，否则"哪些该重放"没有数据支撑 |
| operator 是自报字段 | 拿着 k_shop 可以任意署名 | 与"凭证即身份"模型一致；要收紧得先有用户体系（§2 边界之外） |
| 重放对"供应商明确拒收"类 DEAD 无保护 | 重放必失败一次、再进 DEAD（PERMANENT 不花预算，代价仅 1 次请求） | 可接受：一次请求的代价换"人不该被系统拦住"；`PERMANENT` 的死信 reason 本来就在提示"改配置后再重放" |
| replay_log 无清理策略 | 只增不减 | 人工动作频率极低（相对 170 QPS 投递），按 10 年量级估算也在百万行内；归档策略（T3.3 的 body 清理）落地时一并考虑 |
| 并发重放的 409 文案不区分原因 | 第二次点击与"状态恰好变了"给出同一响应 | 语义上两者对调用方都是"重新看状态"，无需区分 |

## 7. 与相邻阶段的关系

- **对 T2.3**：DEAD 的"唯一宣布者"不受重放影响——重放不产生死信事件，也不该产生（它是对死信的响应，不是新的死）；
- **对 T3.1**：详情响应新增 `replays`，§6.1 列的三类时间线空洞补掉一类（重放）；跳过与取消仍无痕迹（有意，见 T3.1 §6.1）；
- **对 T3.3**：重放次数是天然的业务指标（"今天人工重放了多少条"），Micrometer 埋点时在 `ReplayService` 加一个 counter 即可，不需要改存储。
