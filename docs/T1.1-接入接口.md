# T1.1 接入接口 —— 设计与实现说明

> 阶段：M1 / T1.1。文档跟随代码进仓库，与 `API通知系统_设计文档_V2.md` §3.3、§5 对应。
> 本阶段只做**入口**：请求进来、校验、落盘、返回单号。投递（T1.2）、幂等返回（T1.3）不在本阶段。

---

## 1. 本阶段边界

| 做                                                      | 不做（留给谁）                                |
| ------------------------------------------------------ | -------------------------------------- |
| `POST /v1/notifications` 接收请求                         | 认领与投递（T1.2）                            |
| API Key 鉴权 → 解析 `caller_id`                            | 按 caller 限流、背压 503（M3 / V1）             |
| 参数校验（必填、长度、method 白名单、URL 协议、体积上限）                     | SSRF 域名白名单与私有 IP 拦截（T2.4）              |
| 落库 `notification`（`status=PENDING`, `next_attempt_at=NOW()`） | 重复键返回原单号的幂等语义（T1.3）                    |
| 返回 `202 + {notification_no, status}`                   | 请求体 AES-GCM 加密（T2.4，本阶段用 `PlaintextPayloadCodec` 占位） |
| 统一错误体与错误码（401 / 422 / 409）                              | 失败队列指标、Prometheus 指标（M3）               |

## 2. 设计思路：五个决策点

### 2.1 为什么同步只做"落库"，然后立刻 202

业务系统**不关心外部 API 返回值**（需求原文），它只关心"我提交的这条会不会被可靠送达"。
所以接入接口的职责终点是：**把请求变成一行持久化数据**。落库成功即代表可靠性义务开始履行，此时返回 `202 Accepted` 是语义最准确的响应——"已接收，处理未完成"。

对比两个错误做法：
- 返回 `200 OK`：语义上表示"处理完成"，与事实不符，业务方会以为已送达；
- 同步调用外部 API 再返回：把供应商的超时、限流、宕机全部透传给业务系统，等于没做这个系统。

### 2.2 为什么 `caller_id` 由 API Key 派生，而不是请求体里的字段

设计文档 §1.4 的结论：`caller_id` 是**提交身份**，不是业务字段。由服务端从凭证派生带来三个直接收益：

1. **不可伪造**：业务方无法替别的系统提交（否则失败归因、限流、数据隔离全部失效）；
2. **契约更小**：请求体少一个必填字段，接入方少一处出错点；
3. **幂等域天然正确**：唯一键 `(caller_id, idempotency_key)` 中的 caller 部分来自凭证，业务方无法通过填写错误 caller 绕过去重。

MVP 用静态配置表（`notify.auth.clients`）：`api-key → caller-id`，一对一。这是"够用即可"的选择——接入方个位数，动态下发密钥属于控制台范畴（设计文档 §6.2 第 6 条已明确不采纳）。

### 2.3 为什么 `next_attempt_at` 用数据库 `NOW(3)`，而不是应用时间

多实例部署时应用时钟漂移会让"到期判断"出现毫秒级分歧，而到期判断是投递引擎的**唯一调度依据**。只要写入端和读取端用同一个时钟源（MySQL），漂移问题就不存在。

这一条在 T1.1 就定死，因为它是**写入约定**：等到 T1.2 才发现写入用了 `Instant.now()`，就要回头改所有历史数据。

### 2.4 为什么先抽 `PayloadCodec` 接口，哪怕现在只存明文

`headers_enc` / `body_enc` 两列的最终形态是 AES-GCM 密文（T2.4）。如果 T1.1 直接把明文塞进列里，T2.4 就要在 Service、Repository、查询接口三处同时改。

抽一个两方法的接口（`encodeHeaders` / `encodeBody`），本阶段 `PlaintextPayloadCodec` 序列化为 UTF-8 字节，T2.4 换成 `AesGcmPayloadCodec` 即可，**上层零改动**。这是"为已知的下一步留缝"，不是过度设计——缝的成本是一个接口，收益是避免一次横切改动。

> 显式声明：本阶段 `*_enc` 列里是**明文**（Header 以 JSON 序列化后存字节）。这是阶段性妥协，已在代码注释与 §7 标注，T2.4 必须完成替换。
>
> **已完成（T2.4）**：`PlaintextPayloadCodec` 已删除，改为 `AesGcmPayloadCodec`（AES-256-GCM，`ver+field+IV+ciphertext+tag`）。上层 Service / Repository / 投递器一行未改，验证了这层接口的隔离作用。详见 `docs/T2.4-出站安全与凭证加密.md` §2.7。

### 2.5 为什么重复幂等键暂时返回 409，而不是 202 + 原单号

T1.3 的验收标准才是"重复提交返回同一单号"。T1.1 若顺手实现，会让 T1.3 没有可验证的增量。

但**不能让它变成 500**：唯一键冲突是可预期的业务分支，不是系统故障。所以 T1.1 捕获 `DuplicateKeyException` 返回 `409 DUPLICATE_IDEMPOTENCY_KEY`，并明确标注"T1.3 将改为 202 + 原单号"。这也让 T1.3 的改动有清晰的前后对照。

## 3. 接口契约

### 3.1 请求

```
POST /v1/notifications
X-Api-Key: k_shop
Content-Type: application/json
```

```json
{
  "idempotency_key": "order_paid:pay_20261030_001",
  "target_url": "https://crm.example.com/api/v1/contacts/status",
  "http_method": "POST",
  "headers": { "Authorization": "Bearer xxx", "X-Tenant": "acme" },
  "body": "{\"contact_id\":\"c_1\",\"status\":\"paid\"}"
}
```

| 字段                | 必填 | 约束                                              | 说明                       |
| ----------------- | -- | ----------------------------------------------- | ------------------------ |
| `idempotency_key` | 是  | 非空、≤128 字符                                     | 建议 `<事件类型>:<事件唯一ID>`，**不做格式强制**（见 §7） |
| `target_url`      | 是  | 非空、≤2048；必须是 `http`/`https`，必须有 host           | T2.4 再加 SSRF 白名单与私有 IP 拦截 |
| `http_method`     | 否  | 默认 `POST`；白名单 `POST/PUT/PATCH/DELETE/GET`        | 防止方法注入                   |
| `headers`         | 否  | ≤50 项；名称/值不含 CRLF；序列化后 ≤4096 字节                 | 含凭证，最终加密存储               |
| `body`            | 否  | ≤64KB                                           | 原始字符串（业务方已渲染好），本系统不解析、不改写 |

### 3.2 响应

**202 Accepted**

```json
{ "notification_no": 1, "status": "PENDING" }
```

| 错误码 | code                          | 场景                                  |
| --- | ----------------------------- | ----------------------------------- |
| 401 | `UNAUTHORIZED`                | 缺少或无效 `X-Api-Key`                   |
| 422 | `VALIDATION_FAILED`           | 字段缺失/超长、URL 协议非法、method 不在白名单、Header 含 CRLF |
| 409 | `DUPLICATE_IDEMPOTENCY_KEY`   | 同 caller 同幂等键已存在（T1.3 改为返回 202 + 原单号） |
| 500 | `INTERNAL`                    | 落库失败等非预期异常                          |

> **已变更（T1.3，2026-10-31）**：409 这一分支已删除，重复提交现在统一返回 `202 + 原单当前状态`，见 `docs/T1.3-幂等去重.md`。本表其余部分与当前实现一致；409 行保留为 T1.1 时点的历史记录。

统一错误体：

```json
{ "code": "VALIDATION_FAILED", "message": "idempotency_key 不能为空" }
```

## 4. 处理流程

```
业务系统
  │ POST /v1/notifications  (X-Api-Key)
  ▼
[ApiKeyAuthFilter] ── 无/错 Key ──▶ 401 UNAUTHORIZED（不进 Controller）
  │ 命中 → request.setAttribute(caller)
  ▼
[IngestController] ── @Valid 失败 / JSON 解析失败 ──▶ 422 VALIDATION_FAILED
  │
  ▼
[NotificationService.submit]
  │ ① 业务校验：URL 协议与 host、method 白名单、Header CRLF/体积、body 体积
  │ ② PayloadCodec 编码 headers/body
  │ ③ Repository.insert（next_attempt_at = DB NOW(3)）
  │      └─ DuplicateKeyException ──▶ 409 DUPLICATE_IDEMPOTENCY_KEY（T1.3 改语义）
  ▼
202 Accepted {notification_no, status:"PENDING"}
```

**校验顺序是有意的**：鉴权 → 结构校验（`@Valid`）→ 业务校验 → 落库。
把鉴权放最前，使无效凭证的请求**不消耗任何业务校验与数据库资源**；结构校验先于业务校验，保证业务层拿到的对象字段一定非空。

## 5. 代码结构

| 类                            | 包              | 职责                                            |
| ---------------------------- | -------------- | --------------------------------------------- |
| `AuthProperties`             | `config`       | `notify.auth.clients` 静态密钥表                  |
| `ApiKeyRegistry`             | `ingest`       | 构建 `apiKey → caller` 索引；解析 `maxAttempts` 缺省值 |
| `ApiKeyAuthFilter`           | `ingest`       | `/v1/**` 鉴权，401 直接写响应；把 `caller` 放进 request attribute |
| `IngestController`           | `ingest`       | 只做参数接收 + 状态码，不含业务判断                          |
| `SubmitNotificationRequest`  | `ingest.dto`   | 请求体 + Bean Validation 注解                      |
| `SubmitNotificationResponse` | `ingest.dto`   | `notification_no` / `status`                   |
| `NotificationService`        | `ingest`       | 业务校验 → 编码 → 落库 → 组装响应；唯一的分支判断处               |
| `NotificationRepository`     | `store`        | `JdbcTemplate` 插入 + 回填自增 id                  |
| `PayloadCodec` / `PlaintextPayloadCodec` | `store` | 编码边界（T2.4 换成 AES-GCM 实现，上层不动）               |
| `ApiException` / `ApiError` / `ApiExceptionHandler` | `api` | 统一错误体与异常映射（含 422 覆盖 Spring 默认 400）             |

## 7. 已知限制（显式记录，不留暗坑）

1. **`*_enc` 列为明文**：T2.4 必须替换为 AES-256-GCM，并加"日志不打 Header"约束；
2. **API Key 明文写在 `application.yml`**：MVP 交接方式；生产应由配置中心/密钥管理系统注入；
3. **无速率限制**：单 caller 高频提交目前会被全盘接受，T3.3 加队列守卫、V1 加按 caller 令牌桶；
4. **不做幂等键格式强制**：`<事件类型>:<事件ID>` 只是接入文档里的建议（见过度设计对比 §6）。格式错误不会导致系统出错，只会降低业务方自己的去重效果；
5. **无出站行为**：本阶段落库后不会有任何网络调用，T1.2 才引入投递引擎。
