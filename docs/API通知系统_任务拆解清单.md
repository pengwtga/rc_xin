# API 通知系统 —— 任务拆解清单（V0 / MVP）

> 配套文档：`API通知系统_设计文档.md`（同目录）。每个任务标注「设计文档章节」，便于回查判断依据。
> 总量：**核心可运行 MVP ≈ 4 人日**，**完整交付 ≈ 6.5 人日**（单人估算，含自测，不含需求澄清等待时间）。

---

## 0. 拆解原则（先说清为什么这样切）

1. **纵向切片优先，不做"先写完所有层再联调"**：M1 结束时系统已经能"提交一条 → 真的打出去"，之后所有能力都是在这个可运行骨架上增量叠加。作业评估关注判断力，一个第 4 天才能跑起来的系统无法暴露设计问题。
2. **每个任务的完成定义是「可验证的行为」，不是「代码写完了」**：验收标准尽量落到一条 `curl`、一条 SQL 或一个测试用例名上。
3. **不在 MVP 路径上的东西一律单列**（§5），避免边做边加、工期失控。
4. **先做能出事故的部分**（认领/租约/失败分级），再做锦上添花的部分（指标面板/重放工具）。

### M1 能存能投（2.0 人日）—— 第一个可演示版本

| ID   | 任务                                       | 产出物                                                                          | 验收标准                                                                                          | 依赖   | 估时   | 文档   |
| ---- | ---------------------------------------- | ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- | ---- | ---- | ---- |
| T1.1 | 接入接口 `POST /v1/notifications` + 校验 + 落库 | `IngestController`、`NotificationService.submit()`、请求 DTO、API Key 鉴权（静态表）      | `curl` 提交合法请求返回 `202 + {notification_no, status:PENDING}`；DB 有一行 `PENDING`/`next_attempt_at<=now`；缺字段返回 422 | T0.3 | 4h   | §3.3 §5 |
| T1.2 | 投递引擎：认领 + HTTP 调用 + 状态落库                | `Dispatcher`（`@Scheduled` 500ms 触发 `pollOnce`）、`ClaimRepository`（§4.3 完整 SQL）、`HttpDeliverer`（JDK HttpClient，connect 3s / total 15s） | 启动 mock 服务，提交 1 条 → mock 收到 1 次请求 → `status=SUCCEEDED`；`delivery_attempt` 有 1 行且 `status_code=200`；从提交到送达 < 2s | T1.1 | 8h   | §4.3 §3.3 |
| T1.3 | 幂等去重（可并行）                              | `UNIQUE(caller_id, idempotency_key)` + 重复键捕获 → 返回原单号                          | 同 key 提交两次：两次都返回 202 且 `notification_no` 相同，表里只有 1 行；换 caller 同 key 可建新行                | T1.1 | 2h   | §4.7 |

**M1 Gate 演示脚本**（3 条命令过一遍）：

```bash
# 1. mock 下游
python3 -m http.server 9001 &
# 2. 提交
curl -sS -XPOST localhost:8080/v1/notifications -H 'X-Api-Key: k_shop' -H 'Content-Type: application/json' \
  -d '{"idempotency_key":"order_paid:pay_001","target_url":"http://127.0.0.1:9001/cb","http_method":"POST","headers":{},"body":"{\"order\":1}"}'
# 3. 查状态
curl -sS localhost:8080/v1/notifications/1 -H 'X-Api-Key: k_shop'
```

> 注意：T1.2 里 `pollOnce()` 必须与 `@Scheduled` 分离——否则 M4 的集成测试会被自己后台线程污染（§9.2 用例 7）。这个坑现在花 10 分钟处理，后面省半天。

### M2 可靠投递（2.0 人日）—— 本项目的核心价值所在

| ID   | 任务                          | 产出物                                                                                       | 验收标准                                                                                            | 依赖   | 估时   | 文档   |
| ---- | --------------------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- | ---- | ---- | ---- |
| T2.1 | 失败分级 + 退避调度                | `ErrorClassifier`（2xx/永久/可重试三类，含端点级覆盖表）、`BackoffPolicy`（`min(cap, base*2^(n-1))*jitter`） | 400 → 1 次后 `DEAD`；500 → `RETRY_WAIT` 且 `next_attempt_at` 符合公式；连续 3 次的间隔单调递增且带抖动；429 时优先用 `Retry-After` | T1.2 | 6h   | §4.4 |
| T2.2 | 租约与崩溃恢复                     | 认领 SQL 的 `lease_until < now` 分支；结果落库带 `lease_owner` 守卫                                     | 投递中途 `kill -9` worker → 60s 内被另一实例认领并完成；`attempt_count` 正确递增；旧 worker 复活后结果不覆盖新状态（人工构造验证）           | T2.1 | 4h   | §4.3 §4.2 |
| T2.3 | 死信终态 + 尝试预算                 | `max_attempts` 判定 → `DEAD`；`last_error_class` 落库；死信日志/告警钩子（先写日志，M3 接指标）                    | `max_attempts=3` 时第 3 次失败后进入 `DEAD` 且不再被认领（查 `idx_due` 无该行）                                    | T2.1 | 2h   | §4.6 |
| T2.4 | SSRF 防护 + 凭证加密              | URL 校验器（scheme 白名单、IP 私有段/回环/链路本地拦截、禁重定向、解析后校验实际 IP 绑定）、Header/Body AES-256-GCM 加解密 | 提交 `http://169.254.169.254/` 返回 422；`http://127.0.0.1` 在未加白名单时被拒；DB 中 `headers_enc` 为密文，日志无明文凭证 | T1.1 | 4h   | §4.10 |
| T2.5 | 端点隔离 + 熔断（可并行）              | per-host 信号量 + 熔断器（60s 窗口，失败率>50% 且样本≥20 → OPEN 60s），**跳过不计 attempt_count**         | mock 一个 host 持续 500 → 该 host 任务进入 `RETRY_WAIT` 但 `attempt_count` 不增长；同时另一 host 的投递 p99 不受影响 | T2.1 | 4h   | §4.5 |

### M2 Gate：6 个故障场景（建议写成可重复执行的脚本 `scripts/fault/*.sh`）

| # | 场景                    | 期望                                             |
| - | --------------------- | ---------------------------------------------- |
| 1 | 下游返回 400             | 1 次即 `DEAD`，无重试                               |
| 2 | 下游返回 500 连续 3 次后恢复    | 第 4 次成功 → `SUCCEEDED`，attempt 4 行             |
| 3 | 下游超时（sleep 20s）       | 15s 断开 → `TIMEOUT` 分类 → 重试                     |
| 4 | 投递中 kill worker       | 租约过期被接手，最终成功；接受"下游收到 2 次"（语义验证）               |
| 5 | 一个 host 全挂            | 该 host 任务被推迟且不烧尝试预算；另一 host 正常                    |
| 6 | 同 key 并发提交 10 次        | 表里 1 行，10 个响应同单号                               |

## 4. 风险与提前处理

| 风险                                  | 影响                        | 处理动作                                                     |
| ----------------------------------- | ------------------------- | -------------------------------------------------------- |
| 认领 SQL 在 `LIMIT` + `SKIP LOCKED` 子查询上报错 | 卡住 M1 半天                  | 用 §4.3 的双层子查询写法（MySQL 8.0 对 `LIMIT` 与 `FOR UPDATE` 同层有限制）；先在 mysql-cli 单独验证 SQL |
| 集成测试被 `@Scheduled` 污染                | 测试随机失败、误打真实地址             | T1.2 起就把调度器抽成 `pollOnce()`，测试配置 `scheduler.enabled=false` |
| 熔断"跳过"被误算成一次失败                      | 供应商长故障时任务被烧成 DEAD，事故扩大     | T2.5 验收标准里直接写"`attempt_count` 不增长"，用测试固化             |
| 加密导致查询/排查变难                         | 现场排查问题要多一步解密，容易图省事去打明文日志 | 只在读写边界解密，日志层强制只打长度；把"日志无明文"写进 T2.4 验收           |
| 压测数据不好看                             | §7 的估算被证伪，需要临时改方案        | 把"实测 vs 估算对比表"作为 T4.2 的交付物，**证伪也是有效结论**（作业评估看重判断过程）     |
