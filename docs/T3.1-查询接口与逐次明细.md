# T3.1 查询接口与逐次明细 —— 设计与实现说明

> 对应：任务拆解 T3.1 ｜ 设计文档 V2 §5（对外 API 契约）、§4.11（可观测性）｜ 依赖：T1.2 明细落库、T2.3 死信终态、T2.4 凭证加密

## 1. 本阶段边界

| 做 | 不做（明确不采纳或归后续） |
| --- | --- |
| `GET /v1/notifications/{id}`：状态 + 逐次 attempt 明细 | 状态流水表（每次状态变更写一行）——理由见 §2.1 |
| `GET /v1/notifications?status=&cursor=&limit=`：键集分页 | 按时间段 / 目标地址 / 幂等键检索 —— 那是"工单系统"，不是本系统的边界（§2 问题边界） |
| Header 白名单脱敏、body 不回显 | 按需解密查看 body（任何"临时放开一下"的口子都会变成常态） |
| 越权与不存在统一 404 | 403 + 404 区分 —— 那等于提供单号存在性探测 |
| 参数错误分 400 / 422 两档 | 给调用方提供 GraphQL 式字段选择（一条 SQL 读全行，投影省不了 IO） |
| 为列表加一条索引（V2 迁移） | 全局运维视图（跨 caller 查所有单）——那需要独立的后台与更高权限，不在对外 API 里 |

**一句话取舍**：这一阶段的产品目标是让"这条为什么没到"能在一次 HTTP 调用里回答完，同时**不因为回答这个问题而把 PII / 凭证再泄露一遍**。后半个目标决定了本阶段一半的设计。

## 2. 设计思路：九个决策点

### 2.1 状态轨迹从明细还原，不建状态流水表

"查单返回状态轨迹"最直觉的实现是加一张 `notification_status_log`，每次状态变更写一行。没有采纳，三个理由按重要性排序：

1. **信息是冗余的**。状态只有 6 个，而每次真正的状态变更都对应一次投递（`PENDING → PROCESSING → SUCCEEDED/RETRY_WAIT/DEAD`），这些已经是 `delivery_attempt` 的行。再写一张表，等于把同一件事记两遍，两处一旦不一致，排查的人不知道该信谁；
2. **代价是写放大**。这张表是队列表，投递路径上每单至少 3 次状态变更，170 QPS 峰值下就是每秒 500 次额外写入，换来的信息量为零；
3. **它只增不减**，且永远不会有人清理（审计属性），几个月后就是库里最大的表，而查询只按单号点查。

所以 `GET /{id}` 返回的是：**当前状态 + 最近一次结果（`last_status_code` / `last_error_class`）+ 逐次明细**。前者回答"现在怎么样"，后者回答"一路怎么走过来的"——把明细按 `attempt_no` 升序读下来，就是时间线。

**这个选择的代价要说清楚**：`CANCELED` 与 T3.2 的人工重放不产生 attempt 明细，它们造成的时间线空洞无法从查询接口看出。T3.2 落地时会补一条 `replay` 审计记录（操作人 + 原因 + 时间），届时轨迹里会多一类事件——但那是"人为操作留痕"，与"投递事实"分开存，仍然不需要状态流水表。

### 2.2 body 不回显：加密的承诺必须延伸到读路径

`body_enc` 用 AES-256-GCM 加密存储（T2.4），保护的是"拿到数据库 ≠ 拿到内容"。如果查询接口把 body 解出来返回，这个承诺立刻降级成"只防备份文件"——任何一个持有 API Key 的调用方都能读到自己的（以及通过 bug 读到别人的）明文 PII。

响应里只有 `has_body: true/false`。**这个字段的存在本身是有意义的**：排障时最常见的问题之一是"我这单到底带没带 body"，`has_body` 能回答它，而不用把内容交出去。

想知道"内容对不对"，只有两条路：查提交侧的请求日志，或者让调用方自查。这是真实的排障能力损失，接受它，因为反向的代价更大。

实现上还有一个细节：`SELECT` 里写的是 `(body_enc IS NOT NULL) AS has_body`，**不把 MEDIUMBLOB 读出来**。单条 body 上限 64KB，为了判断非空而把它搬进内存再丢掉，在列表/详情被高频调用时是纯浪费。

### 2.3 Header 用白名单，不用黑名单

Header 必须回显一部分——"我提交时到底带没带 `Authorization`"是最高频的排障问题，而 header 的**名字**本身就在密文里，不解就列不出来。

问题是要不要回显值。**白名单**：

| 头 | 回显 | 理由 |
| --- | --- | --- |
| `Content-Type` | 原文（截断 200 字符） | 对方按什么解析，直接决定 415/400 的归因 |
| `Accept` | 原文 | 同上 |
| `User-Agent` | 原文 | 有的供应商靠它做风控 / 灰度 |
| `X-Request-Id` | 原文 | 与对方技术支持对齐日志时唯一的锚点 |
| 其余全部 | `****` | 默认拒绝 |

为什么不用"敏感名单 + 其余回显"：**黑名单永远漏**。今天想到 `Authorization`、`Cookie`，明天调用方用 `X-Auth-Token`、`X-Supplier-Secret`，后天有人把密钥塞进 `X-Signature-Payload`。漏一次的结果是把下游凭证写进另一个系统的日志和前端页面，且不可撤回。白名单的失效方式是"看不见想看的头"（可接受），黑名单的失效方式是"泄漏"（不可接受）。

占位符是固定 4 个星号，**不保留长度、不保留前缀**：长度也能泄漏信息（比如"这个 token 长度像 JWT"），前缀更是直接给出凭证的开头。

判断用小写化后比对，且必须用 `Locale.ROOT`——用默认 Locale 在土耳其语环境会把 `I` 折成 `ı`，`AUTHORIZATION` 就绕过了。

### 2.4 越权与不存在返回同一个 404

```sql
WHERE id = ? AND caller_id = ?
```

查不到就 404，**不区分**"不存在"与"不是你的"。如果前者 404、后者 403，这个接口就成了单号存在性探测器：调用方可以从 404/403 的差异推断出某个单号是否存在、属于谁的业务量级。

响应体也逐字节相同（`{"code":"NOT_FOUND","message":"通知不存在或无权访问"}`），集成测试直接断言两条响应的字符串相等——比断言状态码更严格，能挡住"状态码一样但消息不同"的退化。

代价：真正的越权排查（"客户说他查不到自己的单"）需要人工核对 caller 与单号的归属，接口不会帮忙区分。内部系统、十几个 caller 的量级，这个代价可以接受。

### 2.5 键集分页，不是 OFFSET

```sql
-- 键集：上一页最后一条的单号做锚点
WHERE caller_id=? AND status=? AND id < ? ORDER BY id DESC LIMIT n+1

-- OFFSET：要求数据库先数过前 N 行
... ORDER BY id DESC LIMIT n OFFSET 10000
```

两个理由，第二个比第一个更要紧：

1. **深翻页的代价与偏移量成正比**。12.5 万行（其中该 caller 的 DEAD 17500 行）实测：

   | 方式 | 扫描行数 | 实际耗时 |
   | --- | --- | --- |
   | 键集（游标指向第 10000 条） | 21 | 1.46 ms |
   | `OFFSET 10000` | 10021（丢掉 10000） | 2.73 ms |

   倍数不吓人，但它是**线性增长**的：翻到 10 万条时就是 10 倍；而且这段开销发生在数据库里，占着连接与 BP 的页。

2. **OFFSET 在并发插入下是错的**。翻页过程中有新单进来，后续页的 OFFSET 指向的位置整体后移，调用方会看到重复行、也会漏行——对一个"拉取死信清单并逐条重放"的消费者来说，重复行意味着重复操作，漏行意味着永久遗漏。键集以单号为锚点，插入不影响已翻过的区间。

`LIMIT n+1` 多取一条只用于判断"还有没有下一页"，避免再发一次 `COUNT(*)`（在队列表上 COUNT 是最贵的那类查询）。

游标就是"上一页最后一条的单号"，十进制明文，**不做 base64 之类的不透明化**：单号本来就对外暴露（提交响应里就有），编码只会让排障多一步解码，不带来安全收益。将来若要改排序键（例如按 `next_attempt_at` 翻页），再引入带版本前缀的游标，届时旧客户端拿到的是 422，而不是悄悄翻错页。

### 2.6 响应片段再截断到 512 字符

`delivery_attempt.response_snippet` 落库时已截到 2048（T1.2：不让失控对端拖住 worker）。查询返回时再截到 512，两个理由：

- 列表/详情是被人看的。2048 字符的错误页在终端里是一屏乱码，关键信息（状态码 + 第一行错误消息）永远在前面 512 里；
- 上游响应体可能**回显我们的请求内容**（少数供应商会把 body 打进 4xx 的响应里），截得越短，二次泄漏面越小。

截断按**码点**而不是 `char`：直接 `substring` 会把 emoji / 生僻字的代理对切成两半，产出非法 UTF-16，下游 JSON 解析器报的错完全指不到这里。

明细本身也有条数上限：单次最多返回最近 **200** 条（`ORDER BY attempt_no DESC LIMIT 200` 后在内存里翻转成正序）。排障时"最近几次怎么失败的"比"最早那次"有用，所以截断的是头部。调用方可以用响应里的 `attempt_count` 与 `attempts` 的长度比较，判断是否被截断——不额外给 `truncated` 布尔，少一个可能与实际不一致的字段。

### 2.7 参数错误分两档：400 与 422

沿用系统既有口径（`ApiExceptionHandler` 的注释）：

| 状态码 | 语义 | 本例 |
| --- | --- | --- |
| 400 `INVALID_PARAMETER` | **类型层面就解析不出** | `/v1/notifications/abc`、`cursor=xyz`、`limit=x` |
| 422 `VALIDATION_FAILED` | 解析出来了，但内容不合法 | `status=FOO`、`limit=0`、`limit=101`、`cursor=0` |
| 404 `NOT_FOUND` | 资源不存在或不属于你 | `/v1/notifications/999` |

这里补了一个**真实存在的坑**：`@PathVariable long id` 遇到 `/abc` 会抛 `MethodArgumentTypeMismatchException`，而 `ApiExceptionHandler` 只有一个 `Exception` 兜底 → 返回 **500**。等于把纯客户端错误打成服务端故障：告警会响、排查会被误导到服务端、SLO 的错误率指标被污染。T3.1 加了专门的 handler 把它映射成 400（`getRequiredType()` 顺手带出"期望 long"）。

`status` 不在枚举里选择报错而不是"当成不过滤"：静默忽略过滤条件会让调用方以为看到的是死信清单、实际是全量清单——**按错的集合做决策比直接报错危险得多**（尤其下一个动作是批量重放）。

### 2.8 解密失败要降级，不能 500

查详情需要解密 headers 才能列出名字。密钥轮换、历史密文损坏、从库同步截断，都会让解密抛异常。

如果此时返回 500，最需要这个接口的时刻（出事了、在查这条单）恰恰查不了。所以失败只降级：`headers_decodable=false` + `headers=[]`，其余字段照常返回。

日志只记单号与异常类型（`e.getClass().getSimpleName()`），**不打异常堆栈里的任何密文**——`AEADBadTagException` 的 message 里可能带数据片段，日志本身也是泄漏面。

`headers_decodable` 与 `headers=[]` 这两个信息都要有：空数组单独一个字段无法区分"本来就没带头"和"解不开"。

### 2.9 索引只加一条，且有实测依据

V2 迁移只加 `idx_caller_status (caller_id, status)`：

- `caller_id + status` 等值定区间，`id` 由 InnoDB 二级索引隐含的主键后缀提供序——所以**不需要显式写第三列**，物理顺序已经是 `(caller_id, status, id)`；
- 这条索引同时覆盖了列表要返回的 `id` 与 `status`，`EXPLAIN` 显示 `Using index`，连回表都省了；
- 实测执行计划：`Covering index range scan ... (reverse)`，**无 filesort**。

刻意**没有**给"无状态过滤的列表"再建一条 `(caller_id, id)`：那是一次运维兜底用法（低频、可以慢一点），而每条二级索引都要在各个 INSERT 上付维护成本——这张表同时还是投递队列，写入侧不该为低频查询买单。25 万行实测，不带状态过滤时优化器在 PRIMARY 反向扫描（0.06ms）与专用索引（0.10ms）之间切换，量级上都没问题。真需要时再加，加之前先看 `EXPLAIN`。

> 为什么是 V2 而不是改 V1：V1 已经推送并执行过，Flyway 的 checksum 会拒绝任何改动（改注释也会变）。本地为了重放 V2，做法是 `DELETE FROM flyway_schema_history WHERE version='2'` + `DROP INDEX`，让 Flyway 重新执行——**只对未推送的迁移可以这么做**，已上线的版本永远只能往前加。

## 3. 处理流程

```
GET /v1/notifications/{id}
  ├─ ApiKeyAuthFilter：X-Api-Key → caller（无效直接 401，不进 Controller）
  ├─ @PathVariable long id          ← /abc 在这里转 400（不是 500）
  ├─ readRepo.find(id, caller)      ← WHERE id=? AND caller_id=?；查不到 → 404
  ├─ readRepo.findAttempts(id,200)  ← ORDER BY attempt_no DESC LIMIT 200 → 翻正序
  ├─ codec.decodeHeaders(...)       ← try/catch：失败 → headers_decodable=false
  │    └─ masker.mask(...)          ← 白名单回显，其余 ****
  └─ 组装 DTO（snippet 再截 512、时间补 Z）

GET /v1/notifications?status=&cursor=&limit=
  ├─ normalizeStatus（大小写不敏感，非枚举 → 422）
  ├─ parseCursor（非数字 → 400，≤0 → 422）
  ├─ normalizeLimit（1..100，越界 → 422）
  ├─ readRepo.page(... LIMIT n+1)   ← caller_id 必带，status/cursor 按需拼
  └─ hasMore = size > limit → nextCursor = 本页最后一条的 id
```

`status`/`cursor` 两个条件在 SQL 里是**字符串拼接**而不是 `(status = ? OR ? IS NULL)`：后者会让优化器放弃 `idx_caller_status`，退化为扫描该 caller 的全部行。

## 6. 已知限制

### 6.1 时间线有三类空洞

`attempts` 只记录"真的发出了 HTTP 的尝试"。下列事件不产生明细，从轨迹上看不出来：

| 事件 | 现状 | 何时补 |
| --- | --- | --- |
| 熔断 / 并发满导致的跳过（T2.5） | 状态是 `RETRY_WAIT` 但列表里看不出"被跳过" | 不补：跳过的语义就是"没发生"，写进去反而污染"尝试次数" |
| 人工重放（T3.2） | 状态从 DEAD 回 PENDING，无痕迹 | T3.2 补 replay 审计记录（操作人/原因/时间），与投递事实分开存 |
| 人工取消（CANCELED） | 同上 | 与重放一起做 |

查询接口的语义是"投递事实"，不是"全量审计"。要审计就单独建审计表，不要往事实表里掺事件。

### 6.2 单条明细上限 200 条是硬编码

`max_attempts` 默认 10，正常情况下永远碰不到。但一条被反复人工重放的单，明细可以无限增长；200 条之后只能看到最近的。真要查更早的，只能上 SQL。

### 6.3 页大小与明细上限没有做成配置项

`limit` 的默认 20 / 上限 100、明细 200 条、snippet 512 字符，都是常量而不是 `notify.query.*` 配置。理由：这些不是"环境差异"（不像超时与租约），而是**接口契约的一部分**——做成配置项之后，同一个 API 在不同环境返回不同的最大值，客户端就得按最小环境来设计，收益为零、困惑+1。

### 6.4 列表没有"全局视图"

`GET /v1/notifications` 永远带 `caller_id`（来自凭证）。运维要看"整个系统现在有多少 DEAD"，只能查指标（T3.3 的 `notify_dead_total`）或上 SQL。这是有意的：对外 API 不该有跨租户的读能力，那类视图属于后台系统。

## 7. 其余限制

| 限制 | 后果 | 触发条件 / 何时补 |
| --- | --- | --- |
| 详情每次解密 headers | 单次详情多一次 AES-GCM（微秒级） | 不值得缓存明文，缓存反而扩大泄漏面 |
| 无状态过滤时可能走 filesort | 该 caller 数据量大时排序成本上升 | 变成热路径时再加 `(caller_id, id)`，见 §2.9 |
| `next_cursor` 用明文单号 | 客户端可能自己拼游标（跳页） | 语义上允许——键集游标本就是"从这之后继续"，不做防篡改 |
| 详情不返回 `attempt.caller_id` 之外的租户信息 | 无法从响应判断"是不是被别人查过" | 查询是只读的，没有审计需求；要审计得在网关注入 |
| 响应里 `target_url` 不脱敏 | 调用方自己的地址，本就已知 | 若将来支持多租户共享单号，需重新评估 |
