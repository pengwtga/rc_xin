# T2.4 出站安全与凭证加密 —— 设计与实现说明

> 对应：任务拆解 T2.4 ｜ 设计文档 V2 §4.10（安全）｜ 依赖：T1.1、T1.2、T2.3 已完成

## 1. 本阶段边界

| 做 | 不做（归后续或明确不采纳） |
| --- | --- |
| URL 校验器：协议白名单、私有段/回环/链路本地/CGNAT 拦截、解析后逐 IP 校验 | ~~连接层绑定 IP（防 DNS rebinding 的完整方案）~~ —— JDK HttpClient 不支持，见 §2.1 与 §6.1 |
| 校验分两层：受理期（不碰网络）+ 投递期（重新解析） | 按 caller 的域名白名单（设计文档 §4.10 原写"按 caller"，本版降级为全局，见 §2.4） |
| Header / Body 的 AES-256-GCM 加密存储 | 密钥轮换 / 多密钥 keyId（V1，需要数据双写与批量重加密） |
| 白名单内的内网目标可走 http，其余强制 https | 证书固定（pinning）、mTLS |
| 密钥配置 fail-fast + 开发密钥启动告警 | 敏感字段的审计日志（谁在什么时候读过 body） |

**一句话取舍**：安全上能闭环的部分（拒绝内网、凭证不落明文）做到位；闭不了的那一段（解析与连接之间的毫秒级窗口）在 §6.1 写清楚，不留"以为防住了"的错觉。

## 2. 设计思路：八个决策点

### 2.1 一次校验不够：受理期与投递期职责不同

设计文档写的是"解析后校验实际 IP"。实现时必须回答一个前置问题：**在哪一刻解析？**

两个候选时刻，代价完全不同：

| | 受理期解析 | 投递期解析（本版） |
| --- | --- | --- |
| 好处 | 调用方立刻收到 422，体验好 | 受理路径零外部依赖；校验的是"真正要连的地址" |
| 代价 | 受理可用性绑上 DNS 可用性：解析抖动时调用方收到 422，看起来像"你填错了"，实际是我们的 DNS 出问题；受理 p99 被 DNS 长尾拖住 | 恶意目标先被受理（202），到投递时才失败，错误暴露得晚 |

所以本版把两层都留下，各管一段：

- **受理期**（`SsrfGuard.checkForIngest`）：只做不碰网络的判定——协议、host 形态、**IP 字面量的落段**。`http://169.254.169.254/` 这种不需要 DNS 就能看出来的，立刻 422；
- **投递期**（`SsrfGuard.checkForDelivery`）：真正投递前**重新解析**域名，逐个检查解析出的 IP。这才是防线——域名随时可以改指向（DNS rebinding），受理时的判断到投递时可能已经失效。

这也解释了为什么 `http://localhost/cb` 在受理期能过：它不是 IP 字面量，本层不解析。到投递期解析出 127.0.0.1，才被拦下（测试用例 `域名解析到回环被拒_localhost是最常见的绕过` 钉住了这一点）。

### 2.2 地址判定的四个盲区（JDK 的便利方法不够用）

`InetAddress` 自带 `isLoopbackAddress / isSiteLocalAddress / isLinkLocalAddress` 能覆盖大部分情况，但**直接信它会漏掉四类**，每一类都是现成的攻击面：

| 盲区 | 例子 | 为什么漏 | 处理 |
| --- | --- | --- | --- |
| CGNAT 段 100.64/10 | **阿里云 metadata `100.100.100.200`** | `isSiteLocalAddress` 只认 RFC1918 三段 | 显式判 `100.64~127.x` |
| IPv6 ULA fc00::/7 | `[fc00::1]` | JDK 只认已废弃的 fec0::/10 | 判首字节 `(b[0] & 0xFE) == 0xFC` |
| IPv4-mapped IPv6 | `::ffff:127.0.0.1` | 若未折叠成 Inet4Address，长度 16 走不到 IPv4 判定 | 识别 `00×10 + ffff` 前缀后按 IPv4 再判 |
| 保留段与广播 | `0.0.0.0`、`240.0.0.0/4` | `isAnyLocalAddress` 只覆盖 0.0.0.0 单个地址 | 判 `0/8` 与 `>=240` |

阿里云那条是这次真正值钱的细节：腾讯云/AWS 用 169.254.169.254（链路本地，JDK 认），阿里云用 100.100.100.200（CGNAT，JDK 不认）。只测 AWS 的话会以为防住了。

### 2.3 fail closed：一个域名多个 IP，任一命中即拒

`getAllByName` 返回数组，可能是 `[公网, 内网]` 混合。**只要有一个落在禁止段就整体拒绝**，不"挑一个安全的地址去连"。否则攻击者可以让 DNS 交替返回，一半概率打中就够了。

同理，`SecurityException`（被安全管理器拦下、无法校验）按最坏情况处理，不放行。

### 2.4 白名单 = 完全信任，精确匹配，不做通配

白名单项（`notify.ssrf.allowed-hosts`）的语义是一次性放宽两件事：**跳过 IP 段校验** + **允许明文 http**。理由：内网自建回调通常只有 http，也没有公网证书；把它们塞进 IP 段校验里，等于逼运维在"改代码"和"关掉防护"之间选。

三条约束：
- **精确匹配**（不区分大小写，去空白），不支持 `*.internal` 这类通配——通配一写就可能连 `evil.internal.attacker.com` 一起放进信任区；
- **默认空**：生产不加白名单就等于只允许公网 + https；
- **全局而非按 caller**（与设计文档 §4.10 的偏差）：真实的 caller 都是内部系统，隔离收益有限；按 caller 需要"投递期反查 caller 配置"这条额外链路，还要接受"配置被删后 caller 变成无白名单"的边界。V1 多租户时再上移，属纯增量改动。

### 2.5 强制 https 只对非白名单目标生效

明文 HTTP 会把 Header 里的供应商凭证暴露在链路、代理日志、镜像流量里——而凭证恰恰是本系统存的东西。所以非白名单目标强制 https。

代价写清：白名单目标可以走 http，这是有意留的口子——**真正敏感的是凭证，而白名单内的目标是我们自己信任的内网服务**。

### 2.6 `SSRF_BLOCKED` 是策略拒绝，不是网络故障：一次即死

被拦下时请求一个字节都没发出，`statusCode = null`。如果按"网络层失败一律 RETRYABLE"处理，这条任务会把 10 次预算全花在"重试一个被策略禁止的地址"上，最后进 DEAD，日志里留下一串假的网络错误。

所以在分类器里给它单开一条：

```java
if (SSRF_BLOCKED.equals(outcome.errorClass())) {
    return new Decision(Type.PERMANENT, null, SSRF_BLOCKED);   // 重试一万次结果一样
}
```

配套的顺序是：**校验放在解密之前**。被拒绝的目标连凭证都不该被解出来——少一次明文在内存里出现，就少一次被 dump 的机会。

### 2.7 加密格式：AAD 带字段标识，IV 每条随机

```
┌───────┬───────┬──────────┬──────────────────────┐
│ ver 1B│field1B│  IV 12B  │ ciphertext ‖ tag 16B │
└───────┴───────┴──────────┴──────────────────────┘
```

- **`field` 作为 AAD**：不加的话，把 `headers_enc` 的密文挪进 `body_enc` 也能解密成功，列的类型约束就成了摆设。测试 `header与body的密文不可互换_AAD挡住整列搬运` 钉住它；
- **IV 每条随机 12 字节**：GCM 下同密钥重用 IV 会泄露明文异或值，是致命错误。"固定 IV + 计数器"这种省事写法直接排除；随机 IV 在 2^96 空间里，按 birthday bound 要到 2^48 条消息才有可观碰撞概率；
- **不做压缩再加密**：压缩率会随明文变化，形成 CRIME 式侧信道。body 本来就只有几 KB，省这点空间不值得引入一个新的攻击面；
- **Header 的 JSON 用私有 ObjectMapper**：这是内部存储格式，不该随对外契约的 `SNAKE_CASE` 策略一起变——否则改一次 API 命名风格，历史密文就解不出来。

### 2.8 密钥：fail fast，并且认得"仓库里的那把"

- 缺失 / 非 base64 / 不是 32 字节 → **拒绝启动**。带着错误密钥跑起来，所有新数据都用它加密，等发现时已经不可逆；
- 仓库里放了一把开发密钥让 `docker compose up` 开箱可跑，但**启动时检测到它就打 WARN**：任何人都能解出库里的凭证。这是"默认可用"与"默认不安全"之间唯一诚实的折中——不是静默降级；
- **不保留明文 codec 作为可选项**：一个"能把 codec 切回明文"的开关，早晚会有人在故障时切过去。旧的 `PlaintextPayloadCodec` 已删除，切换即不兼容历史明文数据（本阶段库里只有测试数据，直接重建）。

## 3. 处理流程：校验在两条路径上的位置

```
提交 POST /v1/notifications
  └─ checkForIngest：协议 / host 形态 / IP 字面量落段      → 不合格直接 422
  └─ 加密 headers/body → 落库（密文）→ 202

投递（Dispatcher.deliverOne）
  └─ checkForDelivery：重新解析域名，逐 IP 校验
       ├─ INVALID/PRIVATE → outcome(SSRF_BLOCKED) → PERMANENT → DEAD（不发请求、不解密）
       ├─ UNRESOLVED      → outcome(DNS)          → RETRYABLE（DNS 抖动，交给重试）
       └─ OK              → 解密 → HTTP 投递 → 分类落库
```

`UNRESOLVED` 与 `PRIVATE` 分开是必须的：前者是"这次解析不出来"（可能下一轮就好），后者是"解析出来是被禁的地址"（永远不会好）。混成一个就会要么误杀可恢复的 DNS 抖动，要么把策略拒绝重试到预算耗尽。

## 6. 已知限制（三条要紧的，先说）

### 6.1 DNS rebinding 只做了缓解，没做闭环

设计文档 §4.10 写的是"校验用的解析结果与实际连接目标必须同一 IP（连接层绑定）"。**本版做不到**，原因不在实现偷懒，而在技术栈：

- JDK `HttpClient` 没有"自定义解析结果"或"指定连接 IP"的入口（18+ 的 `InetAddressResolverProvider` 是全局 SPI，会波及同进程所有解析，且仍不能保证连接时用的就是校验过的那次结果）；
- 要真正闭环，三条路：换 Apache HttpClient（可注入 `DnsResolver`）、自己写 socket 层、或把 URL 的 host 换成 IP 并手动设 `Host` 头（JDK 默认禁止设置受限头，需开 `jdk.httpclient.allowRestrictedHeaders`，且会破坏 TLS 的 SNI 与证书主机名校验——代价比收益大）。

本版的缓解是"投递前重新解析"，把窗口从**落库到投递**（可能几小时）压到**校验到连接**（毫秒级）。要真正利用这个窗口，攻击者需要：控制目标域名 DNS + 极短 TTL + 恰好在我们校验后的毫秒内切换 + 该域名已通过接入校验。**能控制 DNS 的攻击者，通常已经能直接改 `target_url`**——那时防护靠的是 API Key 鉴权，不是这段代码。

触发条件写明：一旦接入外部不可信 caller，或出现真实的 rebinding 事件，就换 Apache HttpClient 补上连接层绑定。

### 6.2 白名单是全局的，不是按 caller 的

设计文档写"按 caller 配置"。本版降级为全局（§2.4），意味着：任何 caller 都能打白名单里的内网地址。风险可控的前提是**白名单里只放内网自建回调、数量极少**。多租户接入时这会成为真实的越权面，必须上移到 `AuthProperties.Client`。

### 6.3 密钥不能轮换

主密钥写死在进程里，轮换需要：新密钥加密新数据 + 旧密钥解老数据 + 后台批量重加密。本版不做，所以**一旦密钥泄露，只能全量清库重建**。缓解手段是密钥由部署环境注入、不进仓库、不进日志；`ver` 字节已为将来的多版本共存留好位置。

## 7. 其余限制

4. **旧数据不兼容**：明文 → AES 是一次性切换，切换前的 `headers_enc` 解不开（会报"不支持的密文版本"）。本阶段库里只有测试数据，直接重建；真实环境需要一次性迁移脚本；
5. **没有解密失败告警**：密钥配错或数据损坏时，任务会按 IO 失败重试到 DEAD，`error_class=IO`，日志里只有一行"投递前处理异常"。运维看到的是"一堆 IO 失败"，看不出根因是密钥——M3 接指标时应把 `解密失败` 单列一类；
6. **`require-https` 是可关的**：配置成 false 就允许全站明文。这是给"内网隔离环境"留的逃生口，但它把一个安全默认值变成了可配置项，靠流程约束（生产配置评审）兜底；
7. **只保护"落库的凭证"，不保护"传输中的"**：我们加密的是 `headers_enc`/`body_enc`，出站请求本身仍然是明文 HTTP（白名单内）或标准 TLS（不做 pinning）。中间人若已能劫持出站流量，凭证照样泄露；
8. **没有请求体大小与内容类型限制之外的输入校验**：body 里可能是任意二进制/JSON，我们不解析、不校验，只加密存储。PII 的最小留存（成功 24h / 失败 7d 清 body）在 T3.3。
