# T2.3 死信终态与尝试预算 —— 设计与实现说明

> 对应：任务拆解 T2.3 ｜ 设计文档 V2 §4.6（死信与重放）/ §4.2（状态机）/ §4.4（重试预算）｜ 依赖：T2.1、T2.2 已完成

## 1. 本阶段边界

| 做 | 不做（归后续阶段或明确不采纳） |
| --- | --- |
| `max_attempts` 判定 → 终态 `DEAD`（两条路径：一次即死 / 预算耗尽） | ~~独立 DLQ 表或死信主题~~ —— **不采纳**，见 §2.1 |
| `last_error_class` 真正落库（4xx/5xx 也有值，此前恒为 NULL） | ~~自动重放~~ —— **不采纳**，见 §2.2 |
| 死信出口 `DeadLetterSink`（默认实现写结构化日志，M3 接指标不改这里） | 告警通道接入（webhook/IM）、指标上报 —— M3 |
| 死信日志脱敏（query 里的下游凭证不进日志） | 人工重放接口 —— T3.2；body 归档清理 —— T3.3 |
| 预算下界 fail-fast（`max-attempts < 1` 拒绝启动） | 批量重放、重放前探测 —— 明确列为 V1 之后 |

**本阶段改了三处判定逻辑**，都不是新功能，而是 T2.1/T2.2 遗留的语义缺口：`error_class` 的漂移（§2.3）、3xx 的分类（§2.4）、死信的宣布者（§2.5）。

## 2. 设计思路：八个决策点

### 2.1 死信是一个状态，不是一张表

`DEAD` 就是 `status` 列的一个取值。不建 `dead_letter` 表、不投递到死信主题，理由和多建一张表没有关系——**多一份数据就多一处可能不一致**：

- 死信表与 `notification` 是两份事实：状态切换成功后写死信失败 → 死信表少一条；先写死信后切状态失败 → 死信表多一条幽灵。要么加分布式事务，要么写对账任务，两者都比"直接查 `WHERE status='DEAD'`"贵得多；
- 死信需要的全部信息（尝试次数、明细、最后状态码、最后错误类别、时间）都已经在两张表里，死信表只能存冗余副本；
- 查询需求（"某 caller 最近 24h 的死信"）走 `(status, updated_at)` 就够了，量级是万级而非亿级，不需要为它单独设计结构。

**唯一需要额外做的事**：让死信"有声音"。状态本身不会说话，见 §2.5。

### 2.2 预算是"总尝试次数"，两条死法共用一个终态

`max_attempts` 的语义容易写错，先钉死：

| 配置 | 最多发出几次 HTTP | 说明 |
| --- | --- | --- |
| 1 | 1 | 只有首次投递，失败即死（本阶段演示用这个值） |
| 3 | 3 | 首次 + 2 次重试 |
| 10（默认） | 10 | 首次 + 9 次重试，配合退避曲线累计约 3.5h ≈ 业务补偿窗口 |

它是**总次数**而不是"重试次数"，因为计数点是认领（`attempt_count = attempt_count + 1` 写在认领 SQL 里），而认领发生在投递之前——崩溃也会消耗一次（T2.2 §2.4）。如果按"重试次数"理解，崩溃路径的计数就永远对不上。

进入 `DEAD` 有两条完全不同的路径，共用一个终态但要能区分：

| 路径 | 条件 | 消耗预算 | 含义 | 处置 |
| --- | --- | --- | --- | --- |
| `PERMANENT` | 分类为 3xx/4xx | **1 次**（不查预算） | 请求或凭证有问题，重试结果一样 | 改配置/凭证后直接重放 |
| `BUDGET_EXHAUSTED` | RETRYABLE 且 `attempt_count >= max_attempts` | 满额 | 下游持续故障，预算被正常花完 | 先确认下游恢复，再重放 |

这个区分不是装饰：值班的人看到一条 DEAD，第一件事就是判断"能不能重放"，而两条路径的答案相反。

**必须写清的语义风险**：`DEAD` 不等于"下游没收到"。at-least-once 下最常见的一种死法是"下游处理成功但响应超时"（T2.2 §2.5 的窗口），此时重放会造成重复业务动作。系统无法区分"供应商明确拒收"和"供应商已处理但响应丢了"，**只有人知道业务能不能承受重复**——所以本阶段只提供状态和证据，重放留给 T3.2 的显式人工动作。

### 2.3 `error_class` 必须由分类器唯一产生（修一处真实漂移）

T2.1 写完之后，`last_error_class` 的取值和设计文档 §4.1 写的 `TIMEOUT/DNS/TLS/CONN_REFUSED/HTTP_4XX/HTTP_5XX` 对不上：落库时用的是 `outcome.errorClass()`，而投递器只在**网络层失败**时给它赋值，有 HTTP 响应时它是 `null`。结果就是：**5xx 被正确判成 RETRYABLE、正确重试、正确进 DEAD，但 `error_class` 一直是 NULL**。按 `error_class` 分组的告警完全看不见 5xx。

根因不是"少写一个字段"，而是**同一个事实有两个产生者**：状态判定在 `ErrorClassifier`，落库字段在 `HttpDeliverer`。修法是把产生权收归分类器：

```java
public record Decision(Type type, Long retryAfterSeconds, String errorClass) {}
```

- 网络层：透传投递器的 `TIMEOUT/DNS/TLS/CONN_REFUSED/IO`（这几类只有传输层能判断）；
- 有响应：按百位归为 `HTTP_3XX/HTTP_4XX/HTTP_5XX`（**不带具体状态码**——`status_code` 已单独成列，`error_class` 的职责是告警聚合用的粗分组）；
- 成功：`null`（写 `"NONE"` 只会让分组查询多一行噪声）。

配套改了一处顺序：`deliverOne` 里先 `classify` 再 `insertAttempt`，让明细表和主表用同一个 `errorClass`。分类是纯函数、不抛异常，前移没有代价。

### 2.4 3xx 从 RETRYABLE 改成 PERMANENT（修 T2.1 的一个误判）

投递器禁重定向（`Redirect.NEVER`），所以收到 3xx 只有两种可能：目标地址变了（供应商换域名），或对端把请求转去了登录页。两种都是**配置问题**，重试 10 次会拿到同一条 302。

T2.1 当时判成 RETRYABLE，注释写的是"跟随与否是 T2.4 SSRF 校验的职责"。这句话本身没错，但推导错了：**SSRF 校验负责的是"要不要跟随"，与"该不该重试"无关**。既然不跟随，3xx 就是一个确定的失败结果，按 §2.2 的原则（错杀可重放、烧预算不可逆）应当一次即死。

本阶段把它改成 PERMANENT，`error_class = HTTP_3XX`。这也是"预算只花在可能自愈的失败上"这条原则的一致性修复。

### 2.5 单一宣布者：死信只报一次

死信必须有声音，但**只能有一个声音**。改造前 `Dispatcher` 在 DEAD 分支直接 `log.warn`，加上出口再打一条，同一条死信在日志里出现两遍，值班的人会以为死了两条。

约定：**`Dispatcher` 只负责状态落库，`DeadLetterSink` 是死信的唯一宣布者。**

- `Dispatcher` 内部那两条改成 `debug`：本地排障要看到"这一轮做了什么决定"时打开，不参与告警；
- `LoggingDeadLetterSink` 用独立 logger `notify.deadletter` 输出一行结构化 WARN，告警规则绑这个名字即可，不用正则扫全量日志，也不会被正常重试的 WARN 淹没。

### 2.6 死信事件必须晚于状态落库（顺序约束，最容易写反）

`publishDead` 只在 `markDead` 返回 `true`（守卫通过、真正影响 1 行）后调用。

写反的后果很具体：先发事件再落库，一旦守卫失败（租约已被别的实例接管），就会为一个**已被他人接手、可能已经成功**的任务宣布死信。值班的人去查单号，发现状态是 `SUCCEEDED`——从此不再相信任何死信告警。

代码上用 `Transition` 记录把这件事固化成类型约束，而不是靠调用顺序自觉：

```java
private record Transition(boolean applied, DeadLetter.Reason deadReason) {
    Transition {
        // 守卫失败说明这行已被他人接管：即使分支判定该进 DEAD，也不许对外宣布
        deadReason = applied ? deadReason : null;
    }
}
```

### 2.7 出口异常必须隔离：状态已经是事实，不许回滚

`sink.onDead()` 跑在**投递线程**上，任何一个实现抛异常都不能影响两件事：已落库的 DEAD 状态、排在后面的其他出口。

所以 `publishDead` 里逐个 `try/catch(Exception)`，失败只留一行 WARN。这条在 M3 接 webhook 时会真正生效——告警系统不可用是常态，"因为告警发不出去所以死信没落库"是不可接受的。

同时给实现提了硬要求（写在接口 javadoc）：**必须快速返回**。一个阻塞 3 秒的出口等于占掉一个 worker，给投递链路加了一条隐性超时。

### 2.8 预算下界 fail-fast

`notify.auth.clients[].max-attempts` 配成 0 或负数时，`attemptNo(1) < maxAttempts(0)` 为假 → 首次失败立刻 DEAD，而"零预算"的真实含义应该是"这条通知根本不该被受理"。这种配置错误不该用运行时行为兜底，在 `ApiKeyRegistry` 构造期拒绝启动：

```
[启动自检失败] caller-id=xxx 的 max-attempts(0) 必须 >= 1（它是最多尝试次数，含首次投递）
```

## 3. 状态机：三条终止路径

```
                    ┌──────────────────────────── SUCCEEDED   (2xx)
                    │
PENDING/RETRY_WAIT ─┼── PROCESSING ──┬─────────────────────── DEAD  (PERMANENT: 3xx/4xx，1 次即死)
        ↑           │  (认领时        │
        │           │   attempt+1)   └─────────────────────── DEAD  (RETRYABLE 且预算耗尽)
        │           │
        └───────────┘  RETRY_WAIT + next_attempt_at（还有预算）
```

三条终止路径里只有一条"好"的。`DEAD` 是**终态**：后续任何 `pollOnce` 都不会再认领它——认领 WHERE 只有 `PENDING/RETRY_WAIT`（到期）和 `PROCESSING`（租约过期）两个分支，`DEAD` 不在其中。这不是额外加的判断，是状态机设计的自然结果，但需要测试把它钉住（§6.1 用例 1 最后三行）。

## 4. 处理流程（`deliverOne` 的顺序是有讲究的）

```
1. decode headers/body → HTTP 投递（任何异常折叠为 IO 失败）
2. classify(outcome)                        ← 先分类：error_class 与晋级决策同源
3. insertAttempt(..., decision.errorClass()) ← 明细无条件写：这次 HTTP 真实发生过
4. 按分类落状态（带 lease_owner 守卫）
     SUCCESS   → markSucceeded
     PERMANENT → markDead            → reason=PERMANENT
     RETRYABLE → 有预算 ? markFailed(RETRY_WAIT, backoff)
                        : markDead    → reason=BUDGET_EXHAUSTED
5. applied == false → stale 计数并丢弃（过期结果不许改状态，也不许发死信）
6. applied && deadReason != null → publishDead（逐个 sink，异常隔离）
```

第 3 步与状态守卫无关：守卫失败说明"这行已被别人接管"，但这次 HTTP 确实发出去了，明细必须留痕（T1.2 §2.5）。第 6 步与第 5 步的顺序就是 §2.6 的约束。

## 5. 代码改动

| 文件 | 改了什么 | 为什么 |
| --- | --- | --- |
| `ErrorClassifier` | `Decision` 增加 `errorClass`；3xx → PERMANENT；新增 `HTTP_3XX/4XX/5XX` 常量 | §2.3 / §2.4 |
| `DeadLetter`（新） | 死信事件 record + `Reason{PERMANENT, BUDGET_EXHAUSTED}` | §2.2：两条死法要能区分 |
| `DeadLetterSink`（新） | 死信出口接口，约定"快速返回、不抛异常" | §2.5 / §2.7：宣布者与执行者解耦 |
| `LoggingDeadLetterSink`（新） | 独立 logger `notify.deadletter`；URL 脱敏；带 `next_action` | §2.5：告警可路由、凭证不进日志 |
| `ClaimRepository` | 拆出 `markDead`（不动 `next_attempt_at`）；`markFailed` 去掉 `nextStatus` 参数 | 终态不该改写"计划投递时刻"，否则 idx_due 里混入永不被认领的行 |
| `Dispatcher` | 注入 `List<DeadLetterSink>`；先分类后落明细；DEAD 走 `markDead` + `publishDead`；内部日志降为 debug | §2.3 / §2.5 / §2.6 / §2.7 |
| `ApiKeyRegistry` | `max-attempts < 1` 拒绝启动 | §2.8 |
| `V1__init.sql` | `last_error_class` / `error_class` 两列注释改为新语义 | 注释与实现必须一致（T2.3 修的就是"注释对、代码不对"） |

`markDead` 不动 `next_attempt_at` 这一点值得单独说：DEAD 行不会再被调度，改写它只是把一个"永远不会到期的时刻"写进 `idx_due` 的扫描区间。保留最后一次计划投递时刻，复盘时反而能回答"它本来该在什么时候再试"；死信发生时间看 `updated_at`。

### 6.1 集成测试（`DeadLetterIntegrationTest`，真实 MySQL + 本地 HttpServer，4 例）

| # | 场景 | 断言要点 |
| --- | --- | --- |
| 1 | `max_attempts=3` + 恒 502 | 三轮后 `DEAD`；`attempt_count=3`；`last_error_class=HTTP_5XX`；明细 3 行且每行都有 `error_class`；**认领 WHERE 条件查不到该行**；再 `pollOnce` 不再触达下游（`mockHits` 停在 3） |

```sql
WHERE (status IN ('PENDING','RETRY_WAIT') AND next_attempt_at <= NOW(3))
   OR (status = 'PROCESSING' AND lease_until < NOW(3));
-- 期望 0
```

## 7. 已知限制（显式记录，不留暗坑）

1. **死信只有日志出口。** 没有 webhook、没有 IM 通知，M3 加 Micrometer 指标时不改 `Dispatcher`。在此之前，死信靠日志采集侧配规则，属于"有人看才有用"；
2. **死信不可见（对调用方而言）。** 提交接口只返回 `notification_no`，调用方要知道结果得等 T3.1 的查询接口——本阶段结束时的能力是"死信被正确记录和宣布"，不是"调用方知道它死了"；
3. **重放不做。** 无接口、无批量、无重放前探测。重放必须人工，理由见 §2.2（系统无法区分"拒收"与"处理了但响应丢了"）；
4. **`DEAD` 行仍保留 `headers_enc`/`body_enc`。** 含下游凭证与业务数据，清理策略在 T3.3（成功 24h / 失败 7d）。本阶段不管，意味着死信越积越多时敏感数据的留存期等于"人工处理完的时间"，靠流程兜底；
5. **死信量没有上限保护。** 某个 caller 把地址配错，一夜之间可以产出几十万条 DEAD（每条都要 1 次 HTTP + 1 行主表 + 1 行明细 + 1 行日志）。真正的止血手段是 T2.5 的熔断（按 host 停投）与 T3.3 的背压，本阶段不做；
6. **`error_class` 的粗分组不可扩。** 要按 401/404 细分只能查 `status_code`；如果将来要区分 `HTTP_5XX` 里的网关错误与业务错误，得新增分类维度，改现有 `ERROR_CLASS` 常量会破坏历史数据的分组一致性。
