# T1.3 幂等去重 —— 设计与实现说明

> 对应任务拆解 T1.3（M1）：同 caller 同幂等键重复提交 → 202 + 原单号，表中只有一行。
> 设计依据：设计文档 V2 §3.3（接入时序）、§4.7（幂等键粒度）、§5（接口契约）。

## 1. 本阶段边界

| 做 | 不做（且明确为什么） |
| --- | --- |
| 唯一键判重 + 冲突后返回原单（202 + 当前状态） | 幂等键格式强制校验（§4.7：`<事件类型>:<事件ID>` 只是建议，不做事件类型注册） |
| 冲突后回查的一次语义闭环 | 同键不同 body 的差异检测（见 §7，这是砍掉 body 指纹的代价，明确承认） |
| 更新 T1.1 的 409 语义 | 幂等键 TTL / 清理（通知是长期事实记录，行不删） |

## 2. 设计思路：六个决策点

### 2.1 判重交给唯一键，不做"先查后插"

先查后插永远有窗口：两个并发请求同时 SELECT 都查不到 → 都 INSERT → 两行。所以判重只有一处可信：`UNIQUE (caller_id, idempotency_key)`。应用层的"先查"只能用来优化路径（省一次异常），不能用来保证正确性——本阶段连这个优化都不做，直接 INSERT，冲突走异常分支。

### 2.2 重复提交返回 202，不是 409

**调用方超时重试是正常路径，不是错误路径。** 返回 409 会强制每个接入方写一个"重复"分支，并且让监控里 `4xx` 上升看起来像客户端 bug——实际上那是幂等保护在工作。202 让重试路径与首次提交完全一致：调用方不需要区分"这次是新提交还是幂等命中"。

这也是 T1.1 里刻意先做 409 的原因：让 T1.3 的语义变更有一份清晰的前后对照（T1.1 文档 §2.5 当时就标注了）。

### 2.3 返回原单的**当前状态**，不是硬编码 PENDING

第二次提交时，原单可能已经 `SUCCEEDED` 甚至 `DEAD`。返回真实状态让调用方直接看到进展，而不是收到一个撒谎的 PENDING。契约里 `status` 是**提交那一刻的快照**，不承诺后续不变——这一点写进接入约定（§3.2）。

### 2.4 冲突后 SELECT，不用 `INSERT ... ON DUPLICATE KEY UPDATE`

`ON DUPLICATE KEY UPDATE` 能省一次查询，但代价是：必须写一个无意义的赋值（`id = id`）；MySQL 影响行数语义（1=插入 / 2=更新 / 0=无变化）要靠 `LAST_INSERT_ID()` 技巧才能拿到原单号，读者几乎一定误读。冲突是低频路径（只有重试时发生），多一次 SELECT 没有成本，**清晰度优先**。

而且 `uk_idem (caller_id, idempotency_key)` 本身就是覆盖索引，这个 SELECT 是一次索引点查。

### 2.5 `submit()` 不加 `@Transactional`

三条理由：
1. 单条 INSERT 本身就是原子的，事务不增加任何保证；
2. 冲突后要在**干净会话**里回查——失败语句在 autocommit 会话里不留痕，但如果包了事务，`DuplicateKeyException` 会把事务标记为 rollback-only，后续 SELECT 虽然能读，但整个事务注定回滚，语义绕；
3. 保持"无事务"能阻止以后有人往 `submit()` 里塞第二个写操作（比如顺手写审计），把它变成一个需要事务的用例——真需要时应该显式改造，而不是悄悄变复杂。

### 2.6 冲突发生时，原单一定读得到（并发窗口分析）

InnoDB 唯一索引的插入遇到**未提交**的冲突键时是**等待**（等行锁），不是立即失败；等对方提交后本事务才拿到 duplicate 错误。所以 `DuplicateKeyException` 到达应用层时，对方那一行必然已提交——随后的 SELECT 不会读空。

这不是纸上推导：§6 的 10 并发用例就是照这个前提验证的（10 个请求同键，全部拿到同一个单号）。

**万一 SELECT 真的读空**（理论上不可能，通知行从不删除）：抛 `IllegalStateException` → 500 + error 日志。不静默吞、不编造单号——掩盖一次"数据库里没有但这行又冲突了"的异常，比暴露它危险得多。

## 3. 语义与契约

### 3.1 响应

| 场景 | HTTP | body |
| --- | --- | --- |
| 首次提交 | 202 | `{"notification_no": 30, "status": "PENDING"}` |
| 重复提交（幂等命中） | 202 | `{"notification_no": 30, "status": "<原单当前状态>"}` |
| 同键但不同 caller | 202（新单） | 幂等域是 `(caller_id, key)`，不同 caller 互不影响 |

重复提交的 `status` 可能是 `PENDING` / `RETRY_WAIT` / `PROCESSING` / `SUCCEEDED` / `DEAD` 中任意一个。

### 3.2 接入约定（写进接入文档的三条）

1. **幂等键由调用方生成**，必须唯一标识"一次业务事件"；我方生成就退化成随机数，保护失效；
2. **超时重试必须原样重发同一个键**（包括相同的 body）——本系统不比对内容，只认键；
3. **一条业务事件一个键**。反例：拿订单号当键 → 同一订单的"付款""发货"两条通知被判重复，第二条被静默丢弃，而接口返回 202 —— 最隐蔽的丢消息方式（设计文档 §4.7）。

## 4. 处理流程

```
POST /v1/notifications
  ├─ 鉴权 → 校验（T1.1 不变）
  ├─ INSERT INTO notification ...              ← 唯一键是唯一判重依据
  │    ├─ 成功       → 202 {no, "PENDING"}
  │    └─ DuplicateKeyException
  │         └─ SELECT id, status WHERE caller_id=? AND idempotency_key=?   （此刻原单必已提交）
  │              ├─ 命中 → 202 {原 no, 原当前状态}
  │              └─ 未命中 → IllegalStateException → 500（异常暴露，不掩盖）
```

## 6. 验证方案与结果

| 用例 | 断言 |
| --- | --- |
| 重复提交（串行两次） | 两次都 202，`notification_no` 相同，表中 1 行 |
| 10 线程并发同键 | 10 个响应 `notification_no` 全相同，表中 1 行，`attempt_count` 不因重复提交变化 |
| 重复提交已完成的单 | 响应 `status` = `SUCCEEDED`（原单当前状态，非 PENDING） |
| 不同 caller 同键 | 2 行，各自 202（幂等域隔离） |
| 冲突回查读空（单测 mock） | 抛 `IllegalStateException`，不返回假单号 |

### 6.3 实测结果（2026-10-31）

**自动化测试**：`MYSQL_IT=true mvn test` → **38/38 全绿**（本阶段新增 4 个：串行重复、10 并发同键、已完成单快照、跨 caller 隔离；另有 Service 单测的冲突分支用例）。

**手工端到端**（真实 MySQL + mock 下游 `scripts/mock_downstream.py`，13 次提交 / 同一 target_url）：

| # | 动作 | 响应 | 结果 |
| --- | --- | --- | --- |
| ① | 首次提交 `t1_3:pay_001` | `202 {"notification_no":78,"status":"PENDING"}` | 正常受理 |
| ② | 立即重复提交（原单在途） | `202 {"notification_no":78,"status":"PENDING"}` | 同单号，**非 409** |
| ③ | 投递完成后再重复提交 | `202 {"notification_no":78,"status":"SUCCEEDED"}` | 返回原单真实快照 |
| ④ | 10 线程并发同键 `t1_3:concurrent_001` | 10 次全部 `202 {"notification_no":81}` | 全部同单号 |
| ⑤ | caller `k_crm` 用相同键 | `202 {"notification_no":92}` | 幂等域隔离，新单 |

**落库与投递核对**：

- `notification` 共 3 行（78 / 81 / 92），每行 `attempt_count=1`、`delivery_attempt` 各 1 条 —— 13 次提交只产生 3 次真实投递；
- mock 下游日志恰好 3 条 `POST /cb` —— 重复提交在入口就被拦下，没有打到下游；
- 结论：**重复率 10/13 的入口压力没有泄漏成下游流量**，这是本阶段唯一要证明的事。

**一个容易误判的观察**：单号出现跳号（78 → 81 → 92）。原因是判重走"先 INSERT 撞唯一键"路径，InnoDB 在唯一性检查**之前**就分配了 `auto_increment`，每个被拒的 INSERT 都会消耗一个号。这是预期行为，不是 bug——**单号只需唯一且单调，不需要连续**；反过来，如果要求连号，就只能串行化接入（回到"先查后插"并加锁），那是拿吞吐换美观。M3 的查单接口与运维文档需要说明这一点，避免值班同学看到跳号以为丢单。

**过程中的一处测试代码问题**：`jsonPath("$.notification_no").value(JsonPath.read(...))` 编译期被解析成 `value(Matcher)` 重载（Matcher 比 Object 更具体），运行时 `Integer cannot be cast to Matcher`。已改为显式取数比较——记在这里是因为：**这属于"测试代码自己也可能是错的"，和 T1.2 那次 `/5xx` handler 漏记命中数同类。**

## 7. 已知限制

1. **同键不同 body 无法识别**：本阶段只认键不比对内容，同一键提交不同 body 会静默返回原单。这是我砍掉 `body_fingerprint` 体系的直接代价（见《过度设计对比分析》第 1 项）——判据是：**幂等键的语义责任在调用方，系统只提供机制**。若要补，最小做法是对 `body` 取 SHA-256 存一列，冲突时比对不一致返回 409；翻案条件是"出现第一起同键不同内容的真实事故"；
2. **幂等键无 TTL**：唯一索引长期占用。通知行是长期事实记录（归档只清 body 不清行），所以键的有效期等于行寿命——这是选择"通知即记录"的自然结果，不是遗漏；
3. **重复提交不计入任何指标**：本阶段没有指标（M3 才有）。M3 时应单独记 `ingest_duplicate_total`——重复率高说明某个调用方的重试策略有问题，这是接入质量信号，不是系统错误。
