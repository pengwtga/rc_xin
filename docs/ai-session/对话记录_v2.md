## Q5｜轮询、超时、批量、重试、worker 这几个数字怎么定

**我（提问）**

> 轮训时间、一条通知的最大消耗时间、批量处理条数、一条通知最大重试次数、worker数，这些数字怎么定？从什么角度来设置数值？

**AI（最终回答）**

产出 `API通知系统_参数定值依据.md`。核心回答：**这五个数字没有一个是独立"选"出来的，先分清参数类型，再从对应角度倒推。**

| 参数      | 值                   | 推导链                                                                              |
| ------- | ------------------- | -------------------------------------------------------------------------------- |
| 轮询间隔    | 500ms               | **体验型**：送达 p99<5s 里分约 10% 给队列等待；100ms~2s 区间内"错了也无所谓"，数量级对即可                      |
| HTTP 超时 | 总 15s / 连接 3s       | **防御型**：按对端 **P99 不按均值**，15×P99 覆盖 GC/慢查询尾部；worker 是稀缺资源，**宁可误杀重试，不让 worker 挂着** |
| 最长处理时间  | 租约 60s              | **耦合型，没有自由度**：`lease = 2×timeout + 抖动余量`；太短双投率由比值决定，太长崩溃恢复延迟等于 lease             |
| 批量条数    | min(100, 空闲 worker) | **耦合型**：硬上界 ≤ 空闲 worker，需求上界 = 有效 QPS × 轮询间隔 ≈ 86 条/周期                           |
| 最大重试次数  | 10 次                | **业务型**：先定补偿窗口（3~4 小时），再用退避曲线倒推——**次数是"窗口 ÷ 曲线"的解**；cap=1h 把控制权在小时级交还人工          |

#### 三个最值得记住的判断

1. **参数间的不等式比绝对值重要**：`lease > timeout`、`batchSize ≤ 空闲 worker`、`次数×退避 ≥ 补偿窗口`，违反即事故；绝对值错了常常无感。所以用启动断言锁死关系；
2. **worker 数按故障态设**：Little's Law 正常态只要 34 并发，200 覆盖的是"下游整体慢 5 倍"；"全部卡 15s"不该用 worker 兜底，那是熔断的职责；
3. **精调价值分级**：lease 比值、batch 约束、重试窗口值得精调；轮询间隔和 worker 绝对值不值得——**为低价值参数写长篇论证，和为想象需求建机制是同一种错误**。

## Q6｜为什么不定义少量 worker，让单 worker 做内部并发

**我（提问）**

> 为什么不定义少量worker，让单worker做内部并发

**AI（最终回答）**

已作为 **§3.5.1 常见疑问**补进《参数定值依据》，紧跟 worker 数推导之后。

1. **并发上限不因实现而变**：需求推出的是"同时在途 ≤ 200"，少量 worker + 内部并发只是把上限从"线程数"挪到"in-flight 计数器"，比较的是实现模型而非上限；
2. **五个不选的理由**：省下的 200MB 不值钱（JDK HttpClient 内部本就是异步 selector，线程只是等待）／`batchSize ≤ 空闲 worker` 不变式在线程模型下由 JVM 免费维护，事件模型要自己实现计数和背压／卡住的投递 `jstack` 可见，回调永续在栈里不可见，与"单号一查到底"的运维承诺冲突／对 DB 和对端的真实消耗一点不少／换 Java 21 虚拟线程即可零改码拿到同等资源效率；
3. **翻案条件**：在途 > 2000 或内存成为约束——第一步也是换虚拟线程，而不是重写成事件模型；事件模型的真正主场（单机数万连接）属于 V2 演进量级。

一句话：**并发上限是需求决定的，实现只决定这个上限由谁来数——JVM 线程池替我数，比我自己写计数器可靠。**

## Q10｜为什么要两张表？一张表也能实现功能吧

**我（提问）**

> 有个问题，数据库模型这一块为什么要两张表？一张表也能实现功能吧

**AI（最终回答）**

能。M1 的功能单表完全跑得起来——`notification` 里已经有 `attempt_count`、`last_status_code`、`last_error_class`。所以问题不是"能不能"，而是"单表要放下什么，就得先放弃什么"。

真正把单表逼到墙角的是三个需求撞在一起。

#### 1 唯一键的粒度和明细的粒度直接冲突

- 幂等要求**一条通知只有一行**：`UNIQUE (caller_id, idempotency_key)`；
- 逐次明细要求**一次尝试一行**：第 1 次 500、第 2 次超时、第 3 次成功都要能看到。

同一张表硬塞只有三条路，都有代价：

| 单表方案                                   | 代价                                                 |
| -------------------------------------- | -------------------------------------------------- |
| 同表多行，唯一键改成 `(caller, key, attempt_no)` | **幂等直接失效**：重复提交无法靠唯一键判重，退化成"先 SELECT 再 INSERT"的竞态  |
| 单行 + `attempts` JSON 列                 | 行越写越宽、每次 UPDATE 整列重写；没法按 `error_class` 建索引；并发下整列覆盖 |
| 单行 + 只留 `last_*`                       | 能演示，但丢掉"第几次、耗时多少、对方返回了什么"                          |

#### 2 读写模式不同

`notification` 是队列 + 状态机：高频 UPDATE、被 `idx_due`/`idx_lease` 反复扫描，行必须窄。`delivery_attempt` 是账本：只 INSERT、单点查。合表意味着每次追加明细都落在热点行上。

#### 3 有一个场景单表在语义上做不到

投递完成时租约已被新 worker 接管：状态行写"别的新结果"是错的；什么都不写，这次尝试就**没有任何记录**，而它恰恰是"下游可能收到两次"的证据。只能靠第二张表——**状态带守卫地写，事实无条件地写**。

#### 判断与翻案条件

两张表不是"拆分过度"，而是两个模型本来就是两件事：**状态是当前值（一行），尝试是事件流（多行）**。判据是：**有没有一个真实的读者会去读这张表；没有读者的表就是负担。** 如果砍掉"查单看每一轮""按错误分类聚合""投递争议留证"三件事，我会毫不犹豫删掉明细表。

## Q12｜`leaseOwner = 实例ID/轮次token` 这点我不太明白

**我（提问）**

> leaseOwner = 实例ID/轮次token 这点我不太明台

**AI（最终回答）**

核心就一句：**`lease_owner` 标记的不是"这台机器"，而是"这一次认领"。**

它在代码里只干两件事：

```java
String roundToken = instanceId + "/" + 随机8位;   // 每轮一个：inst-A/r1、inst-A/r2…
claims.claim(roundToken, batch, 60);             // ① 认领
// 同事务内 SELECT ... WHERE lease_owner = roundToken AND status='PROCESSING'
claims.markSucceeded(id, roundToken, 200);       // ② 守卫
```

① 是**回读**：`UPDATE` 不返回被改的行，只能按自己刚写进去的标记把这一批捞出来；② 是**守卫**：投递完写回结果时，确认"我写的还是我认领的那次"。

#### 为什么回读不能用裸实例 ID

`@Scheduled` 每 500ms 触发一次，一轮认领后把任务丢进线程池就立刻返回——**下一轮开始执行时，上一轮的行还在 `PROCESSING`、还在投递中**。慢请求 12s，意味着任何时刻同一实例手里有二十几轮的行同时在途。这时 `SELECT WHERE lease_owner='inst-A' AND status='PROCESSING'` 捞回的是这个实例历史上所有在途行，不只是本轮刚认领的——#42 被投第二次。

注意一个容易混淆的点：**认领本身不会重复**（第二轮认领不到 #42，因为它已 `PROCESSING` 且租约没过期）。重复只发生在"认领之后的回读"，因为回读条件只有"owner + PROCESSING"，缺了"哪一轮"这个维度。token 补的就是这个维度。

#### 为什么不加一列 `claim_batch`

语义上 `lease_owner` 本来就是"谁持有"，token 只是把"谁"细化到"谁的第几轮"，同一个概念的两个精度。单独加一列意味着认领 SQL 多写一个字段、DDL 多一列、读者多理解一个概念。

另外两个备选也想过：**内存里存本轮 id 列表**（可行，但是应用态，重启就没了，DB 里也查不到"这一轮捞了哪些行"）；**`UPDATE ... RETURNING`**（PostgreSQL 有，MySQL 没有）。

#### 一个反直觉的好处

守卫比 token 而不是比实例，看起来"更细了会不会更容易失败"，实际是**更严格**：某条投递因 GC 停顿超过 60s 租约、被别的实例抢走，旧轮次写回时影响 0 行，结果被正确丢弃。如果守卫比的是实例 ID，**同实例的旧轮次会反过来覆盖新状态**，那才是真正的隐患。

#### 为什么"没有恢复代码"

| ----------------------------------------------------------- | ------------------------------------------------- |
| `staleResults` 累计计数并写进守卫失败的 WARN                            | 守卫失败是"租约曾被接管"的唯一直接信号，原来只有一行无上下文的 WARN             |

## Q22｜继续 T2.4

**我（提问）**

**AI（最终回答）**

T2.4 完成，98/98 全绿（T2.3 是 72），未提交。

#### 校验分两层，这是第一个判断

设计文档写"解析后校验实际 IP"，但没回答**在哪一刻解析**。受理期解析能让调用方立刻拿到 422，代价是 DNS 抖动变成调用方的 422（"你填错了"其实是"我们查不了"），且受理 p99 被 DNS 长尾拖住；投递期解析则受理路径零外部依赖，但恶意目标会先被受理。所以两层都留：受理期只判**不碰网络**的东西（协议、host 形态、IP 字面量），投递期重新解析、逐 IP 校验。`http://localhost/cb` 受理期放行、投递期解析出 127.0.0.1 才拦下——测试专门钉了这条。

#### JDK 的便利方法漏了四类，每一类都是现成攻击面

`isSiteLocalAddress` 看着够用，实测不够：

| 盲区                  | 例子                                 | 为什么漏                        |
| ------------------- | ---------------------------------- | --------------------------- |
| CGNAT `100.64/10`   | **阿里云 metadata `100.100.100.200`** | 只认 RFC1918 三段               |
| IPv6 ULA `fc00::/7` | `[fc00::1]`                        | 只认已废弃的 `fec0::/10`          |
| IPv4-mapped IPv6    | `::ffff:127.0.0.1`                 | 长度 16 走不到 IPv4 判定           |
| 保留段                 | `0.0.0.0`、`240/4`                  | `isAnyLocalAddress` 只覆盖单个地址 |

阿里云那条最值钱：只测 AWS 的 `169.254.169.254` 会以为防住了。判定原则是 **fail closed**——解析出多个 IP，任一落入禁止段就整体拒绝。

#### 三个实现细节

- **`SSRF_BLOCKED` 不是网络故障**：被拦时 `statusCode=null`，若按"网络层失败一律 RETRYABLE"，这条任务会拿 10 次预算重试一个被禁止的地址。单开一条判 PERMANENT；
- **校验在解密之前**：被拒的目标连凭证都不该被解出来；
- **加密格式 `ver(1)|field(1)|IV(12)|ciphertext+tag(16)`**：`field` 作 AAD（否则能把 headers 密文挪进 body 列解出结果）；IV 每条随机（GCM 下 IV 重会泄露明文异或值）；Header JSON 用私有 ObjectMapper（内部存储格式不该随对外契约变）。明文 codec 直接删掉——留一个"切回明文"的开关，早晚有人在故障时切过去。

#### 一个必须承认的妥协

DNS rebinding 只缓解、没闭环：JDK `HttpClient` 没有自定义解析器或指定连接 IP 的入口。本版把窗口从"落库到投递"（可能几小时）压到"校验到连接"（毫秒级）。要利用它，攻击者得控 DNS、极短 TTL、恰在毫秒内切换——**而能控 DNS 的攻击者通常已经能直接改 `target_url`**，那时靠的是 API Key 鉴权。触发条件：接入外部不可信 caller 或出现真实 rebinding 事件，就换 Apache HttpClient 补上。

回归暴露的旧问题：集成测试造数据时把 `headers_enc` 直接写成明文 JSON，换 AES 后解密失败（日志 `不支持的密文版本: 123`，123 是 `{`）。改了 5 个用例：造数据一律走真实 codec，别绕过加密边界。

## Q26｜重放为什么不直接投递？

**我（提问）**

> 重放为什么不直接投递？

**AI（最终回答）**

因为投递在本系统里**只有一条路径**，而这条路径上挂着八件事。重放如果直接调下游，要么把这八件事复制一遍（第二套语义，两边迟早漂移），要么绕过它们（那就等于悄悄降级了系统的核心保证）。

**1｜绕过的保证谁来补？** 一次投递要过：租约（防两个实例同时投）、退避（Retry-After）、端点熔断与并发配额（T2.5）、投递期 SSRF 复检（T2.4）、错误三级分类、死信宣布、明细落库、失败计数上报。HTTP 线程直接调，这些一个都没有——刚恢复的供应商会被几十个重放请求瞬间打爆，恰恰是 T2.5 花整轮做的防护；指向内网的 URL 也不会被拦。

**2｜状态机出现两个写入者。** `attempt_no` 有唯一键、`attempt_count` 要自增、终态由 `markSucceeded`/`markDead` 宣布。HTTP 线程去写成功态，就得处理"和正在跑的 worker 撞同一行"——而它现在能安全，靠的是 `SKIP LOCKED` + 租约这套只有引擎里才有的上下文。现在重放唯一写的字段是 `status/next_attempt_at/max_attempts`，**不碰 `attempt_count`、不插明细**。

**3｜接口时延等于一次出站超时。** 同步投递意味着要等满 `httpTimeout`，期间占着 Tomcat 线程。重放是运营动作，典型场景是"供应商恢复了我批量点一下"——最不该悬着的接口就是它。

**4｜崩溃窗口。** 先落盘意图再异步投递，进程任何时候崩掉，意图都还在库里。反过来"调完再记账"，若下游收到了、进程却在记账前挂了，这次投递的事实就永久丢失。顺带，审计与迁移能做成同事务 fail-closed，也只有事务里不含远程调用时才成立。

**5｜语义上本来就不是一回事。** 接口表达的是"**我允许你再试一次**"，不是"**现在就试**"。所以幂等由守卫保证；投递节奏归引擎，熔断打开时这批就等着；重放后的这次尝试在 `delivery_attempt` 里和自动重试长得一模一样（序号连续），T3.1 的时间线才不会断。

**代价**（已写进文档）：重放不是"点完即成功"，要等下一轮轮询；`PENDING + attempt_count>0` 成为合法组合；队列有积压时重放的单排在后面，管理意图不插队。

**什么时候"直接投递"才是对的？** 只有一种：重放前的**探活**。那个动作语义是"我只想验证端点通了没"，不产生业务动作，所以必须独立于投递路径，还得加"探测请求不带业务字段"的约束——两件事不该混在一个接口里。

一句话口径：**重放只改状态、不执行投递；投递永远是引擎的独占职责。**

#### 指标（12 个 `notify_*`）的四个决策

- **抓取时绝不查库**：Gauge 是 scrape 时求值的，取值函数里写 SQL，一次 DB 抖动就让整个 `/actuator/prometheus` 变 500——**监控在最需要它的时刻丢掉全部指标**。改成 `QueueSampler` 每 10s 刷快照，Gauge 只读内存，采样失败保留上次值；
- **"最老任务年龄"用 `next_attempt_at`，不能用 `created_at`**：这是本轮最容易写错、后果最大的一处。用创建时间，一条正在 1 小时后重试的单（指数退避最长 3.5h，这是**正常**的）会被算成"最老 30 小时"，阈值一过就把整个受理入口关掉；
- **计数封顶**：`COUNT(*) FROM (SELECT 1 … LIMIT maxPending+1)`。监控只需要"有没有越过阈值"，封顶让这条查询在积压 500 万时仍只扫 10 万行。封顶值必须严格大于阈值，否则背压永不触发且没有任何报错；
- **不给"成功率"建 Gauge**：成功率必须选窗口，而窗口是查询时的事。只存 `success/retryable/permanent` 原始计数，`rate()` 交给 PromQL。`endpoint` tag 用 MeterFilter 把第 201 个之后折成 `other`——值来自调用方填的 URL，是无界基数。

#### 背压与归档

背压放在 `submit` 第一行：先看年龄（`>=`）再看条数（`>`）；**fail-open**；**只挡新提交**，查询与重放照常——事故时运维恰恰需要这两个。503 必须带 `Retry-After`，不告诉调用方等多久，他只能立刻重试，而立刻重试正是把背压变成雪崩的方式。

## Q30｜这个问题（身份头没注入）有什么影响吗

**我（提问）**

> 这个问题有什么影响吗

**AI（最终回答）**

有影响，但要分场景看严重程度。

**1｜对"下游去重"这条契约的影响——取决于调用方配不配合**

- 调用方自己在 `headers` 里带了业务幂等键，透传后下游能拿到，去重照常成立——**这个场景零影响**；
- 调用方没带（而这恰恰是最容易发生的：接入文档没强制要求，代码也不校验），双投窗口发生时下游收到两个**内容完全相同、但没有任何稳定标识**的请求。下游唯一能做的去重是"整个请求体哈希比对"，在重试、字段顺序、时间戳稍有不一致时就失效——等于退回到"没有去重契约"；
- 也就是说：**语义上承诺 at-least-once，机制上却把"下游可去重"的责任悬空了**。最坏情况是重复扣款/重复发券这类事故，而系统层面看不到任何异常。

**2｜对账与排查**：下游收到重复请求想反馈"你重复发了单 X"，说不出来——它根本不知道单号。归档后（成功 24h 清载荷）连"两次请求内容是否一致"都查不到，争议没法复盘。

**3｜对校验结论**：这条和"429"是同一类错误但方向相反——429 是"承诺了不存在的拒绝行为"，这条是"把一个没做的机制写成已强制执行的契约"。都属于评审时最伤可信度的偏差。

**4｜修复成本很低**：`HttpDeliverer.deliver()` 里加两行 header 注入（单号本来就在 `Dispatcher` 手里），加一个集成测试断言，20 分钟内含验证。建议现在就补，而不是留在文档里当已知缺口长期挂着。
