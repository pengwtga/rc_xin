# AI 会话记录：哪些建议被采纳、哪些被否掉

这份记录只挑**决策点上有分歧**的段落。AI 一次就说对的地方（比如"用 AES-GCM 而不是自研加密"）
没有归档价值；有价值的是"AI 给了方案 A，判断之后改成 B，并写下了为什么"。

每条按「AI 建议 → 我的判断 → 最终决定（落到哪）」组织。原始提问见 `questions.md`。

---

## 1. 注释的粒度：从"方法级"到"每一列为什么要存在"

- **AI 建议**：给 Java `record` 的组件加 `/** ... */`，说明字段含义。
- **我的判断**：含义在 `record` 里已经有了（字段名基本自解释），真正费时间的是**打开 DDL 时不知道
  这个索引是为哪条查询建的**、`lease_owner` 里到底存的是什么。注释要减少"翻来翻去"的成本，
  不是把字段名翻译一遍。
- **最终决定**：DDL 每一列写"存什么 + 谁写 + 什么时候为空"；每个索引写"为哪条查询服务"；
  `lease_owner` 从"租约持有者"改成"实例ID/轮次token，标记哪一次认领"——因为它是守卫键，
  不只是标记。Java 侧 `BackoffPolicy` 补"无状态无锁"和 `delayMs` 恒 ≥ `MIN_DELAY_MS`。
  落到 `V1__init.sql` 与 `BackoffPolicy`。

## 2. 最老任务年龄：用 `created_at` 还是 `next_attempt_at`

- **AI 建议**（第一版）：背压要看"最老的待投任务多老了"，用 `created_at` 最直观。
- **我的判断**：错得会很难受。一条正在做 1 小时退避的单（指数退避 cap 3.5h，这是**正常**行为）
  会被算成"最老 30 小时"，阈值一过就把整个受理入口关掉——**监控指标把系统自己打挂**。
- **最终决定**：用 `next_attempt_at <= NOW()` 且取最小值，语义是"已经到期但还没被投递的最老一条"。
  写了回归钉子 `BackpressureIntegrationTest.退避中的老任务不触发背压`。
  落到 `QueueSampler.OLDEST_SQL` + `docs/T3.3-指标背压与归档.md`。

## 3. 重放为什么不直接投递

- **我的提问**：「重放为什么不直接投递？」
- **AI 的判断**（这次是我同意的）：投递在本系统里只有一条路径，那条路径上挂着八件事——
  租约、退避、端点熔断与配额、投递期 SSRF 复检、错误分类、死信宣布、明细落库、失败计数。
  同步投递要么复制一遍（第二套语义，两边迟早漂移），要么绕过它们（悄悄降级核心保证）。
- **最终决定**：重放只改状态（`DEAD → PENDING` + 追加预算），投递永远是引擎的独占职责。
  接口时延从"一次出站超时"降到 O(1) 的 UPDATE；崩溃窗口从"投递完再记账"变成"先落意图再投"。
  代价写进文档：`PENDING + attempt_count>0` 成为合法组合。
  落到 `ReplayService` + `docs/T3.2-人工重放.md`。

## 4. 演示脚本用"真实失败流量"造积压，得出过假结论

- **AI 建议**（第一版）：背压演示就用一批打向 502 的请求，等它们堆在 `RETRY_WAIT` 里。
- **我的判断**：跑出来 mock 收了 20 次、库里只有 8 条待投——两个数对不上，看起来像"丢单"。
  实际是读到的是**在途状态**：那 12 条正在被投递（`PROCESSING`），不在 `RETRY_WAIT`。
  更糟的是这个演示会随"恰好正在重试"而抖动，每次跑出的数字都不一样。
- **最终决定**：先做隔离探针证明路径无误（关熔断 40 请求对 40 明细），再把演示改成
  直接插两条 `next_attempt_at` 在未来的 `PENDING`——不受投递时序影响，且完全符合 backlog 口径
  （`PENDING + RETRY_WAIT`，不看时间）。
  落到 `scripts/observability_demo.sh` + `docs/T3.3-指标背压与归档.md`。

## 5. 跳过延迟不能取 0

- **AI 建议**（测试里）：把 `RETRY_WAIT` 的行统一快进到"现在"，让重试立刻发生，测试跑得快。
- **我的判断**：统一快进会让熔断那一行的 84 条任务抢走全部认领名额，健康端点被饿死，
  测试失败的原因看起来是"隔离失效"，其实是测试自己造的。
- **最终决定**：按 URL 分开快进；并把这条经验变成**启动断言**——`skip-delay-seconds` 必须 > 0，
  否则"认领 → 退还 → 立刻再认领"是一个不烧预算的死循环，CPU 打满而队列不动。
  落到 `StartupGuard.validateCircuit` + `CircuitBreakerIntegrationTest` 的饿死回归用例。

## 6. 指标 Gauge 里写 SQL（被否）

- **AI 建议**（第一版）：`Gauge.builder("notify.queue.backlog", jdbc, ...)` 直接查库，代码最短。
- **我的判断**：Gauge 是 scrape 时求值的。一次 DB 抖动就让整个 `/actuator/prometheus` 返回 500——
  监控在最需要它的时刻丢掉全部指标。而且 scrape 频率 × 实例数会放大成每分钟几十次聚合查询。
- **最终决定**：`QueueSampler` 每 10s 查一次、缓存成快照，Gauge 只读内存原子量；
  采样失败保留上次值（宁可用 20s 前的数据，也不报错）。计数还做了封顶
  （`SELECT COUNT(*) FROM (… LIMIT maxPending+1)`），积压 500 万时仍只扫 10 万行。
  落到 `QueueSampler` / `NotifyMetrics`。

## 7. 集成测试的 `MYSQL_IT` 门禁（被否）

- **AI 建议**（早期）：集成测试连本机 MySQL，用一个环境变量门禁，没有库时自动跳过，
  这样 `mvn test` 在谁的机器上都是绿的。
- **我的判断**：这种绿是假的。干净机器上 `mvn verify` 全绿，但 40 多个集成用例一个都没跑，
  而 CI 上没人会去数用例数——比红更危险。
- **最终决定**：Testcontainers 起真实 MySQL，删掉门禁，`mvn verify` 报 166 个用例、
  0 skipped；容器全 JVM 共用一个（12 个测试类的属性组合会各起一个容器）。
  代价（跑测试需要 Docker）写进 README，不用门禁藏起来。
  落到 `SharedMySql` / `AbstractIntegrationTest` / `docs/T4-交付.md` §1。

## 8. 压测该打一个端点还是十二个

- **AI 建议**（第一版）：压测就打一个下游，最简单。
- **我的判断**：跑出"投递只消化 57/s、积压 6930"，第一反应是投递引擎不行；但算一下
  `max-concurrent-per-endpoint=16` × 每 500ms 一轮 ≈ 32/s 级，就知道这是**端点许可**
  在卡，不是引擎。设计文档的前提是 150 QPS 摊在 ~12 个活跃端点上。
- **最终决定**：压测改成 12 个端点（复现设计前提），同时把单端点那次结果**保留下来**
  作为已知边界写进 `docs/T4-交付.md` §2.5，并给出旋钮
  （`max-concurrent-per-endpoint ≥ QPS × 平均延迟`）与两条不能同时要的路（退还 vs 排队）。
  落到 `scripts/loadtest.sh` 的 `--endpoints`。

## 附：一次没被采纳、但记下来的建议

| AI 建议 | 为什么没采纳 | 什么条件下会翻案 |
| --- | --- | --- |
| 用 Redis 分布式锁保证"同一单不会被两个实例投" | 锁会引入新的单点与租约问题；`SKIP LOCKED` + 租约已经保证"同一时刻只有一个 worker 持有"，剩下的重复是 at-least-once 的固有部分 | 需要 exactly-once 语义（实际上不可能只靠锁拿到） |
| 幂等去重表 + 请求指纹，做"伪 exactly-once" | 只能防重复提交，防不了重复投递；多一张表就多一次写、多一个不一致源 | 调用方明确要求"提交阶段强幂等 + 可撤销" |
| 状态流水表（每次状态变更插一行） | 状态变更都对应一次投递，流水就是明细的冗余；每单多 3 次写（实测已经是 4 写） | 需要按状态轨迹做分析/审计，且能接受写放大 |
| 给"投递成功率"建 Gauge | 成功率必须选窗口，窗口是查询时的事；存原始计数让 `rate()` 算，换窗口不用发版 | 无 |
