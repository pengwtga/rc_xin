#### 1｜replay 怎么操作，怎么通知业务方

**replay 的本质不是技术操作，而是责任移交。** 一条 `DEAD` 有两种可能：供应商明确拒收（重放必再失败），或供应商已处理但响应超时（重放会造成重复业务动作）。系统无法区分，只有人知道业务上能否承受重复。所以自动重放是危险动作，不是优化项。

**操作（加上必要的四个约束）**

```sql
UPDATE notification
SET status='PENDING', replay_epoch = replay_epoch + 1,
    max_attempts = max_attempts + 10
WHERE notification_no = ? AND status = 'DEAD'
```

1. **状态守卫**：`AND status='DEAD'`，重复点击影响 0 行，天然幂等，不需要分布式锁。
2. **必须支持批量**。只做单条是操作失误——凭证过期 1 小时会积压几千条 DEAD，人不可能一条条点。所以要 `POST /replay-batch`（按 caller + error_class + 时间窗）。
3. **批量前要前置体检**：先探一条。没修好就重放 3000 条 = 把 3000 份重试预算再烧一遍。
4. **批量要摊平**：3000 条同时变 PENDING 涌向同一 host，就是把刚恢复的供应商再打挂一次。按 `now + i×200ms` 摊到 10 分钟。

> 顺带一个会**真实导致故障的坑**：不能把 `attempt_count` 归零重放，否则 `delivery_attempt` 的 `(notification_id, attempt_no)` 唯一键直接冲突。已改为保留单调计数 + 新增 `replay_epoch`，唯一键变成三元组。这也让 attempt 记录能按“第几轮”分组看。

**怎么通知业务方**

按错误类型**路由**，不广播（广播给所有人 = 没人负责）：

| error_class   | 该通知谁                    | 通道            |
| ------------- | ----------------------- | ------------- |
| 400/422 参数错   | **业务方**（他们的 bug，要改代码重发） | 失败清单 API + 日报 |
| 401/403 凭证失效  | **接口负责人/运维**（改一个配置救全部）  | 立即告警          |
| 5xx/超时超预算     | **业务方**（决定业务是否降级）       | 失败清单 API + 日报 |
| DNS/TLS、熔断、积压 | 运维                      | 立即告警          |

给业务方用**拉取式游标**（`GET /v1/notifications?status=DEAD&since=cursor`），不用 webhook——webhook 要求每个业务系统额外实现端点，还引入“通知系统的通知失败怎么办”的递归问题。边界重申：**我们负责让人知道失败，业务方负责决定业务上怎么办。**

#### 2｜SKIP LOCKED + 租约是什么

分五步，缺一步设计就不成立：

**① 为什么不能裸 SELECT**
`SELECT ... WHERE status='PENDING' LIMIT 100`，两个实例拿到同一批 100 条 → 全部重复。必须“取到即占住”。

**② 为什么不是普通 FOR UPDATE**
`FOR UPDATE` 会**阻塞等待**：实例 B 排队等 A 提交。实例越多排队越重，整张表退化成单通道。它解决“不重复”，但代价是吞吐。`SKIP LOCKED` 则是——碰到已锁定的行**不等待、直接跳过**，去取下一批。于是每个实例拿到的行集合互不相交，且零等待。多实例扩容退化成“加机器”。

**③ 但 SKIP LOCKED 只在事务内有效**
事务一提交，行锁就释放。所以必须**在同一事务里把 status 改成 PROCESSING**——“占住”这件事要从锁落到数据上，才跨事务有效。

**④ 可状态标记带来新问题 → 租约**
`status=PROCESSING` 之后，worker 被 kill / OOM / 卡网络黑洞，这行就**永远停在 PROCESSING**。静默卡死比失败更糟，因为它不告警。所以给“占有”加有效期：`lease_owner`（谁占的）+ `lease_until`（占到什么时候 = 认领时刻 + 60s）。

**⑤ 完整语义只体现在一个条件里**

```sql
WHERE (status IN ('PENDING','RETRY_WAIT') AND next_attempt_at <= NOW(3))
   OR (status = 'PROCESSING' AND lease_until < NOW(3))   -- ← 崩溃回收
```

第二条 `OR` 不是特殊恢复路径，只是“**租约过期的任务，和到期任务一样可认领**”。整个崩溃恢复机制就这一行，没有清理任务、没有补偿脚本。

```
t=0    A 认领 #42，lease_until=t+60
t=3    A 投递中，进程被 kill
t=60   租约到期，状态仍 PROCESSING，没人管
t=61   B 命中 OR 分支，认领 #42，重投
```

**结论：租约保证“不丢”，不保证“不重”。** A 在“请求已发出、结果未落库”之间崩溃，这个窗口物理上无法消除——这正是语义必须是 at-least-once 的根本原因。

**五条会出事故的实现约束**：租约必须 > HTTP 总超时（否则双投率暴涨，启动时断言）；`attempt_count` 在认领时自增而非完成后（否则毒消息无限循环）；**认领事务里绝不放 HTTP 调用**（否则一条 15s 请求占着 DB 连接，把 HTTP 慢变成数据库不可用）；租约时间用 DB `NOW()` 不用应用时钟（时钟漂移是最隐蔽的重复源）；`batchSize ≤ 空闲 worker 数`（认领 100 条只有 30 个空闲 worker，剩下 70 条等租约过期被重领——**自己制造重复**）。

#### 3｜150~170 QPS 怎么定出来的

**先说清：这是假设，不是测量。** 但原文档的算法是错的——我写“日 100 万 × 3 倍系数 = 100 QPS”，可 11.6 × 3 = 35，根本得不出 100。已改为按**“最坏 10 分钟”**推导：

| 步骤           | 计算                        |
| ------------ | ------------------------- |
| 日均           | 100 万/天 → 11.6 QPS        |
| 时段集中         | 70% 压 10 小时 → 19.4 QPS    |
| **最坏 10 分钟** | 10% 压 600 秒 → **167 QPS** |
| 设计点          | **150 QPS**，校验按 200 做     |

均值乘一个系数最容易骗自己；通知类尖峰由**业务事件**驱动（一次推送、一次开抢），不是均匀日间系数。

**但真正重要的不是这个数字，而是“猜错了会不会改变结论”**——所以补了敏感性分析：

| 日量        | 峰值 QPS   | DB 余量   | 结论        |
| --------- | -------- | ------- | --------- |
| 30 万      | ~50      | 27×     | 明显够       |
| **100 万** | **~170** | **~9×** | **V0 成立** |
| 300 万     | ~500     | 3×      | 启动 V1     |
| 1000 万    | ~1700    | 1×      | 必须上 MQ    |

**估算差 3 倍内选型完全不变，要到 10 倍才翻转。** 这比“我算出了 150 QPS”有说服力得多。

#### 4｜剩下 6 条的标准是什么

你抓到的是**逻辑漏洞**：3 条标准只能解释 12 条里的 6 条（1/6/8、2/12、9），另外 6 条（3/4/5/7/10/11）没有归属。原因是那 3 条尺子只覆盖了“成本侧”，漏了“边界侧”和“替代侧”。

已扩成 **6 把尺子**，并区分硬约束与软权衡：

**硬约束（违反即不成立，不参与权衡）**

- **A｜归属**：这件事本来是不是我的职责？越界能力无论做得多好都是负债——它与真正的责任方产生两套并存语义，出问题时双方都不认账。
- **B｜净故障面**：新增的失败模式是否多于它消除的？每个新组件都带新故障（分区、版本、脑裂、配置漂移）。“消除 1 类、引入 3 类”永远不划算。

**软权衡（需与收益比较，条件变化允许翻案）**

- **C｜必要性**：解决的是已发生的问题，还是想象中的问题？判据不是“将来会不会”，而是“现在有没有观测数据”。
- **D｜替代性**：同一目的有没有更便宜的等价手段？多数“高级方案”想买的效果，能用契约或数据模型换来。
- **E｜位置**：复杂度加在我可控的代码里，还是运行时不确定性上？
- **F｜可解释性**：出问题能否归因、测试、预测？

覆盖核对（写在文档里了）：

| 尺子     | 拦下哪几条                      |
| ------ | -------------------------- |
| A 归属   | 5 模板引擎、10 供应商评级、11 Saga 补偿 |
| B 净故障面 | 1、2、3、4、7、9、10、12          |

## Q3｜设计要求文档中的两张表有些字段没有写注释，把字段注释补完整

**我（提问）**

**AI（最终回答）**

注释已补全。**notification 表 21 列、delivery_attempt 表 9 列全部有 COMMENT**，用 `information_schema` 校验过没有空注释。

#### 补的不只是注释

既然要动，就把三处缺失一起补了：

- **表级 COMMENT**：`notification` 标注“本身即队列：SKIP LOCKED 认领 + 租约实现可见性超时”，让看表结构的人立刻知道这张表的角色。
- **索引级 COMMENT**：说明每个索引服务哪个查询路径，避免后来人只按经验加索引。
- **`PRIMARY KEY` 从行内移到表约束**——这是必须的，否则没法给索引加 COMMENT。

注释内容都落到“**为什么是这个值**”，而非复述字段名。例如 `lease_until` 写的是“= 认领时刻 + 60s，过期即视为持有者已崩溃”，`attempt_count` 写的是“在**认领时**自增（非完成后）”——这两条正是 D4 里最容易写错的地方，把坑写进注释里比写在文档里更容易被看到。

#### 实际运行后才发现两个问题

DDL 是要被评审实际执行的，所以我启动了一个临时 MySQL 8.0.46 容器跑了一遍，结果：

1. **`status` 缺 DEFAULT** → 报 `Field 'status' doesn't have a default value`。任何 INSERT 都必须显式带状态，接入层漏一个字段就报错。已加 `DEFAULT 'PENDING'`。
2. **`LIMIT @batch` 是语法错误** —— MySQL 的 `LIMIT` 不接受用户变量。文档里写 `LIMIT :batchSize` 只在 JDBC/MyBatis 绑定参数时成立，我在文档里补了这句说明，否则别人照抄到 SQL 客户端会卡住。

顺带验证了 D4 那段最容易出事的认领 SQL：用派生表包一层 `FOR UPDATE SKIP LOCKED`，**不会**撞 MySQL 的 1093 错误（不能 UPDATE 同一张表的子查询）。实测行为符合设计——第一轮 `attempt=1 / worker-1`，把 `lease_until` 改到过去后，第二轮 `worker-2` 接管、`attempt=2`。

这条实测记录我写进了文档 3.3 节末尾。面试场景下它的价值比注释本身大：**“我跑过”比“我设计过”可信得多**，而且发现的问题正好佐证了 D4 里那几条约束不是凭空推的。

## Q4｜notification表的ordering_key我不了解是什…

**我（提问）**

> notification表的ordering_key我不了解是什么意思，注释我也没看懂

**AI（最终回答）**

没看懂是**我的问题，不是你的问题**——一个字段需要长篇解释才说得清，说明它的语义本来就没定清楚。我已经重写了。

#### 它是什么

一个**分组键**，不是序号。

同 `ordering_key` 的通知被归为一组，**组内不允许并发投递，组与组之间完全并行**。

| 场景              | 取值           | 为什么这组要紧                    |
| --------------- | ------------ | -------------------------- |
| 同一订单的「下单→付款→发货」 | `order:8837` | CRM 先收到“已付款”再收到“已下单”，状态会错乱 |
| 同一用户的状态变更       | `user:10231` | 用户的注册、升级、退订有先后依赖           |
| 同一 SKU 的库存变更    | `sku:A-100`  | 扣减 10 和回补 3 顺序颠倒，最终库存算错    |

**为什么不做全局顺序**：全局有序 = 所有通知排一条队 = 整个系统吞吐降到单个 worker。但绝大多数通知之间没有因果关系（不同用户、不同供应商），所以只对真正有依赖的那一组加约束，其余放开。

**值由调用方填**，因为“什么算同一组”是业务语义（按订单？按用户？按 SKU？），我猜不出来。`NULL` = 不约束，这是默认值，也是绝大多数情况。

#### 但原注释有一处误导，这才是关键

原注释写“同 key 的通知**串行投递**”，听起来像“按顺序投递”。它实际只保证：

> 同一 key 在同一时刻**最多一条处于 PROCESSING**。

这**不等于**严格顺序。反例：

```
t=0   #1 创建（order:8837），投递失败 → RETRY_WAIT，10 分钟后重试
t=0   #1 已不在 PROCESSING，于是 #2 立刻被认领
t=1   #2 投递成功
t=600 #1 重试成功
      → 实际到达顺序：#2 先，#1 后，顺序被破坏
```

要做严格顺序，得改成“**只有队首可见**”：同 key 内存在更早的未完成任务时，后面的任务一律不可认领。代价是 **head-of-line blocking**——队首那条一直失败，整组都被堵住，最长堵到重试预算耗尽（STANDARD 档约 3.5 小时）。等于**一个供应商的偶发故障，会让同一订单的后续所有通知一起延迟**。

#### 我的决定：只做弱保证，严格顺序明确不做

|      | 弱保证（本版）              | 严格顺序（不做）            |
| ---- | -------------------- | ------------------- |
| 语义   | 同 key 不并发            | 同 key 按创建顺序串行       |
| 实现   | 认领 SQL 加一个 anti-join | 额外维护“队首”状态 + 组内阻塞告警 |
| 故障影响 | 单条失败只影响自己            | 队首失败阻塞整组            |
| 复杂度  | 1 处 SQL              | 3 层                 |

需求里三个场景都没提顺序诉求。为想象的需求付 head-of-line blocking 的代价，正是文档 §6 判据 C 要拦的那类决策。

**但配套三件事必须做，否则这个字段就是给假安全感**：① 注释写明不保序（已改）；② 接入文档禁止当顺序保证用；③ 强顺序诉求的正确解法在业务侧——前一条投递成功后再提交下一条。

#### 文档改动

- 新增 **§3.5** 完整讲清上述内容（含反例、四维对比、升级路径）
- `ordering_key` 注释改为：`可选分组键，由调用方填（如 order:8837）。同 key 同一时刻最多一条处于 PROCESSING；【不保证严格按序】，重试会乱序（见 §3.5）。NULL=不约束`
- §2.2 非目标同步改为“同 key 不并发，非严格按序”

- 任务清单加 T4.11（C 级）

| notification_no（我方生成） | idempotency_key（对方填）             | ordering_key（对方填） | 投递给谁 |

**AI（最终回答）**

这个问题迫使我重新检查文档，结果发现文档确实漏了一块。我补充了 §2.4，**并删除 `ordering_key`**。

#### 1｜文档给不出答案，只能肯定“不止一个”

「企业内部多个业务系统」是**问题陈述**，不是系统清单——它只声明调用方不止一个。「注册/付款/购买」是**事件清单**，也不是系统清单。同一事件由哪个系统发出，取决于团队如何划分，与事件本身无关。

同一份文档至少能容纳三种情况，都说得通：

| 情况          | 内部                                            | 是否符合文档 |
| ----------- | --------------------------------------------- | ------ |
| A：1:1（你的理解） | 用户系统→广告，订阅系统→CRM，订单系统→库存                      | 符合     |
| B：多对多       | 用户中心、交易中心、商品中心；“付款”由交易发出，“Contact 状态”由客户主数据发出 | 符合     |
| C：单体        | 一个 monolith 承载三个事件                            | 符合     |

#### 2｜我认为实际情况是 B，并未采用 A

**外部系统的边界是「供应商的产品边界」，内部系统的边界是「团队组织边界」。** 两者的划分原则不同，没有理由正好对齐。逐个拆开看：

- **广告转化回传**：转化数据在交易侧，内部对应方很可能属于增长/营销或交易，不一定是“用户系统”；
- **CRM Contact 状态**：付款事件来自计费，Contact 主数据却归属客户中心——往往是两个团队；
- **库存变更**：订单调库存大概率是**同步内部 RPC**，只有“跨公司通知库存供应商”这一段才需要可靠性保障。

所以“内部 3 个 ↔ 外部 3 个”是巧合，不是结构。真实系统里更常见的是**一个内部系统对多个外部供应商**（用户中心既通知广告，又通知 CRM 画像同步），以及**一个外部系统收多个内部系统**（CRM 收计费的付款状态、收客户中心的资料变更）。

#### 3｜但这个不确定性不影响设计：`caller_id` 并不代表部署单元

它的语义是**提交身份**——一个 credential、一个限流桶、一个归因标签：

- 一个部署单元可持有多个 `caller_id`（单体里营销和财务各申请一个 Key）
- 多个部署单元可共用一个 `caller_id`（同团队的两个服务）

所以“1 个还是 3 个”是**接入时注册几个 Key**，不是架构决策。受影响的只有三个参数级的地方：容量（事件总量不变）、隔离粒度（多 caller 时可叠加限流）、归因精度（能定位到具体调用方）。**结构不变。**

#### 4｜你的推论一半对、一半不成立

| 推论                  | 判断                                                              |
| ------------------- | --------------------------------------------------------------- |
| 事件唯一标识 → 不会**重复**投递 | ✅ 成立，这就是 `idempotency_key`                                      |
| 事件唯一标识 → 不会**乱序**到达 | ❌ 不成立。唯一性是“两个是不是同一个”（相等判断）；有序需要**同一实体的单调版本序列**（全序）。有 ID 不等于可比先后 |

更要紧的是——**乱序由我这层制造，不来自业务层**：

```
业务侧：t=0 发「注册」，t=1 发「付款」     ← 发送顺序完全正确
我方：  「注册」失败 → 退避 10 分钟重试
        「付款」首次成功
到达顺序：「付款」先、「注册」后            ← 顺序被异步重试破坏
```

**引入异步 + 重试的那一刻，到达顺序就不再由发送端决定**，与内部是单体还是微服务无关。你说的“微服务天然有序”只在**同步调用链**里成立；经过我这个异步缓冲，这个性质就丢了。

#### 5｜一个反向发现：1:1 反而让排序更不可能

如果真按 1:1，同一订单的两条通知分别由**订单系统**和**订阅系统**发出，两者互不知情。要在业务侧串行提交，就得让订单系统等订阅系统投递成功——这是跨团队协调。

反过来，如果三个事件都由**同一个系统**在同一事务后发出，业务侧串行提交才可操作。

**所以“内部 1 个还是 3 个”正好决定“顺序能不能在业务侧解决”。而两种答案都不支持在传输层做弱有序。**

#### 6｜决定：删掉 `ordering_key`

这是整套设计里唯一一处“先加、后删”。三条理由：

1. **传输层有序本来就不可靠**：人工 replay 一条 DEAD 必然晚于后续所有通知；同一实体的通知可能投给不同 `target_url`（两条无关连接）；多实例 + 连接池复用。既然下游无论如何都要按版本号处理，传输层有序就是**冗余**——它不能让下游省掉这段逻辑，只能让下游**以为**可以省掉。
2. **弱有序是最糟的一档**：降低碰撞概率但不建立正确性。一个“看起来有保证、实际只在多数情况下成立”的机制，**会被依赖**，然后以偶发、无法复现的形式出问题。
3. **成本藏在热路径**：认领 SQL 多一个 anti-join（每 500ms 一次）+ 一个索引 + 一份“填了但不保序”的说明——而这份说明本身就是“字段没定清”的证据。

升级路径保留（槽位表，加列+加索引，无迁移），触发条件写死：**某个调用方明确提出“同一实体必须按序到达”，且能说清乱序的业务后果**。没有这个具体场景，就不做。

- **§3.5 重写**为「为什么首版不做顺序保证」，含三条理由 + 两条升级路 + 顺序该在哪解决的三层对比
- **§3.6 收敛**为只讲幂等键粒度（原来的“两个键对比”只剩一个键）
- **DDL 删除 `ordering_key` 列**；§2.2 非目标、§5 取舍表、§7 V1、§9 待验证假设同步改
- **任务清单**：删除 T4.11，新增 T0.6/T0.7（记录拓扑未知 + “先加后删”决策）

## Q8｜设计要点文档：目前任务轮询是 500ms，如果有强时效性的业务系…

**我（提问）**

> 设计要点文档：目前任务轮询是 500ms，如果有强时效性的业务系统接入，改造成本高吗？
> 任务拆解清单文档几个问题：1、Flyway迁移是为了什么，通知量级上升切消息组件吗，成本如何？2、执行归档任务是为了什么？

**AI（最终回答）**

三个问题都答了，文档同步补强。先直接回答。

#### 1｜强时效接入，改造成本高吗？——不高，且前两级免费

关键是别把“改造成本”理解成换架构。降法分三级：

**① 调配置（零代码）**：轮询间隔本来就是预留配置项（T1.3），降到 50ms 即可。空闲 DB QPS 从每实例 2 涨到 20，仍可忽略。适合“偶发强时效”。

**② 提交后唤醒（insert-then-hint，约一个小类）**：V0 是模块化单体，接入 API 和 Dispatcher 在同一个 JVM 里——这是本方案白送的一个优势。落库成功后直接把 `notification_id` 塞进内存交接队列，Dispatcher 立即认领，绕过等待。**妙处在于提示丢了也无所谓**：轮询 500ms 后照常兜底，所以 at-least-once 语义完全不变。DB 是唯一事实来源，内存队列只是加速器。p50 受理延迟从 ~250ms 压到 ~10ms。

**③ 跨实例信号（多实例后才需要）**：hint 只唤醒本 JVM，多实例时其他实例仍靠轮询。真出现瓶颈再上 Redis pub/sub——那是第一次引入新组件的时机，之前都是免费的。

顺带修正一处：原文档 §9.8 写的备选是“DB 触发器 + 事件通知”，**这个建议是错的**——逻辑藏在数据库里无法单测，触发器与 binlog/复制的交互不可控。已改掉。

但有两个比优化更重要的问题要先问业务方：

- **“强时效”指我方受理延迟，还是端到端送达？** 端到端里我方只占一小段，外部供应商的处理延迟往往比 500ms 大一个数量级。先要数据，再决定优化哪一端。
- **如果“必须 1 秒内送达且失败要实时可见”**——这个场景大概率**不该走本系统**。§1.1 说过，异步通知的定位是“业务系统不关心返回值”；验证码这类同步交互应该同步调用。**边界判断优先于性能优化。**

#### 2｜Flyway 是为了什么？——和切消息组件无关

这是个常见误会。Flyway 是**数据库 schema 的版本管理**：每次改表 = 新增一个 `Vn__xxx.sql` 文件，应用启动时自动按序执行未应用的迁移。三个收益：

1. schema 变更进 code review，谁在何时改了什么有历史可查；
2. 新环境（评审现场、同事本机）一条命令把库建到最新；
3. 评委会直接看到 schema 演进过程——本身就是“真实工程经验”的证据。

**它不服务换 MQ。** 真正的量级切换是另一条路（设计文档 §7 V2）：`notification` 表从“队列”退回“状态存储”，到期扫描换成 Kafka 消费者，schema 基本不动——这是当初选“DB 即队列”刻意留的缝。切换成本：应用层改造 1~2 周 + 养一套 Kafka，触发条件是日量 10 倍（§8.3 敏感性分析）。Flyway 本身的成本：接入半天，之后每改一次表加一个文件，唯一纪律是已提交的迁移不可再改。

#### 3｜归档任务是为了什么？——两个目的，都不是“顺手清理”

- **合规（主要目的）**：注册/付款事件的 body 含手机号、邮箱、金额。“PII 最小留存”是 D10 的硬要求——成功 24h、失败 7 天后必须清除明文，`body_sha256` 保留供排查。**这不是性能优化，是安全设计的一部分。**
- **扫描效率**：到期扫描走 `(status, next_attempt_at)` 索引，已完结行留在热索引里会拉深 B+ 树、降低 buffer pool 命中率；MEDIUMBLOB 溢出页还额外占空间。

节奏上分两步：首版只清 body（UPDATE 置空，分批 LIMIT 执行避免大事务）；到 V1（日 > 300 万）再把已完结行整体搬到归档表。之所以不用分区表一步到位——`uk_idem` 与按 `created_at` 分区冲突（唯一键必须含分区列），这个坑任务清单里已记录。

#### 文档改动

- 设计文档 **§9.8 重写**：三级降级路径 + hint 丢失兜底的设计 + 删掉错误的触发器备选 + 两个先要问业务方的问题
- 任务清单：**T1.4 下加 Flyway 说明块**（是什么/与换 MQ 无关/成本）、**T2.6 下加归档说明块**（合规 + 扫描效率两目的）、**新增 T4.12**（insert-then-hint，C 级，DoD 含“hint 丢失时轮询兜底”的单测）

你的问题再次暴露了一个写作问题：任务清单里“Flyway"“归档任务”这类**工具名词当任务名**，对不了解的人是黑盒——我已经在这两处补了“它解决什么问题”。这个问题值得记着：工具名词进任务清单时，旁边必须跟一句动宾结构的解释。
