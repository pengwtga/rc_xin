# T2.1 失败分级 + 退避调度 —— 设计与实现说明

> 对应：任务拆解 T2.1 ｜ 设计文档 V2 §4.4 ｜ 依赖：T1.2 已完成

## 1. 本阶段边界

| 做 | 不做（归后续阶段或明确不采纳） |
| --- | --- |
| `ErrorClassifier`：结果 → SUCCESS / PERMANENT / RETRYABLE 三级，**入参只有结果** | 熔断与端点隔离（T2.5） |
| 未列出的 4xx 一律 PERMANENT（保守侧，§2.2） | ~~端点级分类覆盖表~~ —— **明确不采纳**，见 §2.3 |
| `BackoffPolicy`：`min(cap, base×2^(n-1)) × rand(1-j, 1+j)` 全抖动 | 死信日志/告警钩子（T2.3，本阶段只落 WARN 日志） |

| Dispatcher 失败分支接入分类结果；PERMANENT 一次即 DEAD | 指标上报（M3） |

T1.2 的已知妥协"4xx 也会重试"在本阶段消除。

## 2. 设计思路：六个决策点

### 2.1 分类只看结果：纯函数，既不依赖地址也不依赖配置

```java
Decision classify(Outcome outcome)
// Outcome = (statusCode | errorClass, retryAfterSeconds)
```

分类的全部输入就是四个值，输出是 `(级别, retryAfter秒)` 二元组。**三层"什么都不加"的决定**：

- **不做策略接口/策略注册表**：三级分类是**语义**，不是可变策略。写成 `interface + 两个实现` 只是把一个 switch 拆成两个文件，还多出"实现怎么选"这个新问题；
- **不做配置表**：曾经有过按 host 的端点覆盖表，review 后整体删除（§2.3）。配置看起来比代码"灵活"，实际是把"谁该负责"的问题藏起来——下游的接口不规范，被一条我们自己的配置悄悄接住了；
- **签名里没有 `targetUrl`**：**同一个 400 无论发往哪个地址，答案都一样。** 这是删掉覆盖表最直接的收益——分类恢复了局部可推理性：给同样的输入必得同样的输出，推理时不需要知道"这是发给谁的"。

单测覆盖整张真值表即可：不需要 mock、不需要构造配置、不需要 Spring 上下文。

### 2.2 未列出的 4xx 默认 PERMANENT（保守侧）

设计文档 §4.4 只列了 400/401/403/404/422 → PERMANENT、408/429 → RETRYABLE。剩下的 4xx（410/413/415…）必须有个默认，我选 **PERMANENT**，理由是不对称代价：

- **错判成 PERMANENT**：任务进了死信，但它是事实记录、可人工重放（§4.6），损失可逆；
- **错判成 RETRYABLE**：一次端点级事故把健康任务的重试预算全烧光，等供应商恢复时任务已 DEAD——不可逆（这正是 T2.5 熔断跳过不计次要防的事）。

**判死不是黑洞**（这是敢往保守侧倒的前提）：任务是事实记录，`DEAD` 可查、可人工重放（§4.6），下游可追。错判的代价是"延迟 + 一次人工"，不是"丢失"。这条兜底不依赖任何新机制——`max_attempts`、`DEAD` 状态、明细表，M1 时就已经全在了。

### 2.3 不做端点覆盖表：不替下游的接口不规范买单

> 本节记录一个**被删掉的设计**。曾经实现过按 host 的端点覆盖表（配置 `host + retryable-statuses`，命中则把该状态码强制改判 RETRYABLE，用来适配"某家供应商用 400 表示系统忙"），代码已全部移除：`NotifyProperties.Classification` / `EndpointOverride` 两个记录、`ErrorClassifier` 的构造器与 host 查表、`application.yml` 的 `classification` 节、独立的 Spring 上下文集成测试。`classify` 的签名从 `classify(outcome, targetUrl)` 收回 `classify(outcome)`。

**为什么删——三条理由，第二条是关键**

1. **问题不在我们这一层。** 4xx 的语义由供应商定义，"用 400 表示系统忙"本质是对方接口不规范。我方加配置去适配，等于把对方的缺陷固化成我方的长期维护项：每来一家不规范的供应商就多一条配置、多一份"这条配置为什么存在"的口头知识。**偶发的外部缺陷，变成了内部的永久机制。**

2. **它假设了一个未经观测的前提，且假设失效时是反向伤害。** 覆盖表只在"状态码语义是 host 级属性、同 host 下所有路径共享一套语义"时成立。一旦某家供应商 `/v1/notify` 的 400 是"忙"、`/v1/query` 的 400 是真参数错：
   - 不配路径维度就**表达不了**；
   - 强行按 host 配，`/v1/query` 的真参数错误会被重试满 `max_attempts`（≈3.5h）才进 DEAD——**一条"正确"的例外配置，制造出一个新的错误面**，而且它恰好把 §2.2 的不对称代价论证翻了过来（把"错判重试"的不可逆损失从供应商级扩散到路径级）。

   补路径维度要定义匹配语义（精确/前缀/正则？大小写？查询串算不算）、多条命中的优先级、冲突校验、变更后重算——那不是"例外登记簿"，是路由规则引擎。**为一个尚未观测到的场景建规则引擎，是《过度设计分析》里那个句式的原样重演。**

3. **"错的代价不对称"其实支持不做，不支持做。** 判死 → 人工重放（可逆）；判重试 → 烧光预算 + 可能重复的业务动作，比如库存扣两次（不可逆）。既然代价不对称，默认行为就该站在可逆那一侧，**而不是靠配置去猜对方大概什么意思**。

**它不是"永远不做"，准入门槛在这里（三条必须同时成立）**

| # | 条件 | 不成立的典型情形 |
| --- | --- | --- |
| 1 | **有量**：该下游的 4xx 造成的人工重放已是运维负担（如日均 >10 条） | "理论上可能会用 400 表忙"——想象的需求 |
| 2 | **没议价权**：对方不可推动（跨公司商业伙伴、改造无期），且已正式提出修正要求被拒 | 内部系统、或对方愿意改——那修对方比修我们便宜 |
| 3 | **无更便宜的替代**：调用方无法在提交侧规避（例如业务方自己延后重试该事件） | 业务方一行代码就能绕开——责任本来就该在能改的一方 |

三条都成立时，**仍然不改配置，而是改这一行代码**：在 `ErrorClassifier` 里为那个状态码加一条带注释的例外。理由是"例外是唯一的、写死的、`git blame` 能追到决策的"；做成配置看起来灵活，实际是把一次性的补偿，变成了需要长期维护、会被误配、会随 host 漂移静默失效的配置面。

**敢删的最强理由：加回来的成本极低。** 整套机制约 40 行代码 + 一个配置节 + 一个独立 Spring 上下文测试，翻案成本小于现在养着它的成本（多一个配置面、一个未经检验的假设、一条"同 host 语义一致"的隐性约定）。**能低成本加回来的东西，就应该先不加**——和《过度设计分析》里砍掉那 11 项用的是同一把尺子。

**它也不解决什么**（边界，避免下次有人拿它当万能适配层）：

| 场景 | 覆盖表能否解决 | 说明 |
| --- | --- | --- |
| 某家 `200` + body 里 `code≠0` 表示失败 | ❌ | 需要解释供应商**业务语义**；需求写明"业务系统不关心返回值"，我方无权代判。要支持就得为每家写响应判定脚本 → 配置平台 |
| 同一 host 下不同路径语义不同 | ❌（且会**反向生效**） | 见上文第 2 条 |
| 各家 URL / Header / Body 格式不同 | ❌（也不需要） | 由 `target_url` + 原样透传解决，本就不需要机制 |
| 各家认证方式特殊（签名/时间戳） | ❌ | 调用方在 headers 里算好再提交，我方只搬运 |
| 响应体是 XML/protobuf | ❌ | 不解析响应，只留 2KB 片段供排查 |

**不做"多一个键"的粒度扩展**：删掉之前的最后一版实现是 `host + 状态码`，如果当时继续加 `path-prefix`，就会顺次长出"匹配语义、优先级、冲突校验、热更新"。**一个机制只要开始需要第二条规则来解释第一条，就该回头看看它是不是根本不该存在**——这次回头看的结果是：不该。

### 2.4 `Retry-After` 只解析秒数格式，不支持 HTTP-date

RFC 7231 允许两种格式。只支持数值秒，原因：

1. 数值格式覆盖了绝大多数供应商实现（Cloudflare/AWS/Google 全是秒数）；
2. HTTP-date 需要**应用时钟**解释"现在"，而本系统的时钟纪律是"时间一律 DB `NOW(3)` 起算"（§4.3 约束 3）——为一个小众格式破例引入应用时钟依赖不值；
3. 解析失败静默忽略、走常规退避——**对方的建议是优化，不是契约**，解析失败不能让投递失败。

翻案条件：真实供应商返回 date 格式且数值路径不可用时再补。

### 2.5 退避公式照设计文档原文，抖动乘在 cap 之后

`delay(n) = min(cap, base × 2^(n-1)) × rand(1-j, 1+j)`

注意抖动乘在 **cap 之后**，所以尾部延迟最大可到 `1.5 × cap`（默认 1.5h）。这是公式的原意而不是疏漏：cap 的目的是**控制节奏量级**（小时级），不是硬上界；而 429 的 `Retry-After` 路径例外——那是对方的**承诺**，clamp 到 `[1s, cap]`，不抖动（对方说了 120s 就是 120s，抖动会破坏承诺语义）。

### 2.6 保持"HTTP 失败用 status_code 表达、error_class 只留给网络层"的口径

400 被判 PERMANENT 后，`last_status_code=400`、`last_error_class=NULL`——分类结果**不**写进 DB。理由：`(status_code, error_class)` 已经无损表达了事实，分类是**推导**，重复存储只会引入"两处不一致"的新故障面（推导规则改了，存量行没改）。T2.3 死信聚合时按 `status_code IS NULL AND error_class IS NOT NULL` 区分网络类失败即可。

## 3. 分类真值表（实现与测试一一对应）

| 输入 | 分类 | 处理 |
| --- | --- | --- |
| 2xx | SUCCESS | `SUCCEEDED` |
| 400/401/403/404/422 | PERMANENT | **一次即 DEAD，不花预算**；401/403 打 WARN 日志（告警钩子 T2.3/M3 接） |
| 其余 4xx（未列出） | PERMANENT | 同上（§2.2 保守侧） |
| 408 / 429 | RETRYABLE | 重试；429 带 `Retry-After` 秒数时优先采用（clamp `[1s, cap]`，不抖动） |
| 5xx | RETRYABLE | 重试 |
| TIMEOUT/DNS/TLS/CONN_REFUSED/IO（errorClass 非空） | RETRYABLE | 重试 |

**真值表里没有"地址"这一列**，这是刻意的：同一个 400 无论发往哪个 host，分类结果都一样。表中没有例外分支，因为不打算有例外（§2.3）。

## 4. 处理流程

```
deliverOne(claimed)
  ├─ HTTP 投递（T1.2，不变；HttpDeliverer 顺带捕获 Retry-After 头）
  ├─ insertAttempt（明细无条件落库，不变）
  └─ classify(outcome)          ← 只看结果，不看地址（§2.3）
       ├─ SUCCESS    → markSucceeded（不变）
       ├─ PERMANENT  → markFailed(DEAD, delay=0)   ← 一次即死，不查预算
       └─ RETRYABLE  → attempt_no < max_attempts ?
                          ├─ 是 → markFailed(RETRY_WAIT, backoff(attempt_no, retryAfter))
                          └─ 否 → markFailed(DEAD, delay=0)
```

## 6. 验证方案与结果

### 6.1 单元测试（无 DB）

- `ErrorClassifierTest`：真值表全量（2xx / 五个列出 4xx / 未列 4xx / 408 / 429 / 503 / 5xx / 五种网络错误类 / Retry-After 传与不传）。**8 个用例，无 mock、无需构造配置**——分类器没有依赖可注；
- `BackoffPolicyTest`：公式边界——attempt=1 区间 `[0.5×base, 1.5×base]`、cap 后抖动可达 `1.5×cap`、`Retry-After` 优先且不抖动、clamp 上下界。

### 6.2 集成测试（真实 MySQL）

| 用例 | 断言 |
| --- | --- |
| 400 → 一次即 DEAD | `DEAD`、`attempt_count=1`、再轮询不认领 |
| 429 + `Retry-After: 120` | `RETRY_WAIT`，`next_attempt_at` 距今 118~122s（对方承诺，不抖动） |
| 429 无 `Retry-After` | `RETRY_WAIT`，退避在 `[0.5×base, 1.5×base]` 秒区间 |
| （回归）500 → RETRY_WAIT / 预算耗尽 DEAD | 原 T1.2 用例继续通过 |

### 6.3 实测结果（2026-10-31）

**自动化测试**：`MYSQL_IT=true mvn test` → **56/56 全绿**（无 DB 环境 42 过 + 14 个集成用例按设计跳过）。较删除覆盖表之前的 59 少 3 个：都是只验证覆盖表的用例——`ErrorClassifierTest` 2 个（命中/未命中、非法 URL 按无覆盖处理）、独立 Spring 上下文的 `EndpointOverrideIntegrationTest` 1 个。**删机制顺带删掉了 3 个测试和整个测试上下文，测试总数下降不是覆盖度下降。**

**手工端到端**（真实 MySQL + 两个 mock 下游：9003 恒 400 / 9004 恒 500）：

| # | 动作 | 4s 后 | 18s 后 |
| --- | --- | --- | --- |
| ① | 提交到恒 400（#120） | `DEAD`，`attempt_count=1`，退避列 `-` | **纹丝不动**：`attempt_count=1`、HTTP 只发生 1 次 |
| ② | 提交到恒 500（#121） | `RETRY_WAIT`，`retry_in_5s`（10s base × 抖动下限） | `attempt_count=2`、HTTP 已发生 2 次 —— **同一条命令的 400 被判死、500 在按曲线重试** |

T1.2 的已知妥协（"4xx 也会重试"）就此消除：**同样的失败预算，现在只花在可能自愈的失败上。**

### 6.4 过程中的两个波折（都属实现侧，非设计变更）

1. **record 加组件引发 Spring 绑定失败**：`NotifyProperties` 增加 `classification` 组件后，先加了个 5 参便捷构造想保住老测试调用——结果 record 出现第二个构造器后 Spring Boot 无法再推断 canonical 构造器，全部集成测试报 `No default constructor found`。撤掉便捷构造、老测试调用点显式补 `null`。**教训：record 的构造器面是绑定契约的一部分，加"方便"要三思**；（后因覆盖表整体删除，该组件已不存在，这条只剩方法论价值）；
2. 编辑集成测试时误删了"明细只追加"用例，跑全量前发现并补回——这正是不删既有用例、全量回归的价值。

### 6.5 review 中的一次删除（唯一的设计变更）

覆盖表在实现完成后、review 中被判定**不该存在**（理由与准入条件见 §2.3）。删除范围：`NotifyProperties` 两个记录（连带 record 从 6 个组件退回 5 个、`null` 参数全部消失）、`ErrorClassifier` 的构造器/查表/URI 解析/异常兜底、`application.yml` 一个配置节、一个独立 Spring 上下文测试、2 个分类器用例；`classify` 签名从 `(outcome, targetUrl)` 收回 `(outcome)`。

值得记的是**删掉之后哪些东西变好了**，否则"删"看起来只是减法：

| 维度 | 有覆盖表 | 删除后 |
| --- | --- | --- |
| 分类器的依赖 | 依赖 `NotifyProperties`、解析 URL、异常兜底 | **无依赖、无状态、不抛异常**，真值表即可穷尽行为 |
| 可推理性 | 同一 400 因地址不同而处理不同 | **同一输入必得同一输出**，本地即可推理 |
| 配置面 | 多一个需要解释、需要校验、会随 host 漂移失效的配置节 | 零配置，分类语义写在代码里 |
| 测试 | 多一个独立 Spring 上下文（启动成本 + 上下文污染风险） | 纯 JUnit，毫秒级 |

**这次删掉的不是"没写完的功能"，是"写完了但不该有的功能"**——两者在 review 里的信号完全不同：前者看排期，后者看它到底替谁解决了什么问题。答不上来，就该删。

## 7. 已知限制

1. **"4xx 一律判死"的运营含义：不规范会显性化，不会被配置悄悄吸收。** 没有覆盖表之后，任何"用 4xx 表忙"的供应商都会直接进死信，靠告警 + 人工重放兜底（T2.3 / T3.2）。这是默认行为、也是刻意的取舍：**让下游的不规范在死信队列里可见，而不是被我方配置悄悄兼容掉。** 若这类供应商多到构成负担，正确的动作是往接入规范里加一条硬要求（"临时故障必须用 5xx/429，禁用 4xx 表忙"），而不是回头加覆盖表——真要加，先过 §2.3 的三条准入条件；
2. **`Retry-After` 的 date 格式不支持**（§2.4，已给翻案条件）；
3. **401/403 的"立即告警"本阶段只是 WARN 日志**——T2.3 落死信钩子、M3 接指标后升级，本阶段不预先建告警机制。
