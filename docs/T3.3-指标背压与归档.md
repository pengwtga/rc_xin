## 1. 三个能力，一句话各自

| 能力 | 一句话 | 关键取舍 |
| --- | --- | --- |
| 指标 | 回答"现在健康吗""是不是某个供应商的问题" | 采样缓存，抓取永不查库 |
| 背压 | 队列不健康时明确说"现在处理不了" | fail-open，只挡新提交 |
| 归档 | 过了保留期只清密文，不删行 | 保留证据，清掉 PII |

## 2. 指标：五个核心口径

### 2.1 指标清单

| 指标 | 类型 | tag | 回答什么 |
| --- | --- | --- | --- |
| `notify_ingest_requests_total` | counter | `route`, `status` | 受理 QPS 与错误率（`rate()` 出结果） |
| `notify_ingest_idempotent_hits_total` | counter | `caller` | 多少请求是重试（去重效率 + 我方变慢的信号） |
| `notify_ingest_backpressure_rejections_total` | counter | `reason` | 拒了几次、因为积压还是因为队头太老 |
| `notify_queue_backlog` | gauge | — | 待投递积压（PENDING + RETRY_WAIT） |
| `notify_queue_oldest_overdue_seconds` | gauge | — | **队头等了多久**（队列健康度的主指标） |
| `notify_queue_dead` | gauge | — | 死信待办量（拉取式消费的处理压力） |
| `notify_delivery_attempts_total` | counter | `endpoint`, `result` | 投递成功率；按端点聚合区分单点与全局 |
| `notify_delivery_skipped_total` | counter | `reason` | 主动没发多少（熔断 / 并发满） |
| `notify_delivery_stale_results_total` | counter | — | 结果被租约守卫丢弃（双投风险，应为 0） |
| `notify_deadletter_total` | counter | `reason` | 死了多少、是对方拒收还是我们花完预算 |
| `notify_circuit_open_endpoints` | gauge | — | 当前几个端点被熔断 |
| `notify_archive_cleared_total` | counter | `tier` | 归档清了多少行 |

### 2.2 决策一：抓取时绝不查库

`/actuator/prometheus` 的 Gauge 是**抓取时求值**的。如果取值函数里写 SQL：

1. 一次 DB 抖动会让整个 scrape 返回 500 —— 监控在最需要它的时刻丢掉全部指标；
2. 代价被放大成 `抓取频率 × 实例数`（15s × 20 实例 = 每分钟 80 次聚合查询），而这台 DB 同时在跑投递队列；
3. 背压需要"队列状态"时也只能跟着查库，把受理 p99 < 50ms 的前提打破。

所以 `QueueSampler` 每 10s 查一次，把结果放进 `AtomicReference` 与几个 `AtomicInteger`，Gauge 只读内存。采样失败时**保留上一次快照**并按次数节流打日志（第一次 + 每 60 次），而不是把异常当信号。

副作用是一个真实代价：**快照最多旧 10s**。演示脚本里清库后立刻提交会被上一轮的积压量误拒，必须等一次采样（见 `scripts/observability_demo.sh` 的注释）。这是可接受的——阈值是 30 分钟量级，10s 的滞后不影响判断；而背压误拒一次 503，调用方按 `Retry-After` 重试即可。

### 2.3 决策二："最老任务年龄"必须用 `next_attempt_at`，不能用 `created_at`

这是本轮最容易写错、后果最大的一处。

- 用 `created_at`：一条 30 小时前创建、正在 1 小时后重试的单（指数退避曲线最长 3.5h，这是**正常**的），会被算成"最老任务 30 小时"，背压判定 `30h > 30min` 成立 → **整个受理入口被关掉**。一个健康的系统因为"有任务正在按计划等待重试"而拒绝所有新流量。
- 用 `next_attempt_at` 且限定 `<= NOW()`：只统计**已经到点却还没被认领**的任务，正常值应该接近 0（轮询 500ms），积压时才抬升。这才是 Kafka consumer lag 的等价物。

`BackpressureIntegrationTest.退避中的老任务不触发背压` 就是这条的回归钉子。

### 2.4 决策三：计数封顶（`LIMIT maxPending + 1`）

`notify_queue_backlog` 的 SQL 是：

```sql
SELECT COUNT(*) FROM (
  SELECT 1 FROM notification WHERE status IN ('PENDING','RETRY_WAIT') LIMIT ?
) t
```

封顶值取 `maxPending + 1`（默认 100001）。理由：

- 监控和背压**只需要知道"有没有越过阈值"**，50 万这个精确数字没有决策价值；
- 封顶后这条 index-only scan 在积压 500 万时仍然扫 10 万行就停，代价不随表增长恶化——这表同时是投递队列，聚合查询不能变成它的负担；
- 封顶值必须**严格大于**阈值。写反（比如固定 10000 而阈值 10 万）就是一个永远不触发的背压，而且没有任何报错。

`notify_queue_oldest_overdue_seconds` 用另一种写法避免聚合：两个状态各取 `ORDER BY next_attempt_at LIMIT 1`（索引第一项），再取两者最小——两次索引定位，与积压量无关。

### 2.5 决策四：不给"成功率"建 Gauge

成功率必须选一个时间窗口（5 分钟？1 小时？），而窗口是**查询时**的事。存原始计数（`success` / `retryable` / `permanent`），窗口交给 PromQL 的 `rate()`。否则换一个窗口就要改代码、发版、再等一个发布窗口。

同理，`result` 分三类而不是"成功/失败"两类：`retryable` 和 `permanent` 的处置完全不同（前者等下游恢复，后者要人看凭证），混在一起就丢掉了告警该走的路径。

### 2.6 决策五：`endpoint` tag 必须有基数上限

`endpoint` 的值来自调用方填的 `target_url`。一个写错的循环或一次压测能造出几十万个 host，每个 `(endpoint, result)` 组合都是一条独立时间序列 —— 这是"指标把服务打挂"的经典形态，而且发生在流量异常时。

`MetricsConfig.endpointTagCardinalityLimit()` 在注册期把第 201 个之后的 endpoint 折叠成 `other`：

- 选**折叠**而不是**拒绝注册**：拒绝会让超限端点完全没有数据，面板上表现为"这个端点没流量"，比"其他"这个桶更危险；
- 折叠保留总量：全局失败率仍然准确，只是失去个别端点的分辨率；
- 上限 200，真实部署是个位数量级的供应商。

同一问题的另一面：**不做 per-endpoint 的 Gauge**（熔断状态只暴露"当前打开几个端点"）。端点值同样是不可信输入。

## 3. 背压：拒绝优于堆积

### 3.1 判定

`BackpressureGuard.ensureCapacity()` 在 `NotificationService.submit` 的**第一行**调用——过载时连 URL 校验和 AES 加密都不做，那些 CPU 花在注定被拒绝的请求上只会让系统更慢。

两个阈值，**先看年龄**：

| 条件 | 语义 | 默认 |
| --- | --- | --- |
| `oldestOverdueSeconds >= maxOldestAgeMinutes × 60` | 队头已经等了太久，SLA 守不住 | 30 分钟（`>=`） |
| `backlog > maxPending` | 积压条数超过消化能力 | 10 万（`>`） |

年龄用 `>=`（阈值是可接受上限），条数用 `>`（10 万条仍在设计容量内，第 100001 条才拒）。两个阈值都越界时报"年龄"——它更接近 SLA，也更能解释"为什么慢"。

### 3.2 四个刻意的边界

1. **fail-open**：从未采样成功（刚启动、DB 刚恢复）时放行。此时提交本身也会失败，不会静默堆积；反过来"拒绝一切"会把一次监控故障升级成全站不可用。
2. **只挡新提交**，不挡查询与重放。事故时运维恰恰需要查单和重放，把管理面挡住等于自断手脚。
3. **读缓存不查库**：受理 p99 < 50ms 的前提（参数依据 §3.2）。
4. **不做 per-caller 限流**：那是公平性（一个调用方打满不该让别人排队），与"系统还能不能接"是两个维度，见任务清单 T3.5。

### 3.3 `Retry-After` 必须给

`503` 不带 `Retry-After`，调用方只能立刻重试——而立刻重试正是把背压变成雪崩的方式。默认 30s：短了等于没背压，长了让业务回调整体推迟；30s ≈ 队列消化 10% 的时间，够引擎缓一口气。

实现上把这个值放在 `ApiException` 上（`retryAfterSeconds`），由 `ApiExceptionHandler` 写成响应头。放在异常上而不是让 Handler 猜：只有抛出方知道该让调用方等多久。

## 4. 归档：清 PII，不清证据

### 4.1 两档保留期

| 档位 | 保留 | 为什么是这个数 |
| --- | --- | --- |
| `SUCCEEDED` | 24h | 投递已完成，请求体只剩"当天排障"的价值 |
| `DEAD` / `CANCELED` | 7d | 要撑到人工重放（T3.2），而重放往往发生在供应商修好之后 |

清三样东西：`body_enc`、`headers_enc`、`delivery_attempt.response_snippet`。第三样容易漏——**下游响应里经常回显手机号、订单号、甚至 token**（有的供应商把凭证回显在错误信息里）。只清请求体不清响应体，等于留了半扇门。

### 4.2 只清密文，不删行

行、状态、`delivery_attempt` 全部保留：

- T3.1 的查询接口要回答"这条为什么没到"，靠的就是这些行；
- T3.2 的人工重放要在 DEAD 行上操作，删了就没得重放；
- 存储成本真到了要处理的时候，是设计文档 §8 的 V1（按月归档到冷表），不是这里。

### 4.3 `updated_at = updated_at`：这一行不能省

`updated_at` 是 `ON UPDATE CURRENT_TIMESTAMP`，语义是"最后一次**状态**变更时刻"。归档不是状态变更。如果不显式赋值，MySQL 会自动刷新它：

- §4.11 里"这行多久没动过"的判断失真——一批每天被清一次的老单，看起来永远像刚处理过；
- 归档自己的时间窗口也会漂移。

MySQL 的规则是"列在 SET 子句里被显式赋值就不自动更新"，所以写 `updated_at = updated_at`。这一行的注释在 `ArchiveRepository` 里，不在文档里就没人看得懂。

### 4.4 分批 + 有限批数

这表同时是投递队列。一条 `UPDATE ... WHERE updated_at < ...` 锁十万行，会把认领 SQL 挡在行锁后面 —— 归档任务本身变成一次投递故障。

- 每批 1000 行，每批独立事务（毫秒级锁）；
- 单次最多 100 批（10 万行）：首次上线可能积压几百万行，一次跑到底意味着几十分钟高 IO，而保留期以天计，"清不完明天继续"完全没有问题。执行时长有上界才能配超时与告警。

循环终止有三个出口，缺一不可：取不到行 / 本批不足 `batchSize` / **实际清理 0 行**。第三个是防死循环：并发清理或数据被重放改状态时，同一批 id 可能反复被选中。

### 4.5 索引：`idx_status_updated(status, updated_at)`

归档条件 `status = ? AND updated_at < ?` 正好是"等值列在前、范围列在后"。现成的三条索引都用不上：

- `idx_due(status, next_attempt_at)`：第二列是投递时刻，不是变更时刻；
- `idx_lease(status, lease_until)`：只服务 PROCESSING；
- `idx_caller_status(caller_id, status)`：前缀是 caller，归档是全局扫描。

## 5. 顺手修的两个真 bug

### 5.1 不存在的路径返回 500

Spring 6.1 起"没有匹配的 handler"抛 `NoResourceFoundException`，它落到 `Exception` 兜底 → **500**。和 T3.1 的 `/v1/notifications/abc` 是同一个病：客户端问题被报成服务端故障，告警会响、错误率指标被污染。

加了一个 handler 明确回 404。发现过程很实际：写指标测试时 MockMvc 访问 `/actuator/prometheus` 得到 500，才注意到这个兜底把 404 吃掉了。

### 5.2 401 没有进受理指标

`IngestMetricsFilter` 最初没有指定顺序，被 `ApiKeyAuthFilter` 包在里面。而鉴权失败时 `ApiKeyAuthFilter` 直接写响应、不再往下传链 —— 里层 filter 的 `finally` 根本不会执行，**401 全部漏计**。而 401 恰恰是错误率里最该看见的一类。

改成 `@Order(HIGHEST_PRECEDENCE)`，包在最外层。

### 6.1 测试

`MYSQL_IT=true mvn test` → **165/165 全绿**（T3.2 时 143，新增 22）：

| 用例 | 数量 | 钉住什么 |
| --- | --- | --- |
| `BackpressureGuardTest` | 8 | 阈值边界（`>=` / `>`）、fail-open、Retry-After、拒绝计数 |
| `QueueSamplerIntegrationTest` | 3 | backlog 口径、逾期只算"已到点"、空库为 0 而非 null |
| `ArchiveIntegrationTest` | 5 | 两档保留期两侧、非终态不动、只清不删、snippet 一并清、`updated_at` 不变、重跑幂等 |
| `BackpressureIntegrationTest` | 3 | 超阈值 503 且不落库、退避中的老任务不触发、健康时正常受理 |
| `MetricsIntegrationTest` | 3 | 真实 Tomcat 上抓 `/actuator/prometheus`，5 个核心指标 + 401 计数 + 幂等计数 |

`MetricsIntegrationTest` 走随机端口而不是 MockMvc：`/actuator/prometheus` 是 actuator 自己的 `WebMvcEndpointHandlerMapping`，MockMvc 切片里不存在——测它会得到一条假路径。

另外，Spring Boot 的测试支持会把 `management.defaults.metrics.export.enabled` 置为 `false`（避免测试向外部监控系统导出），所以测试里必须显式 `management.prometheus.metrics.export.enabled=true`，否则 registry 退化成 `SimpleMeterRegistry`、端点直接不存在。这个坑值得记住：**测试环境的 metrics 行为和线上不一样**。

## 7. 已知限制

| 限制 | 代价 | 什么时候需要处理 |
| --- | --- | --- |
| 背压读 10s 前的快照 | 清空积压后仍可能拒 1~2 次 | 不需要处理：调用方按 Retry-After 重试 |
| 归档每天全范围扫描该状态的老行 | 已清空的行仍会被扫到再由条件过滤；5000 万行量级约数秒 | 真不能接受时做分区归档（§8 V1），不要加水位表——水位丢了还是要全扫 |
| 指标是单实例视角 | 多实例要靠 Prometheus 聚合 | 已足够：`sum by (...)` |
| 没有 per-caller 限流 | 一个调用方打满会让别人一起被 503 | T3.5（429 + 令牌桶） |
| 归档任务没有分布式锁 | 多实例同时跑会重复清同一批 | 影响很小（条件幂等、清 0 行即退出），真要锁用 `GET_LOCK` |
