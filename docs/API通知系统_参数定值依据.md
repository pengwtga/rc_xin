# 参数定值依据 —— 每个数字是怎么推出来的

> 配套：`docs/API通知系统_设计文档.md` §4.3–4.8、§7、§9.1。
> 核心观点：**这五个数字没有一个是独立"选"出来的——它们要么从业务容忍度倒推，要么从彼此的约束关系推导。参数之间的不等式比绝对值更重要。**
> 引用方式：源码与 `application.yml` 注释里的「参数定值依据 §x.y」指本文；设计文档只写结论，推导链在这里。

---

## 1. 定值方法：先分类，再定角度

五类参数，各自的角度不同，用错角度就会"拍脑袋"：

| 类别                 | 参数                          | 定值角度                          | 定错的代价                   |
| ------------------ | --------------------------- | ----------------------------- | ----------------------- |
| **业务型**（用户在等什么）    | 最大重试次数、退避曲线                 | 业务可接受的最长补偿窗口                  | 该自动恢复的没恢复 / 死信告警风暴      |
| **体验型**（SLA 里承诺什么） | 轮询间隔                        | 受理→送达延迟的 SLA 配额               | 几乎无代价（数量级对即可）           |
| **防御型**（防谁）        | HTTP 超时、连接超时                | 对端的 P99，不是平均值                 | 误杀慢请求 / worker 被拖死      |
| **耦合型**（被别的参数约束）   | 租约时长、认领批大小                  | 由其他参数**推导**，没有自由度             | 双投率暴涨 / 自己制造重复          |
| **容量型**（为多少负载）     | worker 数                    | 正常态 Little's Law + 故障态放大 + 熔断兜底 | 排队 / 资源浪费               |

推完之后每一项都要做两件事：**写进启动自检**（破坏约束直接拒绝启动）和**列入上线校准表**（实测对比，偏差超 3 倍重估）。

## 2. 参数之间的约束关系（先看这张图，绝对值是次要的）

```
connectTimeout(3s) < httpTotalTimeout(15s) « lease(60s)
                      ▲                      │
                      │                      │ lease 必须覆盖"一次认领的完整占用"
                      │                      ▼
                 支撑 SLA: 送达 p99 < 5s   lease ÷ 2 ≈ 轮询×批次 的供给节奏要跟上消费速率
                                             │
              max_attempts(10) × 退避曲线 ≈ 业务补偿窗口(≥3.5h)
                                             │
              batchSize ≤ min(空闲worker数, 每周期补给需求)
                                             │
              worker(200) 覆盖故障态并发, 再往上交给熔断
                                             │
              背压阈值 = 用"消化时间"表达, 不用条数表达
```

三条硬不等式（违反即事故，写进 T0.3 启动断言）：

1. `lease > httpTotalTimeout + 落库余量` —— 否则双投率暴涨；
2. `batchSize ≤ 当前空闲 worker 数` —— 否则认领后排队等租约过期，自己制造重复；
3. `重试总覆盖时间 ≥ 业务补偿窗口` —— 否则"自动重试"形同虚设，人工重放常态化。

## 3. 逐参数推导

### 3.1 轮询间隔：500ms —— 体验型，数量级正确即可

**推导**：
- 上界（SLA 配额）：送达 p99 < 5s 的预算里，分给"队列等待"的部分取 ~10%，即 ~500ms。轮询延迟直接叠加在每一条通知上，它是 p50 的大头（正常投递本身只要 200ms）；
- 下界（成本）：8 实例 × 2 次/秒 = 16 QPS 的索引扫描（走 `idx_due`，覆盖索引，微秒级），就算 100ms 间隔成本也不构成压力——**但缩短到 100ms 买不到任何东西**，因为下游投递本身要 200ms；
- 区间结论：100ms ~ 2s 内这个参数"错了也无所谓"。选 500ms 是区间中点。

**反直觉点**：这个参数精确到"数量级"就够，**不值得为它做优化**（这正是 hint 唤醒被否掉的原因——为省 240ms p50 引入第二条认领路径）。设计文档里真正要写的是"为什么 500ms 已足够"，而不是"为什么正好是 500"。

### 3.2 HTTP 总超时 15s / 连接超时 3s —— 防御型，按对端 P99 设

**推导**：
- **按 P99 不按均值**：正常供应商 API p99 < 1s。超时是防御参数，要覆盖的是对端 GC 停顿、慢查询抖动这类尾部，15s ≈ 15×P99 余量；
- **连接超时单独设短**：TCP 握手正常 <100ms，连接卡住 = 网络不通或对端假死，等再久也不会成功。3s 已是握手正常值的 30 倍；
- **两个方向的代价不对称**：超时太短 → 误杀"慢但会成功"的请求，代价 = 一条完整重试（下一条又要 200ms + 占额度）；超时太长 → worker 槽位被占，代价 = 其他通知排队。**通知系统的 worker 是稀缺资源，所以宁可误杀、不让 worker 挂着**——这决定了余量取 15× 而不是 100×；
- **不是独立值**：它被 lease 约束（见 3.3），被熔断约束（连续超时会快速累计失败率触发 OPEN）。

**校准**：上线一周后取真实 p99，若 p99 < 500ms 且误杀率 > 0.1%，把总超时降到 8s。

### 3.3 租约 60s —— 耦合型，没有自由度

**推导**：`lease > httpTotalTimeout(15s) + 结果落库(~50ms) + 调度/时钟抖动`。数学下限 ~16s，工程上取 **2× 超时 = 30s 起步**，再为 GC 长停顿、网络黑洞这类"进程活着但不干活"的场景放大到 **60s**。

**两个方向的代价**（这就是为什么它没有自由度）：
- 太短：A 还在投（比如卡在 15s 超时边缘），B 已认领重投 → **双投率直接由 lease/timeout 的比值决定**。lease=20s、timeout=15s 时，每次慢投递都有 ~25% 概率撞车；
- 太长：worker 被 `kill -9` 后，那条任务要等 lease 过期才能被接手 → **崩溃恢复延迟上限 = lease 时长**。60s 意味着单实例崩溃的最坏恢复是 1 分钟——这在异常路径上，不影响 p99 SLA，可接受。

**结论写法**：设计文档里这个值的推导式比值本身重要——`lease = f(timeout)`，timeout 变它就跟着变，两个数字必须一起改，所以用启动断言锁死关系。

### 3.4 认领批大小 —— 耦合型，由两个不等式夹出来

**推导**：
- **硬上界**：`batchSize ≤ 空闲 worker 数`（§2 不等式 2）。认领 100 条但只有 30 个空闲 worker → 70 条占着 `PROCESSING` 等租约过期重领，是自己制造重复投递；
- **需求上界**：每个轮询周期需要补给的量 = 有效 QPS × 轮询间隔 = 172 × 0.5s ≈ **86 条**。批大小超过这个值纯粹浪费；
- **事务代价**：认领是短事务，`SKIP LOCKED` 持锁行数 = batch 大小。100 行 ~ 毫秒级无感；1000 行开始与接入写入竞争锁区间。

**结论**：`batchSize = min(100, 空闲worker数)`，运行时取小，配置上限 100 只是防呆。**注意它不是"调优参数"——两个不等式已经把解空间夹得很窄，剩下唯一自由度是"要不要低于需求"，而低于需求只影响供给节奏，下一轮就补上了。**

### 3.5 worker 数 200 —— 容量型，按故障态设而不是正常态

**推导分三步**：

1. **正常态（Little's Law）**：L = λ × W = 172 QPS × 0.2s ≈ **34 并发**。这是下限，只保证"队列不积压"；
2. **故障态放大**：并发需求与下游耗时成正比。供应商整体变慢 5 倍（0.2s→1s）→ 需要 172 并发。**按"整体慢 5 倍"而不是"全部超时"设计**——全部卡满 15s 超时（需 2580 并发）的场景不该用 worker 数兜底，那是熔断的职责（失败率超阈值 → OPEN → 任务推迟且不计次）。worker 数只覆盖"局部慢"，"整体死"交给熔断；
3. **资源核算**：200 平台线程 ≈ 200MB 栈内存，可接受。**关键解耦**：worker 不各持 DB 连接——只在认领和落库两个瞬间借还，连接池 20–30 就够。**worker 数与连接数解耦，是"能用 200 个 worker"的前提**。

**反直觉点**：worker 数不是越大越安全。3000 个 worker 遇到全局故障时是 3000 个并发请求同时打向刚恢复的供应商——惊群把对方再打挂一次。worker 数的上限由"对下游的最大并发压力"反向约束，200 恰好也是"恢复期惊群可接受"的量级。

#### 3.5.1 常见疑问：为什么不定义少量 worker，让单 worker 做内部并发？

**先厘清**：真正的资源约束是"同时在途投递数 ≤ 200"，这个上限由需求（容量推导）决定，不随实现改变。"少量 worker + 内部并发"只是把上限的实现位置从**线程数**挪到**事件循环里的 in-flight 计数器**——问题实质是并发上限放在线程模型还是事件模型里。

**为什么不选事件模型（V0）**：

1. **省的东西不值钱**：200 平台线程 ≈ 200MB 栈内存；且 JDK HttpClient 内部本就是异步 selector 事件循环，线程只是同步等待，不占连接也不占 CPU；
2. **正确性从免费变自费**：不变式 `batchSize ≤ 空闲 worker` 在"一投递=一线程"模型里由 JVM 线程池天然维护；事件模型下要自己实现 in-flight 计数 + 背压，并新增"回调泄漏导致容量静默缩水"的故障模式。砍了那么多机制，不为省 200MB 再请一个回来；
3. **可调试性是本质差距**：线程模型里卡住的投递 `jstack` 直接可见；事件模型里表现为"永不触发的回调"，栈里不可见——与"单号一查到底"（§4.11）的运维承诺直接冲突；
4. **不减少任何真实消耗**：瓶颈是对端延迟和 DB 认领。两种模型下每条投递的认领事务、HTTP、落库次数完全相同，DB 连接池与 worker 数已解耦——省线程只是省栈内存；
5. **升级路径现成**：换 Java 21 虚拟线程，执行器一换、代码不改，内存成本趋近于零——虚拟线程让"线程 vs 事件"的争论在 Java 里基本消失。V0 拿线性代码的可读性，不必预支事件模型的复杂性。

**翻案条件**：在途投递 > 2000、或 200MB 线程栈成为单机内存约束 → 第一步是换虚拟线程（零改码），仍不够才考虑事件模型；事件模型的真正主场是"单机数万连接、数万 host"的量级——那属于 §8 V2 演进范畴。

> 一句话：**并发上限是需求决定的，实现只决定这个上限由谁来数——JVM 线程池替我数，比我自己写计数器可靠。**

### 3.6 最大重试次数 10 —— 业务型，从补偿窗口倒推

**推导**：这是五个参数里唯一从"业务在等什么"出发的：

1. **先定业务容忍**：付款通知 CRM 失败后，多久之内自动恢复算可接受？人工发现（告警）→ 修复（凭证/网络）→ 期望系统自愈的窗口，保守取 **3–4 小时**。超过就等人工重放（`DEAD` 可见 + 单条 replay）；
2. **退避曲线倒推次数**：`sum(base × 2^(n-1)) × jitter均值`，base=10s、cap=1h 时，10 次累计覆盖 **~3.5h** ✓。**次数是"窗口 ÷ 曲线"的解，不是独立 chosen 的数字**——改 base 或 cap，次数就得重算；
3. **cap 的作用**：没有 cap，指数曲线到 20 次时单次间隔达天级——系统该在"小时级"把控制权交还人工，而不是假装还在自动恢复。cap=1h 让尾部重试保持小时节奏；
4. **为什么不是 3 次**："重试 3 次"是 Web 同步调用的直觉（用户在等）。这里"用户"是对账系统，一天后才看结果，自动重试的价值就是"人工介入前多撑几小时"。同时注意：**10 次预算只花在可重试错误上**——4xx 一次都不花（§4.4），所以 10 并不激进。

**校准**：这个参数和 3.1 的超时不同，它没有"实测对端 P99"可校准，校准依据是**死信里 TIMEOUT/5xx 的占比**——占比高说明窗口不够，业务方真的在大量人工重放，就把窗口拉长。

### 3.7 顺带：背压阈值 —— 用消化时间表达，不用条数

PENDING > 10 万、最老任务 > 30min 触发 503。这两个数的角度：

- **10 万条的正确读法是 "~10 分钟消化时间"**（10 万 ÷ 172/s）：低于消费速率的瞬时尖峰会自己排空，不值得拒绝；持续高于产能 10 分钟才说明是产能问题——503 让上游减速是正确反应；
- **30min 最老年龄**：p99 SLA（5s）的 360 倍，含义是"系统已明显偏离承诺"。用**与 SLA 的偏离倍数**定阈值，比拍一个分钟数有依据。

**方法论**：容量相关阈值尽量用**时间**（消化时间、年龄）而不是**数量**表达——数量随容量失效，时间不会。

## 4. 哪些数字精调有价值，哪些没有

| 参数              | 精调价值 | 说明                                                        |
| --------------- | ---- | --------------------------------------------------------- |
| lease vs timeout 比值 | **高** | 直接决定双投率，必须用断言锁死                                           |
| batchSize vs 空闲 worker | **高** | 违反即自我制造重复投递                                               |
| 次数 × 退避 ≈ 补偿窗口   | **高** | 决定"自动恢复"是否名副其实                                            |
| 轮询间隔             | 低    | 100ms~2s 区间内无感，数量级对即可                                     |
| worker 绝对值       | 低    | 100~500 区间内都被熔断兜底；真正要写进文档的是"它覆盖故障态、熔断兜底极端态"的分工           |
| 超时绝对值            | 中    | 15×P99 起步即可，上线按实测降                                        |

> 把"精调价值"想清楚是避免过度设计的一部分：文档里为低价值参数写长篇论证，和为想象需求建机制是同一种错误。

## 5. 上线校准：每个数字的复核信号

| 参数         | 校准信号                            | 动作                        |
| ---------- | ------------------------------- | ------------------------- |
| 轮询间隔       | 实际 p50 受理→送达                    | 若 > 1s 且投递本身 < 300ms，查调度而非缩间隔 |
| HTTP 超时    | 误杀率（超时后人工确认下游实际成功）> 0.1%        | 降超时或分级超时                  |
| lease      | zombie 计数持续 > 0（旧结果被丢弃）         | 说明 lease < 真实长尾耗时，按观测放大   |
| batchSize  | 认领返回 0 行但 `idx_due` 有到期任务（供给不足） | 查锁竞争，而不是盲目加大批             |
| worker     | 正常态并发长期 < 50                    | 缩池省内存；或确认量级假设偏差           |
| max_attempts | DEAD 中 TIMEOUT/5XX 占比高 + 人工重放频繁 | 拉长补偿窗口（加次数或 cap）          |
| 背压阈值       | 503 后上游是否真有减速行为                 | 无则阈值形同虚设，需要推动接入方实现退避      |

**总原则**：所有参数分两层——**推导层**（业务容忍 → SLA → 约束不等式 → 数值）写进设计文档，**校准层**（观测信号 → 调整动作）写进运维手册。数值本身都会变，推导链和约束关系不会。
