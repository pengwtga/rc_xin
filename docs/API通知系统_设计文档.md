# API 通知系统设计文档

> 对应作业要求的「README 或设计文档」。
> 本文档回答三件事：**系统边界**、**可靠性与失败处理**、**取舍与演进**。原则：先给判断，再给机制；每个机制都注明为什么、代价是什么。
> 配套两份：`docs/文档与代码校验记录.md`（本文逐节与代码对账的结果——11 处修正、3 处仍未解决的缺口），`docs/API通知系统_参数定值依据.md`（每个数字的推导链与约束不等式，正文只写结论）。

---

## 0. 一句话结论

这是一个**可靠出站 HTTP 投递**问题，不是消息总线问题。核心只有三件事：

1. **请求先落盘** —— 不丢；
2. **投递有租约** —— 不重复卡死；
3. **失败有分级** —— 不白重试。

其余一切（模板渲染、业务编排、多租户、可视化后台）都在边界之外。

---

## 1. 问题理解

### 1.1 本质抽象

需求描述里的三个业务场景（广告归因、CRM 状态同步、库存变更）指向同一个技术抽象：

```
业务系统 --(已渲染好的 HTTP 请求)--> [本系统] --(尽可能可靠地)--> 外部供应商 API
```

### 1.2 三个关键事实 → 设计含义

| 需求中的事实                         | 设计含义                                                 |
| ------------------------------ | ---------------------------------------------------- |
| 业务系统**不关心返回值**                 | 无需同步等待结果 → 接入侧只做"已接收"确认，投递完全异步                       |
| 但业务系统**关心"有没有送达"**             | 不能 fire-and-forget 返回 200，必须有可查询的投递状态与唯一单号           |
| 外部 API **地址/Header/Body 各不相同** | 本系统不做格式转换，只做**透传**；格式化责任在业务侧。一旦做模板渲染就变成半个业务中台，**不做** |

### 1.3 由场景反推出的硬约束

1. **不能丢**：付款通知 CRM 失败 = 用户付了钱状态没同步，丢一条的代价远高于多投一条；
2. **不能卡死**：某供应商挂 3 小时，不能拖垮其他供应商的投递，也不能拖垮接入侧；
3. **不能重复放大**：外部系统大多不幂等，不能"为了可靠"把一个 400 重试成雪崩；
4. **必须可追责**：出问题要能回答"这条投了几次、每次返回什么、为什么还在重试"；
5. **调用方可能超时重试**：同一事件不能变成两条通知。

### 1.4 一处需求没说、但设计绕不开的信息

**企业内到底几个业务系统？与外部供应商是否一一对应？** 需求只说"多个业务系统"，三个例子是事件清单而非系统清单。我不猜这个答案，而是让设计不依赖它：`caller_id` 定义为**提交身份**（一个 API Key + 一个限流域 + 一个归因标签），不是部署单元——内部是 1 个还是 3 个系统，只是"注册几个 Key"的接入动作，不改结构。接入前需向业务方确认（见 §10）。

## 2. 系统边界

### 2.1 我解决的问题

| #   | 问题      | 解决到什么程度                   |
| --- | ------- | ------------------------- |
| 1   | 请求持久化   | 接入即落库，返回后进程崩溃也不丢          |
| 2   | 异步投递    | 独立投递引擎，与接入侧解耦             |
| 3   | 失败重试    | 按错误类型分级 + 指数退避 + 重试预算     |
| 4   | 崩溃恢复    | 租约机制，worker 挂掉后任务被重新认领    |
| 5   | 端点隔离    | 单供应商故障不影响其他供应商（并发隔离 + 熔断） |
| 6   | 重复提交防护  | 调用方幂等键去重                  |
| 7   | 最终失败兜底  | 死信状态 + 告警 + 人工重放          |
| 8   | 可观测与可追责 | 状态查询、逐次投递记录、核心指标          |
| 9   | 出站安全    | SSRF 防护、凭证加密存储            |

### 2.2 我明确不解决的问题（及理由）

| 不解决                  | 理由                                                          |
| -------------------- | ----------------------------------------------------------- |
| **端到端 exactly-once** | 物理上不可能：下游已处理但响应超时时只能重试。改为契约：我保证**至少一次** + 下游按幂等标识去重         |
| **下游业务是否真的生效**       | 只能观测 HTTP 层。CRM 返回 200 但内部写库失败是 CRM 的问题，做业务对账即越界            |
| **消息顺序保证**           | 异步重试本身就会乱序，传输层任何顺序保证都让下游免不了版本判断（推导见 §4.9）。顺序由下游按业务版本号/时间戳收敛 |
| **请求内容转换 / 模板渲染**    | 业务系统已知道供应商格式，多一层转换就多一处需同步维护的契约，收益只是省一次序列化                   |
| **供应商探活与 SLA 管理**    | 不是监控系统，只做被动的失败率统计与熔断                                        |
| **重试策略可视化编排**        | 首版配置文件 + 预设参数。规则引擎是典型过度设计                                   |
| **按业务优先级排队**         | 首版先到先投。等真的出现"营销挤占付款"的事故再分级，那时才有数据支撑                         |
| **多租户计费 / 配额结算**     | 内部系统，限流只为保护自身                                               |

### 2.3 一条必须讲清的边界线

> **可靠性止于「送达」，一致性由下游负责。**

我保证：供应商返回 2xx 即标记成功；没拿到 2xx 就按策略继续尝试。
我不能保证：供应商收到两次时只处理一次。**但"下游能识别重复"这件事由我方强制提供，不靠调用方自觉**——每次投递由投递器注入两个身份头：

| 头                   | 值                       | 来源                                                             |
| ------------------- | ----------------------- | -------------------------------------------------------------- |
| `X-Notification-Id` | 我方单号（`notification.id`） | 认领回读；重复投递时两次的值**完全相同**，下游可据此判重与回传对账                            |
| `X-Idempotency-Key` | 调用方业务幂等键                | 提交时入库的 `idempotency_key`，**不要求调用方再塞进 `headers`**——要求调用方记得传等于没做 |

三个实现细节：① 注入点收敛在 `HttpDeliverer`（线上发什么头只看一个类），与固定 `User-Agent` 同处；② 调用方自带同名头会被我方值**取代**而不是拼成两个值——下游拿到两个值等于没有去重键；③ 其余调用方 header 仍原样透传（`host`/`content-length`/`connection` 跳过）。

**边界**：我方只负责"给出去重标识"，**不保证下游真的按它去重**。语义仍然是 at-least-once；是否幂等是下游的契约义务，写进接入规范，不由本系统代劳。

## 3. 整体架构

### 3.1 组件视图

```
                    ┌──────────────────────────────────────────────┐
 业务系统 A ─┐      │  接入层 Ingest API                            │
 业务系统 B ─┼─────▶│  · 鉴权(API Key) · 校验 · 幂等去重 · 背压(503)  │
 业务系统 C ─┘      │  · 落库 → 202 Accepted + notification_no      │
                    └───────────────────┬──────────────────────────┘
                                        │ 写
                    ┌───────────────────▼──────────────────────────┐
                    │  MySQL（唯一事实来源）                         │
                    │  notification / delivery_attempt / replay_log │
                    └───────────────────┬──────────────────────────┘
                                        │ 认领（SKIP LOCKED + 租约）
                    ┌───────────────────▼──────────────────────────┐
                    │  投递引擎 Dispatcher（可多实例水平扩展）        │
                    │  · 到期扫描(poll 500ms) → Worker Pool          │
                    │  · 按端点并发隔离 · 超时预算 15s · 熔断 per endpoint │
                    │  · 失败分类 → 退避 → 重排 / 死信                │
                    └───────────────────┬──────────────────────────┘
                                        │ HTTPS
                              ┌─────────▼──────────┐
                              │ 外部供应商 API      │
                              └────────────────────┘

 旁路：查询/重放 API · 指标(Prometheus) · 死信告警
```

**关键点**：接入层与投递引擎之间**没有 MQ**，靠数据库表衔接——理由见 3.4。

### 3.2 技术栈

| 组件    | 选择                          | 理由与替代                                                                                                 |
| ----- | --------------------------- | ----------------------------------------------------------------------------------------------------- |
| 语言/框架 | Java 21 + Spring Boot 3.3.5 | 我最熟的技术栈（作业不限）；同样可用 Go/Python，选型结论不变。服务本体是固定线程池 + 阻塞 HTTP，虚拟线程只用在上压测器里（`scripts/loadgen/LoadGen.java`） |
| 存储    | MySQL 8.0（InnoDB）           | 既是状态存储也是队列载体（SKIP LOCKED 需 8.0+）；替代是 PostgreSQL（同样支持 SKIP LOCKED，等价）                                  |
| 投递客户端 | JDK HttpClient              | 自带连接池与超时控制；不需要 Apache HttpClient 的多段读超时（总超时已覆盖，多一个依赖多一类故障）                                            |
| 指标/告警 | Micrometer + Prometheus     | 内部系统标配；不引入 APM/链路追踪（链路只有 2 跳，见 §6.2）                                                                  |
| 配置    | application.yml + 环境变量      | 退避参数、租约时长、池大小全部可配置，代码内无魔法数                                                                            |

### 3.3 一次投递的完整生命周期

```
1. 业务系统 POST /v1/notifications
   Header: X-Api-Key, Idempotency-Key: order_paid:pay_20261028_001
   Body:   { target_url, method, headers, body }

2. 接入层：鉴权 → 背压判定 → SSRF 静态校验 → method/headers/body 校验 → 加密 → INSERT
   ├─ (caller_id, idempotency_key) 已存在 → 返回 202 + 原单号（不新建：靠唯一键冲突兜住，不是先查后插）
   └─ 不存在 → INSERT status=PENDING, next_attempt_at=now
   → 202 Accepted { notification_no, status: "PENDING" }

3. Dispatcher 每 500ms 认领到期任务（SQL 见 §4.3）

4. Worker 执行 HTTP 调用（connect 3s / total 15s 预算）
   注入身份头 X-Notification-Id（单号）/ X-Idempotency-Key（调用方幂等键），其余调用方 header 透传
   记录 delivery_attempt（状态码、耗时、错误分类、响应片段 2KB）

5. 结果分支：
   2xx                     → SUCCEEDED
   3xx / 4xx（除 408/429）  → DEAD（永久失败，立即告警，不浪费重试预算）
   408/429/5xx/超时/网络错   → RETRY_WAIT + next_attempt_at = now + backoff(n)
   尝试次数超预算            → DEAD
   熔断中 / 端点并发已满      → 退还（attempt_count-1、不写明细），推迟 next_attempt_at
   端点被 SSRF 策略拒绝      → DEAD（error_class=SSRF_BLOCKED，一次即死）

6. 最终失败：GET 状态详情（含每轮 attempt）→ 人工 replay → 回到 PENDING
```

### 3.4 为什么用「数据库即队列」，第一版不上 MQ

1. **量级不需要**：估算峰值 ~170 QPS（推导见 §7），单实例 MySQL 的写入余量约 **4.3 倍**（每单 4 写、600 行/秒实测，§7 已按实测修正），估算偏差 3 倍以内不改变结论；
2. **少一个系统 = 少一类故障**：上 MQ 要处理"写 MQ 成功但 DB 写失败"的双写一致性，排查链路从两段变三段，还要养一套集群；
3. **瓶颈不在接入写入**：MQ 解决削峰和广播，这里的瓶颈是下游 HTTP 延迟，削峰只是把排队位置从表挪到 broker；
4. **SKIP LOCKED + 租约 = SQS 最核心的两个语义**（并发消费不重复 + 崩溃后可见性恢复），一段 SQL 自己实现。剩下 80% 的 MQ 能力（削峰、广播、多消费组）本量级用不上。

**代价（写在明面上）**：轮询 500ms 延迟（"秒级送达"够用）；DB 承担队列读写，量级涨 10 倍必须换（§8）。

**翻案条件**：日投递 > 1000 万，或出现多消费方（审计/计费）需求 → 按 §8 V2 演进（outbox + Kafka），不改现有表契约。

## 4. 核心设计

### 4.1 数据模型

```sql
CREATE TABLE notification (
  id               BIGINT UNSIGNED   NOT NULL AUTO_INCREMENT COMMENT '唯一单号，对外直接暴露（内部系统 + API Key 鉴权，无枚举风险）；不引入 ULID 等第二套标识',
  caller_id        VARCHAR(64)       NOT NULL COMMENT '调用方标识，由 API Key 解析；用于鉴权、幂等域、限流与数据隔离',
  idempotency_key  VARCHAR(128)      NOT NULL COMMENT '调用方填的事件级幂等键，建议 <事件类型>:<事件唯一ID>，如 order_paid:pay_001',
  target_url       VARCHAR(2048)     NOT NULL COMMENT '外部供应商 API 地址，落库前经 SSRF 校验',
  http_method      VARCHAR(8)        NOT NULL DEFAULT 'POST' COMMENT '白名单 POST/PUT/PATCH/DELETE/GET',
  headers_enc      VARBINARY(4096)   NULL     COMMENT '含凭证的 Header 经 AES-256-GCM 加密存储，密钥由部署环境注入；查询接口脱敏返回，日志不打印',
  body_enc         MEDIUMBLOB        NULL     COMMENT '请求体加密存储（注意用 MEDIUMBLOB 而非 VARBINARY(65535)：后者计入 InnoDB 65535 字节行上限会建表失败，错误码 1118）；成功 24h / 失败 7d 后由归档任务清除（PII 最小留存）；查询接口只回 has_body，不回内容',
  status           VARCHAR(16)       NOT NULL DEFAULT 'PENDING' COMMENT 'PENDING/RETRY_WAIT/PROCESSING/SUCCEEDED/DEAD/CANCELED',
  attempt_count    SMALLINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '累计尝试次数，认领时自增；达到 max_attempts 转 DEAD',
  max_attempts     SMALLINT UNSIGNED NOT NULL DEFAULT 10 COMMENT '重试预算，按调用方配置（默认 10）；与 attempt_count 同类型，重放时两者相加不会溢出',
  next_attempt_at  DATETIME(3)       NOT NULL COMMENT '下次可投递时刻（UTC）；退避、熔断推迟都改这个字段',
  lease_owner      VARCHAR(64)       NULL     COMMENT '租约持有者 = 实例ID/轮次token（如 a1b2c3d4e5f6/7f3a9c21）；标记"哪一次认领"而非哪台机器，既用于回读本轮行，也是状态落库的守卫键',
  lease_until      DATETIME(3)       NULL     COMMENT '租约到期时刻（UTC）；过期即可被重新认领',
  last_error_class VARCHAR(32)       NULL     COMMENT 'TIMEOUT/DNS/TLS/CONN_REFUSED/HTTP_4XX/HTTP_5XX；告警路由依据',
  last_status_code SMALLINT          NULL     COMMENT '最近一次 HTTP 状态码',
  created_at       DATETIME(3)       NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  updated_at       DATETIME(3)       NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_idem (caller_id, idempotency_key) COMMENT '接入幂等：同调用方同业务键只允许一条',
  KEY idx_due   (status, next_attempt_at) COMMENT '到期任务扫描',
  KEY idx_lease (status, lease_until)      COMMENT '租约过期回收'
) ENGINE=InnoDB COMMENT='通知任务表 —— 本身即队列';

CREATE TABLE delivery_attempt (
  id               BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  notification_id  BIGINT UNSIGNED NOT NULL COMMENT '关联 notification.id',
  attempt_no       SMALLINT UNSIGNED NOT NULL COMMENT '全局第几次尝试（跨重放继续递增，与 attempt_count 一致，因此重放不会撞唯一键）',
  started_at       DATETIME(3)     NOT NULL,
  duration_ms      INT             NULL,
  status_code      SMALLINT        NULL COMMENT '网络层失败时为 NULL',
  error_class      VARCHAR(32)     NULL,
  response_snippet VARCHAR(2048)   NULL COMMENT '响应体前 2048 字符截断存储',
  created_at       DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3) COMMENT '明细写入时刻（UTC）；与 started_at 的差即"投递结束到落库"的延迟',
  PRIMARY KEY (id),
  UNIQUE KEY uk_n_attempt (notification_id, attempt_no),
  KEY idx_n (notification_id)
) ENGINE=InnoDB COMMENT='逐次投递明细 —— 只追加，用于追责与排查';

CREATE TABLE replay_log (
  id                   BIGINT UNSIGNED   NOT NULL AUTO_INCREMENT,
  notification_id      BIGINT UNSIGNED   NOT NULL COMMENT '被重放的通知；不建外键（同 delivery_attempt）',
  operator             VARCHAR(64)       NOT NULL COMMENT '操作人，缺省为调用方标识；统一小写存储',
  reason               VARCHAR(512)      NOT NULL COMMENT '重放原因，人工填写且必填（422）',
  attempt_count_before SMALLINT UNSIGNED NOT NULL COMMENT '重放时的累计尝试次数快照——attempt_count 不归零的证据',
  max_attempts_after   SMALLINT UNSIGNED NOT NULL COMMENT '重放后的预算（attempt_count_before + 当前档位）',
  created_at           DATETIME(3)       NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  KEY idx_n (notification_id)
) ENGINE=InnoDB COMMENT='人工重放审计 —— 只追加；与投递事实(delivery_attempt)分开存，查单详情直接读它补时间线';
```

第三张表是 T3.2 补的，理由见 §4.6：**重放动作没有发出任何 HTTP，塞进 `delivery_attempt` 既不是事实，还会破坏"`attempt_no` 与 `attempt_count` 一致"这条不变式**。

两个容易写错的地方，提前定死：

- `attempt_count` 在**认领时**自增，不在完成后——worker 崩溃时没人执行"完成后自增"，毒消息会无限循环；
- `attempt_no` 采用**全局递增**编号而非每轮重放重新从 1 计数——重放时天然不撞 `uk_n_attempt` 唯一键，省掉一套"重放轮次"字段。

#### 为什么明细要单独一张表（先承认：原始需求没要明细）

原始需求只说了两件事：把请求送达、业务方不关心返回值。逐次明细确实不在需求文字里，`last_status_code` / `last_error_class` 已经能回答"最后一次怎么样"，**最严格的单表实现是可成立的**。保留第二张表的理由不是"以后可能有用"，而是需求里那句"业务方不关心返回值"实际做了一次责任转移：**返回值只有我们看得见，于是"到底送到没有、发了几次"的答案只能来自我们**。

而这个答案在 at-least-once 语义下天然有争议：需求举的三个例子——广告归因、CRM 状态、库存变更——**没有一个是幂等安全的外部动作**（库存扣两次就是事故）。一旦下游来问"这两次请求是你们发的吗、什么时候发的"，只有 `notification` 一行 + `last_*` 是答不出来的（它被最后一次覆盖），而明细表能给出完整时间线与次数证据。同样，§4.6 说重放决策"只有人能判断"，人要判断就得看得到每次的状态码，而不是最后一次。

成本侧也做了一次一致性检查：我砍掉的机制（信封加密、`replay_epoch`、批量重放）都**引入了新的状态机/路径/配置**；明细表没有——一张 7 列的只追加表 + 一个 `INSERT`，不进热路径、不被认领 SQL 触及。**"多存一份事实"和"多造一个机制"不是一个量级的复杂度。**

**合并条件**：若确认运维只需要回答"送达 / 未送达 + 最后一次原因"，删掉 `delivery_attempt`，只留 `last_*` 三个字段即可，T3.1 的返回结构相应简化。这张表删得掉、没有调用方依赖它的存在——**可删除的独立表不是"预埋钩子"**。

### 4.2 状态机

```
        ┌──────────┐  claim   ┌────────────┐  2xx   ┌───────────┐
   ────▶│ PENDING  │─────────▶│ PROCESSING │───────▶│ SUCCEEDED │
        └────┬─────┘          └─────┬──────┘        └───────────┘
             │                      │ 可重试失败
             │                      ▼
             │              ┌──────────────┐  退避到期 / 重新 claim
             │              │  RETRY_WAIT  │────────┐
             │              └──────┬───────┘        │
             │                     │ 超预算/永久失败 │
             │                     ▼                │
             │              ┌──────────────┐        │
             └─replay───────│     DEAD     │────────┘
                            └──────────────┘
   PROCESSING 且 lease_until < now → 可被重新 claim（崩溃回收）
```

`SUCCEEDED` 是**真终态**（只有它没有回头路）；`DEAD` 是终态但**可被人工重放**回 `PENDING`——重放的守卫就是 `WHERE status='DEAD'`，对 `SUCCEEDED` 重放会返回 409（§4.6）。其余状态（`RETRY_WAIT` / `PROCESSING`）都是过渡态，由调度与租约自动推进。

`CANCELED` 在枚举与查询/归档里都留了位置，但**本版没有任何写入路径产生它**——它预留给"调用方撤销"这一尚未确认的需求（§10）。写在这里是为了让读代码的人知道：看到 `CANCELED` 不是 bug，但也不该指望能造出来。

### 4.3 任务认领：SKIP LOCKED + 租约

多实例从同一张表取任务，不能直接 `SELECT`（会拿到同一批重复投递）。三种做法对比：

| 做法                       | 行为        | 问题                                |
| ------------------------ | --------- | --------------------------------- |
| 普通 SELECT                | 不加锁       | 重复消费，不可用                          |
| `FOR UPDATE`             | 选中行打排他锁   | 实例间阻塞等待，吞吐被串行化                    |
| `FOR UPDATE SKIP LOCKED` | 碰到已锁行直接跳过 | 无——多实例拿到的行集合互不相交且无等待，横向扩展退化为"加机器" |

完整认领 SQL：

```sql
UPDATE notification
SET status        = 'PROCESSING',
    lease_owner   = :instanceId,
    lease_until   = DATE_ADD(NOW(3), INTERVAL 60 SECOND),
    attempt_count = attempt_count + 1
WHERE id IN (
  SELECT id FROM (
    SELECT id FROM notification
    WHERE (status IN ('PENDING','RETRY_WAIT') AND next_attempt_at <= NOW(3))
       OR (status = 'PROCESSING' AND lease_until < NOW(3))   -- 崩溃回收就在这一行
    ORDER BY next_attempt_at
    LIMIT :batchSize
    FOR UPDATE SKIP LOCKED
  ) t
);
```

第二个 `OR` 分支**不是特殊的恢复路径**：租约过期的任务和到期任务一样可认领。整个崩溃恢复机制就是这一个条件——没有清理定时任务、没有补偿脚本。

关键时序（A 崩溃、B 接手）：

```
t=0    A 认领 #42，lease_until = t+60
t=3    A 投递中 → 进程被 kill
t=60   租约过期，任务仍 PROCESSING
t=60.x B 认领 #42（attempt_count=2）→ 重新投递 → 供应商可能收到两次
```

**租约保证"不丢"，不保证"不重"**。"请求已发出、结果未落库"之间崩溃的窗口物理上无法消除——这正是投递语义必须是 at-least-once 的根本原因。

五条实现约束（违反任何一条都会出事故）：

1. **`lease_until` 必须 > HTTP 总超时 + 余量**（60s vs 15s，余量断言取 5s → `StartupGuard` 要求 `lease > total + 5s`），否则双投率暴涨。启动时断言，不满足拒绝启动；
2. **认领事务里绝不放 HTTP 调用**——先认领提交事务，再投递。否则一条 15s 请求占着连接，几十个 worker 就耗尽连接池；
3. **租约时间用数据库 `NOW()`，不用应用时钟**——多实例时钟漂移是最隐蔽的重复投递来源；
4. **`batchSize ≤ 当前空闲 worker 数`**——认领 100 条但只有 30 个空闲 worker，剩下 70 条等租约过期被重领，是自己制造重复；
5. **落状态必须带 `lease_owner` 守卫**——投递耗时超过租约时（GC 停顿），旧 worker 的结果已过期，守卫失败（影响 0 行）就丢弃结果并计数，绝不覆盖新结果。

**崩溃恢复没有独立机制**：没有清理定时任务、没有补偿脚本，"租约过期即可认领"这一个条件就是全部。语义上限是 at-least-once——"请求已发出、结果未落库"的窗口物理上消不掉，"不重"必须由下游的幂等键兜住。相关取舍（为什么不做心跳续约、为什么崩溃必须消耗一次尝试预算、为什么守卫键是"这一次认领"而不是"这台机器"）见 docs/T2.2-租约与崩溃恢复.md §2。

**停机要走优雅路径**：`shutdownNow()` 中断在途请求等于主动制造"结果未落库"，每次滚动发布都会有一批任务在租约过期后被重投；应先停止收新任务、等待在途投递自然结束（上限 `totalTimeout + 1s`，且必须 < 租约），超时才强杀。崩溃是意外，停机是日常，日常不该付意外的代价。

### 4.4 失败分级决定重试策略

| 结果                                | 分类        | 处理                                                   | 依据                                                                                      |
| --------------------------------- | --------- | ---------------------------------------------------- | --------------------------------------------------------------------------------------- |
| 2xx                               | SUCCESS   | 标记成功                                                 | —                                                                                       |
| 3xx（投递器禁重定向，故不会自动跟随）              | PERMANENT | **直接 DEAD，不重试**                                      | 目标地址已变或被转去登录页，属配置问题；重试 10 次只会拿到同一条 302                                                  |
| 4xx（除 408 / 429）                  | PERMANENT | **直接 DEAD，不重试**；401/403 立即告警                         | 请求本身有问题，重试 10 次结果一样，只会放大告警。**没列出的 4xx 一律按此兜底**（409/410/451 同样一次即死）——错杀可人工重放（可逆），烧光预算不可逆 |
| 408 / 429 / 503                   | RETRYABLE | 重试，**优先遵守 `Retry-After`**（不抖动，只 clamp 到 `[1s, cap]`） | 对方明确表示"稍后再来"。503 单列是因为它常带 `Retry-After`，而不是因为它"不算 5xx"                                  |
| 5xx（除 503）/ 超时 / 连接拒绝 / DNS / TLS | RETRYABLE | 重试                                                   | 对方内部故障或网络问题，可能自愈                                                                        |
| SSRF 策略拒绝（请求一个字节都没发出）             | PERMANENT | **直接 DEAD**，`error_class=SSRF_BLOCKED`               | 目标落在禁止网段或被策略拦下，重试一万次结果一样（§4.10）                                                         |

**这是整套设计里最重要的一个判断**："失败就重试 3 次"是无分类重试——一个 400 被重试 10 次，占满 worker、拉起告警风暴，还让真正的 5xx 排不上队。

**3xx 归 PERMANENT 是 T2.3 的一次修正**：初版按"跟随重定向是 SSRF 校验的职责"把它归为 RETRYABLE，但 SSRF 校验决定的是"要不要跟随"，与"该不该重试"无关——既然投递器禁跟随，3xx 就是一个确定的失败结果，重试只会用整份预算换同一条 302。

**对"供应商状态码不规范"的处理：不兼容，让它显性化。** 有供应商用 400 表示"系统忙"，本版**不做按端点/按 host 的例外配置**（实现阶段曾做过一版，review 后删除）。三条理由：① 这是下游的接口不规范，加配置适配等于把对方的缺陷固化成我方的长期维护项；② 任何按 host 的覆盖都假设"同 host 下所有路径语义一致"，一旦不成立，为 A 路径配的例外会让 B 路径的真错误重试满 3.5h——**一条正确的配置制造出新错误面**；③ 代价不对称本身就支持保守：判死可人工重放（可逆），判重试会烧光预算且可能重复业务动作（不可逆）。准入门槛（有量 / 无议价权 / 无更便宜替代，三条同时成立）与翻案方式见 docs/T2.1-失败分级与退避.md §2.3。

**退避**：`delay(n) = min(cap, base × 2^(n-1)) × rand(0.5, 1.5)`，默认 base=10s、cap=1h、max_attempts=10，覆盖约 3.5 小时。加全抖动是为了防止供应商恢复瞬间所有任务同一秒涌出（惊群）把对方再打挂一次。

### 4.5 端点隔离：并发隔离 + 熔断

- 按**端点**（`scheme://host:port`，不是裸 hostname）维度做并发信号量 + 熔断器（6 桶 × 10s 的滑动窗口，失败率 > 50% 且样本 ≥ 20 → OPEN 60s）；
- OPEN 期间该端点的任务不真正发出，直接退还并推迟 `next_attempt_at`；端点并发配额满时同样退还，只是延迟短（2s vs 30s）——**配额满只是排队，不是故障**。

**容易漏掉的细节**：熔断跳过**必须不计入尝试次数**。否则供应商挂 30 分钟，会把排队中的健康任务全部"烧"成 DEAD——明明是对方的问题，却耗光我方重试预算，等对方恢复时任务已经死了。

**为什么需要**：不做隔离，一个慢供应商会占满阻塞式 worker 池，其他供应商全部排队——故障扩散。这是需求里"不同供应商"给出的明确信号。

**有意简化**：熔断器只在进程内存、多实例各自独立判断。全局熔断需要共享存储，局部熔断已能保护自身。端点跟踪表另有 1 万条上限（`max-tracked-endpoints`），超出后新端点退化为"不隔离"——**内存有界优先于隔离完整**：端点键来自调用方填的 URL，不设上限就是一条现成的内存耗尽路径。

**T2.5 落地的五处细化**（原设计只到"按 host 熔断"这一层，实现时必须回答下面这些）：

- **端点是 `scheme://host:port`，不是裸 hostname**。同机不同端口是两个下游，按 hostname 归并会把它们的健康度混算；按全 URL 又会让每个路径各自熔断，等于没有熔断；
- **必须补 HALF_OPEN**。原设计只有"OPEN 60s"，到期全量放行等于每 60s 打一轮（对方多半没恢复），比不熔断更糟。改为半开只放 1 个探针，成功才恢复全量；
- **失败样本只算 RETRYABLE**。4xx/3xx 是我们请求的问题，计入的话一个配错凭证的 caller 能把共用该端点的所有人一起熔断；
- **"不计尝试次数"的实现是认领后 `attempt_count - 1`**（认领自增是 T1.2 为了崩溃可回收而定的，不能改），且退还路径**一行明细都不写**——写了会撞 `uk_n_attempt`，任务卡在 PROCESSING 一分钟；
- **跳过延迟取 30s 而非 0**。0 会形成"认领-退还"热循环，且这些行会一直抢走认领名额，饿死其他端点。

### 4.6 死信与重放

- **死信就是一个状态**（`DEAD`），不单独建 DLQ 表/主题——多一份数据就多一处可能不一致；
- **重放必须是显式的人工动作**。一条 DEAD 可能是"供应商明确拒收"（重放必失败）或"供应商已处理但响应超时"（重放造成重复业务动作）——**系统无法区分这两者，只有人知道业务上能不能承受重复**。所以自动重放不做，决策权在人，系统只提供能力；
- MVP 重放接口：`POST /v1/notifications/{id}/replay`，带状态守卫 `WHERE status='DEAD'`（天然防重复点击，不需要分布式锁），`attempt_count` 不归零，`max_attempts` 追加一档预算；
- 批量重放（按 caller + error_class + 时间窗）与重放前探测、摊平下放，列 V1——凭证过期积压几千条 DEAD 时确实需要，但那是运营工具，不是第一版的能力底线。

**T3.2 落地的六处细化**（原设计只有一句"追加一档预算"，实现时必须回答下面这些）：

- **预算档位取调用方当前配置**，不是把 `max_attempts` 翻倍：`new_max = attempt_count + tier`，tier 与提交时同一来源（caller 覆盖值或全局默认）。运营给某 caller 调大预算，下一次重放自动按新档给；如果按"当前 max_attempts 翻倍"实现，重放三次预算就从 10 变 80，语义失控；
- **重放写 `PENDING` 而不是 `RETRY_WAIT`**（与 T2.5 跳过退还相反）：跳过的行下一刻就要被再次认领，RETRY_WAIT 表达"等待重试"；重放的行是刚从 DEAD 里捞出来的，PENDING 表达"回到队列起点"。调度上两者等价，差别只在人怎么读——所以按状态统计的查询必须把 `attempt_count` 一起看（`PENDING + attempt_count>0` 从此是合法组合）；
- **审计与状态迁移同事务（fail-closed）**：新增 `replay_log`（操作人/原因/预算快照），审计写不进去状态就不许迁移——"没有记录的重放"无法追溯，比重放失败更糟。对照投递侧：attempt 明细是无条件插入，因为那两件事不是"动作与它的审计"；
- **`reason` 必填**（422），`operator` 缺省为调用方标识并统一小写。强制写原因让动作慢半拍，拦住"看到 DEAD 就全选重放"的条件反射；
- **不重置 `last_error_class`/`last_status_code`**：重放时刻还能从查单接口看出"它之前是被什么打死的"，成功落库时由 `markSucceeded` 自然清空。审计历史交给 `replay_log`，查询接口的 `replays` 字段补上 DEAD→PENDING 的时间线空洞（T3.1 §6.1 承诺在此兑现）；
- **返回码按"结果"定，不按"动作"定**：状态迁移在返回前已提交（同步小事务，无队列），所以是 **200** 而不是 202；对非 DEAD 的单返回 **409**——422 是"参数不合法"，409 是"参数没问题、但当前状态不允许"，运维脚本靠这个码区分"该刷新列表"和"该改参数"；越权与不存在同为 **404**；`reason` 缺失是 **422**。

**死信必须有声音，且只有一个声音**（T2.3 落地）：

- 状态本身不会说话，所以 `DEAD` 的落库与"宣布"分开：`Dispatcher` 只负责状态落库，`DeadLetterSink` 是死信的唯一宣布者（默认实现写 logger `notify.deadletter` 的结构化警告，M3 接指标/告警时不改 `Dispatcher`）。两处都打 WARN 等于同一条死信报两遍，值班的人会以为死了两条；
- **宣布必须晚于落库**：守卫失败（租约已被接管）时不许发死信——否则会为一个已被他人接手、可能已成功的任务报警，之后没人再相信死信；
- **出口异常必须隔离**：告警系统不可用是常态，不能因为它失败就回滚"已进 DEAD"这个事实，也不能阻断排在后面的出口；
- 死信事件带 `reason`（`PERMANENT` 一次即死 / `BUDGET_EXHAUSTED` 预算耗尽）：两条路径的处置相反——前者改配置后直接重放，后者要先确认下游恢复，否则重放一次又死一次；
- 诊断字段 `error_class` 由**分类器唯一产生**（网络层 `TIMEOUT/DNS/TLS/CONN_REFUSED/IO`，有响应时 `HTTP_3XX/4XX/5XX`）。此前状态判定在分类器、落库字段在投递器，结果 5xx 判对了但 `error_class` 恒为 NULL，按它分组的告警完全看不见 5xx。

### 4.7 幂等键的粒度（最容易写错的一处）

`idempotency_key` 标识的是"**这一次通知提交**"，比订单/用户低一层。**一个订单在表里是多行，不是一行**：下单、付款、发货各提交一次，各用各的键（`order_created:evt_x` / `order_paid:pay_x` / `order_shipped:shp_x`），互不冲突。

|      | `idempotency_key`                                                      |
| ---- | ---------------------------------------------------------------------- |
| 谁生成  | **调用方**（我方一生成就退化成随机数，保护失效）                                             |
| 防什么  | 业务系统超时重试/重复消费导致同一条通知提交两次                                               |
| 不防什么 | 同一订单的不同事件（应该各建一条）；乱序（明确不解决，§4.9）                                       |
| 唯一键  | `UNIQUE (caller_id, idempotency_key)`                                  |
| 校验   | MVP：非空、≤128 字符。`<事件类型>:<事件ID>` 两段式建议写进接入文档，不做强制格式校验（避免引入"事件类型注册"这套小机制） |

**最危险的反例**：拿订单号当幂等键 → 同一订单的"付款""发货"两条通知被判为重复直接丢弃，而接口返回 202，业务方以为成功了——最隐蔽的丢消息方式。接入文档必须给正反例。

### 4.8 接入侧背压：拒绝优于堆积

- **队列健康度守卫（本版唯一的容量保护）**：`PENDING` 积压超阈值（10 万条）或最老到期任务年龄超 30min 时，新请求 `503 + Retry-After`；
- **本版不做 429 限流**：限流回答的是"按调用方分公平"（一个 caller 打满不该让别人排队），与"系统整体还能不能接"是两个维度。本版只需要后者，用 503 表达更准确——429 会让调用方以为自己发多了，实际是系统接不动。按 `caller_id` 的令牌桶列 V1（触发条件见 §8）。

**为什么**：通知系统接收成本极低、完成成本极高（依赖外部），没有背压它就变成无限缓冲区——上游以为提交成功，实际几小时后才投，而"几小时后送达的广告归因"等于没投。**明确说"现在处理不了"，比"收下了但延迟未知"更负责任。**

**T3.3 落地的五处细化**（`docs/T3.3-指标背压与归档.md` §3）：

- **"最老任务年龄"用 `next_attempt_at` 而不是 `created_at`**。用创建时间会把"正在按计划长退避（最长 3.5h）"的正常任务算成积压，30 分钟阈值一过就把整个受理入口关掉——健康的系统因为"有任务正常等待重试"而拒绝所有新流量。只统计 `next_attempt_at <= NOW()` 的到期未认领任务，正常值应接近 0；
- **判断读 10s 采样快照，不查库**（受理 p99 < 50ms 的前提）。代价是清空积压后仍可能多拒 1~2 次，调用方按 `Retry-After` 重试即可；
- **fail-open**：从未采样成功时放行——此时提交本身也会失败，不会静默堆积；而"拒绝一切"会把一次监控故障升级成全站不可用；
- **只挡新提交**，查询与重放照常。事故时运维恰恰需要查单和重放，把管理面挡住等于自断手脚；
- **两个阈值的口径不同，必须知道**：年龄只看 `next_attempt_at <= NOW()` 的到期任务，而条数口径 `notify_queue_backlog` 统计 `PENDING + RETRY_WAIT` **全部**——含正在长退避（最长 3.5h）的任务。所以 10 万条里可能躺着几万条"按计划还要等一小时"的行。这是有意的：条数阈值防"表无限长"，年龄阈值防"送达在变慢"，两者回答不同问题；合成一个数就会在"长退避洪水"和"真的卡住"之间失去分辨力。

### 4.9 顺序：明确不保证（一行都不做）

**不做全局有序，也不做"同实体不并发"的弱有序。**

1. 传输层做到极致也仍然乱序：人工 replay 必然晚于后续通知；同一实体的通知可能投给不同 `target_url`；多实例并发。下游无论如何都要按业务版本号收敛，传输层有序是**冗余**的；
2. 弱有序最危险：一条重试就能打破它，但它**会被依赖**——业务方按"填了就保序"写代码，问题以偶发、低频、无法复现的形式出现。一个"看起来保证、实际不保证"的机制比"明确不保证"更糟；
3. 成本不为零：认领热路径多一个 anti-join、多一个索引。

真需要时（某调用方明确提出且能说清乱序的业务后果）：认领 SQL 加"同 key 内无更早未完成任务"条件即可，加列 + 加索引级别，无迁移。**先不做不是把问题推后，是留一张便宜的回头票。**

### 4.10 安全

本系统**主动向外发起任意 URL 请求**，天生是 SSRF 放大器。

| 风险                                   | 措施                                                                                                                                                                 |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| SSRF（`http://169.254.169.254/`、内网地址） | ① 出站主机白名单（全局、精确匹配，不做通配）；② 解析后校验实际 IP，拒绝私有段/回环/链路本地/**CGNAT**；③ 禁止跟随重定向；④ 非白名单目标强制 HTTPS                                                                            |
| DNS rebinding                        | 投递前**重新解析**并逐 IP 校验（fail closed：任一 IP 落入禁止段即整体拒绝）。连接层绑定受限于 JDK HttpClient，见 docs/T2.4-出站安全与凭证加密.md §6.1                                                     |
| 凭证泄露（Header 里的供应商 API Key）           | AES-256-GCM 加密存储（字段标识作 AAD、IV 每条随机），查询脱敏，日志不打 Header                                                                                                               |
| PII 留存                               | body 与 headers 加密存储；成功 24h / 失败 7d 后由归档任务清空 `body_enc`、`headers_enc` **以及明细里的 `response_snippet`**（下游响应同样会回显手机号、订单号甚至 token）；**只清载荷、不删行**——行是"这条为什么没到"的唯一证据；日志只打长度 |
| 越权                                   | 调用方只能查询/重放自己提交的通知                                                                                                                                                  |

**校验分两层，不能合并**（T2.4 落地）：

- **受理期只做不碰网络的判定**（协议、host 形态、IP 字面量落段）。受理路径不该依赖 DNS——解析抖动时调用方会收到 422，看起来像"你填错了"，实际是我们的 DNS 出问题；受理 p99 < 50ms 的前提也在这里；
- **投递期重新解析**才是防线。域名随时可以改指向，受理时的判断到投递时可能已失效；被拦下的目标按"策略拒绝"处理——一次即 DEAD（`error_class=SSRF_BLOCKED`），且**校验放在解密之前**，被拒的目标连凭证都不该被解出来。

**地址判定有四个 JDK 覆盖不到的盲区**，每一个都是现成攻击面：CGNAT `100.64/10`（**阿里云 metadata `100.100.100.200` 在此段**，而 `isSiteLocalAddress` 只认 RFC1918）、IPv6 ULA `fc00::/7`（JDK 只认已废弃的 `fec0::/10`）、IPv4-mapped 的 IPv6 形式、`0.0.0.0/8` 与 `240/4` 保留段。只按"私有 + 回环 + 链路本地"三类判，会漏掉阿里云那条。

### 4.11 可观测性：三个必须能回答的问题

| 问题          | 手段                                                          |
| ----------- | ----------------------------------------------------------- |
| 现在健康吗？      | 接入 QPS/错误率、队列深度、**最老待投任务年龄**（比队列深度更准）、投递成功率、各端点失败率与熔断状态、死信数 |
| 这条为什么没到？    | 单号一查到底：状态轨迹 + 每次 attempt 的状态码/错误分类/耗时/响应片段                  |
| 是不是某供应商的问题？ | 按端点（`scheme://host:port`）聚合失败率，区分单点故障与全局问题                  |

不接分布式追踪：链路只有 2 跳，结构化日志 + 单号贯穿即可定位。

**T3.3 落地的五个口径**（`docs/T3.3-指标背压与归档.md` §2）：

- **抓取时绝不查库**：Gauge 在 scrape 时才求值，取值函数里写 SQL 会让一次 DB 抖动把整个 `/actuator/prometheus` 打成 500。改由采样器每 10s 刷快照，Gauge 只读内存；采样失败保留上次快照；
- **计数封顶**：`notify_queue_backlog` 用 `SELECT COUNT(*) FROM (... LIMIT maxPending+1)`。监控只需要"有没有越过阈值"，封顶让这条查询在积压 500 万时仍只扫 10 万行。封顶值必须严格大于阈值，否则背压永不触发且没有报错；
- **不给"成功率"建 Gauge**：成功率必须选窗口，而窗口是查询时的事。只存 `success/retryable/permanent` 原始计数，窗口交给 PromQL 的 `rate()`；
- **`endpoint` tag 限基数**：值来自调用方填的 URL，第 201 个之后折叠成 `other`（拒绝注册会让超限端点"看起来没流量"，比"其他"桶更危险）。同理不做 per-endpoint 的 Gauge；
- **`stale_results` 单独计数**：它是"双投正在发生"的唯一直接信号（投递耗时逼近租约），正常应恒为 0，值得单独告警。

**指标清单**（`/actuator/prometheus`，命名统一在 `NotifyMetrics`，业务代码不直接拼字符串）：

| 指标                                            | 类型      | tag                              | 回答什么                                              |
| --------------------------------------------- | ------- | -------------------------------- | ------------------------------------------------- |
| `notify_ingest_requests_total`                | Counter | `route`（当前恒为 `submit`）, `status` | 接入 QPS 与错误率；只数 `POST /v1/notifications`，查询/重放不混进来 |
| `notify_ingest_idempotent_hits_total`         | Counter | `caller`                         | 幂等命中：既证明去重在生效，也说明有人在重试                            |
| `notify_ingest_backpressure_rejections_total` | Counter | `reason`                         | 背压是被"年龄"还是"条数"触发的                                 |
| `notify_delivery_attempts_total`              | Counter | `endpoint`, `result`             | 成功率（窗口交给 `rate()`）与按端点失败率                         |
| `notify_delivery_skipped_total`               | Counter | `reason`                         | 主动不发（熔断/配额满）——**不计入失败**，混进去会让熔断打开时失败率反而下降         |
| `notify_delivery_stale_results_total`         | Counter | —                                | 双投的唯一直接信号，正常恒 0                                   |
| `notify_deadletter_total`                     | Counter | `reason`                         | 死信量与死因（`PERMANENT` / `BUDGET_EXHAUSTED`）          |
| `notify_queue_backlog`                        | Gauge   | —                                | 积压条数（封顶 `maxPending+1`）                           |
| `notify_queue_oldest_overdue_seconds`         | Gauge   | —                                | 最老到期任务逾期秒数——队列健康度主指标                              |
| `notify_queue_processing`                     | Gauge   | —                                | DB 里 PROCESSING 的行数                               |
| `notify_queue_dead`                           | Gauge   | —                                | 尚未处理的死信量                                          |
| `notify_circuit_open_endpoints`               | Gauge   | —                                | 当前 OPEN 的端点数                                      |
| `notify_dispatch_workers_active` / `_size`    | Gauge   | —                                | worker 实时占用 / 池容量                                 |
| `notify_archive_cleared_total`                | Counter | `tier`                           | 归档清了多少行（按 success / failed 分档）                    |

两个 Gauge 要放在一起看：`notify_queue_processing` 是**每 10s 查库**得到的行数（含崩溃遗留的 PROCESSING），`notify_dispatch_workers_active` 是**内存实时**在途数。两者持续背离，说明有一批行卡在 PROCESSING 却没人跑——这正是"租约回收是否及时"的观测点。

## 5. 对外 API 契约

| 接口   | 方法/路径                                              | 说明                                                                           |
| ---- | -------------------------------------------------- | ---------------------------------------------------------------------------- |
| 提交通知 | `POST /v1/notifications`                           | 202 + `{notification_no, status}`；重复提交返回原单号与**原状态**                          |
| 查询状态 | `GET /v1/notifications/{id}`                       | 状态 + 每轮 attempt 明细（最近 200 条）+ `replays`；`headers` 白名单脱敏、body 只回 `has_body`   |
| 人工重放 | `POST /v1/notifications/{id}/replay`               | 仅 DEAD → PENDING，带操作人与原因；**200**（同步已完成），非 DEAD 为 409                         |
| 失败清单 | `GET /v1/notifications?status=DEAD&cursor=&limit=` | 按 caller 鉴权，拉取式消费（不做推给业务方的 webhook，避免"通知失败的通知"递归问题）；`limit` 1~100，默认 20，键集分页 |

| 错误码 | 场景                                                            |
| --- | ------------------------------------------------------------- |
| 400 | 参数类型层面解析不出（`/notifications/abc`、`cursor=xyz`）——纯客户端错误不能变成 500 |
| 401 | API Key 无效                                                    |
| 404 | 单号不存在**或不属于当前调用方**（两者同一个响应，不提供存在性探测）；路径本身不存在同此                |
| 409 | 状态不允许该动作：对非 DEAD 的单重放、或并发重放抢输了——"是你的单，但此刻不能这么动"               |
| 422 | 参数缺失/URL 未过校验/内容不合法（`status=FOO`、`limit=101`、`reason` 为空）     |
| 429 | 超限流（**V1**：按 caller 的令牌桶；本版未启用，容量保护统一走 503）                   |
| 503 | 队列积压，背压触发（带 `Retry-After`）                                    |

## 6. 关键取舍与明确不采纳的方案

### 6.1 取舍一览

| 决策点  | 选项 A                | 选项 B           | 选择  | 依据                       | 承担的代价                                  |
| ---- | ------------------- | -------------- | --- | ------------------------ | -------------------------------------- |
| 队列载体 | MySQL 表             | Kafka/RabbitMQ | A   | 峰值 ~170 QPS 余量充足；避免双写一致性 | 轮询延迟；量大需迁移                             |
| 投递语义 | at-least-once       | exactly-once   | A   | B 物理不可达                  | 下游必须幂等                                 |
| 接入模式 | 202 + 异步            | 同步等待结果         | A   | 隔离外部故障                   | 业务需查状态                                 |

| 部署形态 | 模块化单体               | 微服务拆分          | A   | 无拆分收益                    | 后续拆分需重构                                |
| 并发隔离 | per-endpoint 信号量+熔断 | 每供应商独立队列       | A   | 够用且简单                    | 极端热点端点仍排队（单端点吞吐 ≈ 许可数 × 轮询频率，见 §7 实测③） |
| 失败处理 | 分类+退避+死信            | 统一重试 N 次       | A   | 避免错误放大                   | 维护分类表                                  |
| 顺序   | 不提供                 | 全局/弱有序         | A   | 异步重试天然乱序；弱有序会被依赖（§4.9）   | 顺序交下游收敛                                |
| 多实例  | 无状态+SKIP LOCKED     | 主节点选举          | A   | 无需协调                     | 每实例轮询开销                                |

### 6.2 明确不采纳的「过度设计」

判据（来自作业评估重点，压成三问）：**① 是不是我的职责（越界不做）；② 新增的故障模式是否多于消除的；③ 解决的是已观测到的问题还是想象中的问题。**

| #   | 方案                         | 不采纳的理由                                                                             | 何时翻案                                  |
| --- | -------------------------- | ---------------------------------------------------------------------------------- | ------------------------------------- |
| 1   | 第一版上 Kafka                 | 170 QPS 用不上；重试还要自造延迟 topic，复杂度只是搬家                                                 | 日投递 > 1000 万或多消费方（§8 V2）              |
| 2   | Redis 分布式锁防重复消费            | SKIP LOCKED + 租约已完整解决；用持久性更弱的组件补已解决的问题，反而引入新的不一致面                                  | 基本不会                                  |
| 3   | exactly-once（本地去重表+请求指纹）   | 防不住"下游已处理但响应丢失"的重复，是假安全感；用契约 + 幂等键获得同等业务效果                                         | 基本不会                                  |
| 4   | 拆 5 个微服务                   | 引入 RPC、分布式事务、链路追踪、部署编排四类新故障，解决的"独立扩展"在本量级不存在                                       | 模块边界已用接口 + 表契约隔离，需要时按线切割              |
| 5   | 内置模板引擎渲染请求体                | 渲染是业务语义；要管变量定义、版本、预览、回滚，收益只是省一次序列化                                                 | 基本不会（模板平台是另一个产品）                      |
| 6   | 可视化配置后台 + 多租户 RBAC + 审计 UI | 内部系统、调用方个位数，80% 工期花在表单和权限上                                                         | 调用方超过 ~10 个且接入排期成为瓶颈                  |
| 7   | 事件溯源 / CQRS                | 状态机 + attempt 明细已满足可追责；ES 的收益本场景用不上                                                | 基本不会                                  |
| 8   | 全链路追踪（Jaeger/OTel）         | 链路 2 跳，单号串日志即可                                                                     | 链路变长（引入 MQ、多跳）时                       |
| 9   | 自适应/AI 智能重试                | 无历史数据、不可解释、不可测试；工程要可预测的固定策略                                                        | 基本不会                                  |
| 10  | PBKDF2+随机盐存请求体指纹           | 真实评审意见的修正是错配：随机盐破坏"相同明文→相同指纹"的可比性，且 30ms/次的迭代成本与受理 p99 冲突。该字段的功能在 MVP 中整体不需要，直接不引入 | 若合规要求归档后内容比对，用 HMAC-SHA256（密钥化，确定性保留） |
| 11  | DB 触发器 + 事件通知做提交唤醒         | 逻辑藏进数据库、无法单测、与 binlog/复制交互不可控                                                      | 不翻案                                   |

### 6.3 判据的自我限制

尺子只做**证伪**不做证明；每条翻案条件都写在表里。今天的过度设计，量级或需求变化后可能变成最小必要设计——判据的价值在于说清**什么时候该翻案**。

## 7. 容量与量级假设

**先声明：这些是假设，不是测量值。** 做法是给量级区间 + 证明结论对误差不敏感。

| 步骤          | 计算                                                |
| ----------- | ------------------------------------------------- |
| 日均量         | 假设 100 万条/天（三类场景合计，含一条事件多条通知）                     |
| 业务集中        | 70% 在 10 小时 → ~19 QPS                             |
| 最坏 10 分钟    | 营销活动 10% 量压进 10 分钟 → ~167 QPS                     |
| 设计点         | **150 QPS**；容量校验按 200 QPS                         |
| 有效 QPS（含重试） | 150 × 1.15 ≈ **172**                              |
| Worker 并发   | Little's Law（均值 0.2s）≈ 34；按"供应商整体变慢到 1s"取 **200** |
| DB 写入       | 172 × **4 写** ≈ 690 行/秒 → 单实例 MySQL 余量 **~4.3 倍** |

**"4.3 倍"的分母是单实例 MySQL 约 3000 行/秒**——按本机 Docker（8.0.46、单盘 fsync ~3ms）的写入能力取的保守基线，不是压测上限（压测只压到 600 行/秒，没去探顶）。换 NVMe 或调大 `innodb_flush_log_at_trx_commit` 分母会变大，结论只会更宽松；反过来分母取 1500，余量掉到 2.1 倍，选型仍然不变。**这个数的作用是给量级，不是给承诺。**

> **T4.2 实测回填**（150 QPS × 60s，12 个 mock 端点，MySQL 8.0.46 容器）：
> ① **每单是 4 写不是 2 写**（受理 INSERT + 认领 UPDATE + 明细 INSERT + 终态 UPDATE），
> 实测 600 行/秒 = 150 × 4，与原估算 350 差 1.7 倍——不到"重估"的 3 倍阈值，选型结论不变，
> 但"余量 9 倍"应改为 ~4.3 倍；
> ② **worker = 200 站得住**：下游 200ms 时实测在途均值 26.4（理论 150×0.2=30），
> 按比例"慢到 1s"时 ≈150，留 25% 余量；
> ③ 单端点 150 QPS 时投递只消化 ~57/s——受 `max-concurrent-per-endpoint` 约束，
> 见 `docs/T4-交付.md` §2.5。

**敏感性分析**：日量 30 万（余量 14×）/ 100 万（4.3×）/ 300 万（1.4×，启动归档）/ 1000 万（<1×，必须上 MQ）。**估算偏差 3 倍以内不改变选型，10 倍才翻转**——所以"DB 即队列"对估算误差是鲁棒的。上线首周用实际峰值 QPS、p99 耗时、最老任务年龄与本节对比，偏差超 3 倍重估。

## 8. 演进路线（按触发条件，不按时间）

| 阶段     | 形态                        | 触发条件                           | 关键动作                               |
| ------ | ------------------------- | ------------------------------ | ---------------------------------- |
| **V0** | 单体 + MySQL 队列 + 轮询 worker | —                              | 本文档全部内容                            |
| **V1** | 多实例 + 归档 + 运营增强           | 日投递 > 300 万，或单表 > 5000 万       | 按月归档；按 caller 限流；批量重放工具；失败清单日报     |
| **V2** | 接入与投递解耦，Kafka 承载投递        | 日投递 > 1000 万，或出现多消费方（审计/计费/分析） | 接入写 outbox → CDC 投 Kafka；DB 退回状态存储 |

**演进原则**：每次升级由观测到的具体数字或事故触发，不由"将来可能会大"触发。
**不会被现有设计卡死**：① 接入与投递只通过 `notification` 表契约交互 → 可换 MQ；② 失败策略收敛在单一 `RetryPolicy` → 可换规则引擎；③ 顺序、优先级都有加列级的回头路（§4.9）。

## 9. 测试与验收

### 9.1 SLA 目标（V0）

| 指标             | 目标                                                                                                                  |
| -------------- | ------------------------------------------------------------------------------------------------------------------- |
| 受理接口 p99       | < 50ms                                                                                                              |
| 送达延迟 p50 / p99 | < 1s / < 5s（下游正常时）                                                                                                  |
| 数据零丢失          | 已受理请求在任何单点崩溃后仍被投递                                                                                                   |
| 死信可见性          | 进入 DEAD 后 1 分钟内可见：结构化日志 `notify.deadletter` + `notify_deadletter_total`（告警规则配在 Prometheus/日志平台侧，本系统只负责"宣布"，不内置告警通道） |

> **T4.2 实测**（150 QPS × 60s，12 端点，见 `docs/T4-交付.md` §2.2）：
> 纯受理 p50/p99 = **3.2 / 16.9ms**（达标）；
> 投递同时满负荷时 p50 不变、p99 三轮分别是 **41.3 / 59.8 / 198.6ms**——前两轮是本机 Docker 卷的
> 提交 fsync 排队（关调度器即回落到 16.9ms，GC 最大暂停 9.5ms 不是原因），第三轮是同一次运行里
> 宿主机层面的停顿（该轮 max 1251ms，而 GC 最长 9.5ms）。**三次都列出来，不挑好看的两次。**
> 换真机 NVMe 或按 §2.7 做批量提交后，这条目标才能在满负荷下稳定成立——边界写进 README，
> 不用"平均一下就好看了"的方式糊过去。

> **送达延迟没有单独测分位数**：T4 只做到了"投递侧 8250 单在 60s 内全部收敛到 SUCCEEDED、
> 积压排空"，这能证明没有滞留，但没有 p50/p99 曲线。要测它需要给每条单记
> `SUCCEEDED_at - created_at`（当前只在 `updated_at` 里间接有），属于 V1 的观测增强。
> 这条缺口写在明面上，比拿"全部成功"冒充"p99 < 5s"诚实。

### 9.2 关键测试用例

1. **幂等**：同 `(caller_id, idempotency_key)` 重复提交，返回同一单号，表里只有一行；
2. **崩溃恢复**：认领后杀掉 worker，验证租约过期后被其他实例接手、attempt_count 正确递增；
3. **双投窗口**：模拟"请求已发出、结果未落库"时崩溃 → 下游收到两次 → 证明 at-least-once 契约（不是缺陷，是语义验证）；
4. **失败分级**：400 一次进 DEAD 不重试；5xx 按退避曲线重试且间隔带抖动；429 遵守 `Retry-After`；
5. **熔断隔离**：mock 一个端点持续 5xx，验证该端点任务被推迟且**不计尝试次数**，其他端点投递不受影响；恢复后明细的 `attempt_no` 不出现空洞；
6. **背压**：积压/年龄任一超阈值后新请求返回 503 + `Retry-After` 且不落库；**反向用例同样重要**——处于长退避中的老任务不得触发背压（用 `created_at` 算年龄就会踩这条）；
7. **集成测试隔离**：测试环境关闭调度器自动启动（`@Scheduled` 后台线程会把测试数据当真实流量投出去——这是实现阶段真实踩过的坑），改为手动触发 `pollOnce()`；
8. **查询边界**：他人单号与不存在的单号同为 404；`headers` 只回白名单键、其余 `****`；body 只回 `has_body` 不回内容；`/notifications/abc` 是 400 不是 500；
9. **重放**：对非 DEAD 返回 409；DEAD → PENDING 且 `attempt_count` 不归零、`max_attempts = attempt_count + 当前档位`；审计写失败则状态不迁移（fail-closed）；
10. **归档**：只清 `body_enc`/`headers_enc`/`response_snippet`，行与明细仍在，`updated_at` 不被刷新；同一批重跑不重复计数；
11. **指标口径**：DB 不可用时 `/actuator/prometheus` 仍返回 200（Gauge 只读快照）；`endpoint` tag 超过 200 个后折叠为 `other` 而不是拒绝注册；
12. **下游去重契约**：真实投递必带 `X-Notification-Id`（等于库里单号）与 `X-Idempotency-Key`（等于提交时的幂等键）；调用方自带同名头被取代，每个身份头只有一个值。

## 10. 已知风险与待确认问题

1. **调用方能否处理 503？** 本版的容量保护只有 503 + `Retry-After`（429 是 V1 的按 caller 限流）。若业务方坚持"必须永远返回成功"，背压只能改成降级队列，复杂度上升。接入前必须确认；
2. **供应商对 4xx 的使用是否规范？** 有供应商用 400 表示临时故障。本版**不做例外配置**，4xx 一律进死信靠人工重放（§4.4）；真要加，准入条件见 docs/T2.1-失败分级与退避.md §2.3（有量 / 无议价权 / 无更便宜替代）。更好的动作是往接入规范里加一条："临时故障必须用 5xx/429，禁用 4xx 表忙"；
3. **企业内几个业务系统、是否已有事件总线？** 若有总线，本系统可退化为纯投递引擎（§1.4）；
4. **PII 保留期是否满足合规？** 法律/风控问题，需与合规确认；
5. **容量假设可能偏 3 倍以上。** 敏感性分析已证明 3 倍内选型不变；若实测 10 倍，V2 提前启动。
